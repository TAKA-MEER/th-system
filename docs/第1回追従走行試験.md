# 第1回追従走行試験

- 実施日: 2026年8月17日
- 目的: 現在の追従走行が実用に足るかを検証する
- 実施体制: 1名でロボットの起動・追従開始・見守りを兼務

## 試験条件

| 項目       | 内容                                                                                                                                                  |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| コース     | 3階を1周（約170m）                                                                                                                                    |
| 走行モード | 追従走行                                                                                                                                              |
| 追従速度   | `follow_planner_mapless` の既定値は `v_max = 0.3 m/s` だが、本試験ではWebUIのライブパラメータ変更機能を用い、当日のみ約1m/sまで引き上げて走行した |
| 環境       | 屋内（3階フロア）                                                                                                                                     |

## 結果

所要時間: **10分50秒**

走行中に発生したイベントを表に整理する（回数は原メモの記録に基づく）。

| イベント                       | 回数 | 備考                                 |
| ------------------------------ | ---- | ------------------------------------ |
| 緊急停止                       | 5    | すべて壁への衝突が原因               |
| 対象見失いによる再選択         | 12   |                                      |
| 追従対象の乗り移りによる再選択 | 1    | 追従対象が物へ切り替わった           |
| ESP32ロスト                    | 1    | ESP32との接続断                      |
| 手動操作による復帰             | 5    | 上記イベントからの復帰手段として使用 |

いずれの項目も発生タイミングや場所の詳細記録は残っていないため、本資料では回数のみを事実として扱う。

また、直線区間でも機体が左右に約1mほど振れて（蛇行して）走行しており、まっすぐ安定して走れているとは言い難い状態だった。

## 考察

原メモに記載されていた考察は以下の通り。

- ESP32が走行系の通信をすべて担っている構成による遅延が、緊急停止・見失いの一因になっている可能性がある。
- 本試験時のWi-Fi状態は比較的安定していたが、Wi-Fi不調時には「駆動系の通信に異常」（ESP32接続タイムアウト）が繰り返し発生する。
- 今回使用した追従速度帯（最大1m/s付近）は、既定値（0.3m/s）から引き上げた状態であり、この速度域でのパラメータ調整はまだ十分に行っていない。
- 所要時間（10分50秒）が長くなった一因として、標準機の最高速度自体が約1m/sであることが挙げられる。パラメータ調整以前に、機体性能そのものが速度上限になっている。

**背景（参考）**: ESP32側のウォッチドッグタイムアウトは、本試験の実施前（2026-08-05）に300ms→600msへ緩和済みである。esp32_bridge が `/cmd_vel` を20Hzで再送していても、WebSocketが乗るTCPのHead-of-Line blockingにより1パケットのロスが再送完了まで後続の受信をブロックするため、送信頻度を上げるだけではWi-Fiジッタ由来の誤発動を防げなかったことによる。この変更が本試験結果にどの程度影響したかは本試験のログからは切り分けられておらず、参考情報として付記するに留める。

## まとめ・今後の方針

10分50秒・約170mの1周の間に、緊急停止5回・見失いによる再選択12回・乗り移り1回・ESP32ロスト1回・手動復帰5回が発生しており、追従走行だけで安定して移動できる状態には達していない。毎回の移動を追従走行に頼るのは運用上の手間が大きく、根本的な改善が必要と考えられる。

今後は追従走行自体の改善を継続しつつ、教示再生走行（記録済み経路を単独でなぞる方式）による代替手段の確立も並行して目指す。なお `docs/plan/task.md` には、ネットワークの改善→追従走行の速度改善→改善後の再試験→教示再生の開発、という方向性が検討メモとして挙がっており、本試験の結果はこの検討の裏付けとなる位置づけである（`docs/plan/` は未確定の検討メモであり、確定した方針ではない点に留意）。

また、標準機の速度的な限界への対策として、ソミック（SOMIC）の自律走行ロボット「サポット（SUPPOT）」のような既製の自律走行ロボットプラットフォームの導入も選択肢として視野に入れている。サポットは4輪駆動・タイヤ式で不整地や傾斜（実用登坂角度20度）に強く、作業者への追従走行にも対応しており、最高速度は改良モデルで約6km/hに達する。標準機の現状の最高速度（約1m/s≒3.6km/h）を上回るため、比較検討の対象としたい。
