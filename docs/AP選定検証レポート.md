# 移動ロボットの無線リンク品質 — アクセスポイント選定から、真の原因の特定まで

**対象**: 試験員に追従して移動するクローラーロボット（配電盤の上部確認作業を支援する機体）
**測定期間**: 2026-08-18 〜 2026-08-20
**状態**: **完了。**当初の目的（アクセスポイントの選定）は達成し、その過程で見つかった真の原因も解消した。

> **本書の要点**
>
> 「どのアクセスポイント構成が最良か」を決めるために測定を始めた。
> 途中で **2 度、支配的な要因を取り違えた**。最終的に判明したのは、
> **制御用マイコン（ESP32）の無線が、負荷時に 600 ms 単位で丸ごと停止していた**ことだった。
> マイコンから親機の役目を降ろすことで、**受信の最悪値は 1920 ms から 300 ms（6.4 分の 1）**になった。
>
> 本書は結論だけでなく、**否定された仮説と、その否定に使った証拠**を等しく記録している。
> 3 つの仮説がデータによって覆され、そのうち 2 つは**筆者自身が一度は「確定」と書いたもの**である。

| 項目 | 変更前 | **変更後** |
| --- | --- | --- |
| 親機（アクセスポイント） | 制御マイコン（ESP32） | **Raspberry Pi**（無線チャンネル 1） |
| 制御データの最大受信ギャップ | 1920 ms | **300 ms** |
| 制御データの途切れ（20 分あたり） | 10 回 | **1 回** |

## 1. なぜアクセスポイントの選定が「速度」の問題なのか

この機体は、制御用マイコン（ESP32）とレーザ測域センサ（LiDAR、Raspberry Pi 経由）が
**どちらも Wi-Fi で PC と繋がっている。**PC は機体に載せない構成である。

無線なので、データは一定間隔では届かない。**受信が途切れる時間（受信ギャップ）**が発生する。
安全上、一定時間データが来なければ「通信断」と判断して車輪を止める必要があるが、
このタイムアウト値は 2 つの制約に挟まれる。

| 制約 | 内容 | 破ると何が起きるか |
| --- | --- | --- |
| **下限** | 平常時の受信ギャップより十分長いこと | 正常なのに通信断と誤判定し、走行が頻繁に止まる |
| **上限** | 「通信が切れてから止まるまでに進む距離」が許容値を超えないこと | 通信が切れたまま走り続け、衝突する |

上限の制約を式にすると次のようになる。

```
最高速度 ≤ 許容侵入距離 ÷ タイムアウト
タイムアウト ≥ 受信ギャップの尾（最悪値）＋ 余裕
∴ 最高速度 ≤ 許容侵入距離 ÷ (受信ギャップの尾 ＋ 余裕)
```

**つまり、受信ギャップの最悪値がそのまま最高速度の上限を決める。**
無線品質の改善は「通信が安定する」という話ではなく、**「どこまで速く走ってよいかが決まる」**という話である。
これが本検証の動機である。

## 2. 測定の方法

### 2.1 測定手法そのものを 2 回作り直した

**本検証で最も高くついた失敗は、測り方の選択にあった。**

| 段階 | 測っていたもの | なぜ不十分だったか |
| --- | --- | --- |
| 第 1 段階 | **直近 30 秒の窓で計算した分位点**を CSV に記録 | **窓の中で平均されて外れ値が消える。**「LiDAR は無傷」という誤った結論の直接の原因（§6） |
| 第 2 段階 | **メッセージが届いた生の時刻**をすべて記録 | 到着間隔は分かるが、**原因の切り分けができない** |
| **第 3 段階** | **生の到着時刻 ＋ パケット捕捉 ＋ ping を、同じ時計で同時に記録** | 跳ねの瞬間に**どの層まで止まっていたか**が分かる。これで初めて原因に届いた |

**「到着間隔」は「遅延」ではない。**毎回きっちり 1 秒遅れて届く経路は、到着間隔だけを見れば
完璧に 100 ms 間隔である。到着間隔の測定は、**一定の遅延に対して構造的に盲目**である。
このため遅延側は別途、送信時刻のスタンプを使って測定した（§8）。

### 2.2 測るもの

| 経路 | 中身 | 期待周期 |
| --- | --- | --- |
| 制御 | 車輪の実速度フィードバック（ESP32 → PC） | 100 ms（10 Hz） |
| 測域 | レーザ測域データ（Raspberry Pi → PC） | 100 ms（10 Hz） |
| **ICMP（ping）** | **マイコンの無線チップ自身が返す応答** | 100 ms |

**ping を並走させたことが決定打になった。**ICMP はマイコンの無線処理層が返すため、
**アプリケーションが固まっていても本来は返り続ける。**それが同時に止まるなら、
止まっているのはアプリではなく無線そのものである。

### 2.3 測定条件（**ここが結果を左右する**）

**「実運用と同じ負荷」で測ることが絶対条件である。**
条件を軽くすると実運用より良い値が出て、その値から決めたタイムアウトは実運用で誤検知を起こす。

| 条件 | 内容 |
| --- | --- |
| センサ | LiDAR を回転させ、データを配信し続ける |
| 制御 | 速度指令を 20 Hz で送り続ける |
| **駆動系** | **エンコーダ・IMU・モータドライバを接続する**（§3 の理由により必須） |
| 位置 | 機体と PC の距離・向きを候補間で変えない |
| **無線チャンネル** | **候補間で必ず揃える**（§7.2 の理由により必須） |
| 時間 | 比較段階は 15〜20 分 |

## 3. 仮説 1 — エンコーダの割り込みが無線を阻害しているのではないか（**否定**）

当初、駆動系のコネクタを外した状態で測定を開始した。しかし**この状態の測定値は使えない**ことが分かった。

### 3.1 何を疑ったか

車輪の回転量を読むエンコーダは、**信号線 4 本すべてに「変化のたびに割り込みをかける」方式**で実装されている。
マイコンのハードウェア機能（パルスカウンタ）は使っていない。

エンコーダの分解能は 1 回転あたり 4096 カウント、駆動輪は 1 回転で約 0.126 m 進む。
したがって割り込みの発生頻度は次のようになる。

| 走行速度 | 1 秒あたりの割り込み回数（左右合計） |
| --- | --- |
| 0.3 m/s | 約 19,500 回 |
| **0.5 m/s** | **約 32,500 回** |
| 1.0 m/s | 約 65,000 回 |

マイコンの割り込み処理は 1 回あたり数マイクロ秒だが、**無線処理のタスクを不定期に横取りする。**
つまり**速く走るほど無線が不安定になり、無線が不安定なほど速く走れなくなる**という関係を疑った。

### 3.2 測定結果 — 差が出なかった

車体を台に乗せて車輪を空転させ、走行させずに実運用相当の割り込み負荷を再現して比較した。

| 条件 | 経路 | 受信ギャップ p99 |
| --- | --- | --- |
| 車輪停止 | 制御 | 140.6 ms |
| **車輪回転 (0.5 m/s)** | 制御 | **139.5 ms** |
| 車輪停止 | 測域 | 211.5 ms |
| **車輪回転 (0.5 m/s)** | 測域 | **221.1 ms** |

**毎秒 3 万回を超える割り込みを掛けても、受信ギャップは変わらなかった。**
使用しているマイコンは 2 コアであり、無線処理と割り込み処理が競合しない構成になっているか、
1 回あたりの割り込み処理が想定より軽いものと考えられる。

**したがってパルスカウンタへの移行（ファームウェアの大規模改修）は見送った。**
ただし「未検証」ではなく**「0.5 m/s では有意差なし」という実測付きの結論**として記録する。
より高速な走行では割り込み頻度が比例して増えるため、速度域を上げた際に再確認する。

**この検証の価値は、否定的な結果そのものにある。**
推測のまま実装を書き換えていれば、効果の無い改修に工数を使ったうえ、
本当の原因が残ったままになっていた。

## 4. 比較する構成

**アクセスポイントは機体側に置く必要がある。**保管場所と試験場の間を約 200 m 移動するため、
固定設置のアクセスポイントでは通信範囲を覆えない。したがって「機体上のどの装置が親機を務めるか」の選択になる。

| 案 | 帯域の分離 | 当初の評価 | **最終評価** |
| --- | --- | --- | --- |
| ① 制御マイコン（ESP32）が親機（**当時の現行**） | 不可 | 追加費用ゼロ。**当初の本命** | **不採用。**これが原因だった（§6） |
| ② **Raspberry Pi が親機** | 不可（無線は 1 系統） | 送信元と親機が同一機になり競合すると予想し、**低く評価していた** | **★ 採用。**実測で最良（§7） |
| ③ 小型ルーターを機体に搭載 | **可能** | 制御と測域を別の帯域に分けられる唯一の案。**最有力候補** | 保留。②で足りたため導入不要 |
| ④ 親機専用のマイコンを追加 | 不可 | 実効速度が測域データの流量に耐えない | 除外（当初のまま） |

**当初は「帯域を分けられるかどうか」が最大の差だと考えていた。**
実際に効いたのはそこではなく、**制御マイコンに親機の仕事をさせるかどうか**だった。
②を低く評価していた根拠（同一機での競合）は、**測定せずに立てた推測**であり、外れた。

## 5. 最初の転換点 — 省電力設定（**部分的に正しかったが、支配要因ではなかった**）

### 5.1 気づいた経緯

Raspberry Pi を親機にした初期の構成で、**制御と測域の 2 つの独立した通信が、同じ瞬間に同時に途絶する**
現象が観測された（0, 153, 478, 549, 652, 723, 861 秒 — 両者で完全に一致）。

送信元が別なのに同時に止まるなら、**原因は送信元ではなく、両者が共有する要素**にある。
そこで両端の設定を調べたところ、**マイコン側も Raspberry Pi 側も Wi-Fi の省電力が有効**だった。

省電力が有効な無線機は、ビーコンの間隔ごとにしか受信しない。
その間に届いたデータは親機側に溜められ、まとめて配送される。

### 5.2 設定を直した結果

| 経路 | 省電力あり | **両端で省電力を無効化** |
| --- | --- | --- |
| 制御 | p99 140.6 ms ／ max 542.1 ms | p99 159.4 ms ／ max **603.4 ms** |
| 測域 | p99 211.5 ms ／ max 623.9 ms | p99 **103.9 ms** ／ max **104.2 ms** |

**測域データの途絶は消えたように見えた**（最大値 104.2 ms ＝ 期待周期 100 ms のほぼちょうど）。
省電力の無効化は**実際に効果があり、最終構成でも維持している。**

**しかしこの表は、§2.1 の第 1 段階の測り方（30 秒窓の分位点）で得たものであり、
外れ値が隠れていた。**生の到着時刻で測り直すと、測域データも 622 ms 跳ねていた（§6.2）。

### 5.3 設定は「変更しただけ」では効かない（**運用上の落とし穴**）

省電力を無効化するコマンドを実行した直後に測定したところ、**改善が見られなかった。**
その後、別件で装置を再起動したところ、初めて効果が現れた。

**稼働中の無線接続には設定が反映されず、再接続（または再起動）が必要だった。**
「設定した」ことと「効いている」ことは別であり、**設定値ではなく実際の状態を確認する必要がある。**

## 6. 真の原因 — マイコンの無線が、負荷時に丸ごと停止していた

### 6.1 一度は「電波は無罪」と結論した（**誤り**）

§5.2 の結果は「制御経路だけが 603 ms 跳ね、測域は完璧」と読めた。
片方の経路だけが悪いなら原因は電波ではないはずで、それを確かめるために
**無線区間だけを ICMP で 10 分間叩いた。**

| 指標 | 値 |
| --- | --- |
| 送受信 | **3000 / 3000（損失 0 %）** |
| RTT 中央値 | 3.5 ms |
| RTT 最大 | **33.2 ms** |
| 100 ms を超えた RTT | **0 件 / 3000** |

ここから **「無線区間は健全。アクセスポイントを差し替えても跳ねは消えない」**と結論し、
**アクセスポイント比較の打ち切りを一度は決定した。**

**この結論は誤りだった。**測定時に **ROS のノードを一切起動していなかった**——
つまり**無負荷で測っていた。**跳ねは負荷時にしか起きない。

### 6.2 負荷を掛けて、4 系統を同じ時計で同時に記録した

パケット捕捉・ROS の受信時刻・2 系統の ping を、**同一の時計で 20 分間**記録した。

| 系統 | 経路 | 400 ms 超の途切れ | 最大 |
| --- | --- | --- | --- |
| 制御データ | TCP / WebSocket | 10 回 | **1920 ms** |
| **測域データ** | **マイコンが中継** | **10 回** | **622 ms** |
| **ping（マイコン宛）** | **マイコンの無線チップが返す** | **10 回** | **641 ms** |
| **ping（Raspberry Pi 宛）** | **マイコンが中継** | **10 回** | **627 ms** |

**跳ねの瞬間、4 系統すべてが同時に途切れていた。**
2 回の測定で観測した **13 回の跳ねすべてで、ping が同時に途切れていた。**

ping はマイコンの無線処理層が返すので、アプリが固まっていても本来は返る。
それが止まる以上、**止まっているのは無線そのもの。**
マイコンの無線が **520〜640 ms、丸ごと停止していた**（20 分で計 6.06 秒）。

### 6.3 負荷依存であることの確認

| 条件 | 400 ms 超の途切れ |
| --- | --- |
| **無負荷**（§6.1 の測定・600 秒） | **0 回**（最大 230.7 ms） |
| **負荷あり**（10 Hz フィードバック ＋ 20 Hz 速度指令 ＋ 測域データ中継・1200 秒） | **10 回** |

無負荷では完璧なので、**電波環境や設置場所ではなく、マイコンの処理能力が律速**である。

### 6.4 なぜ測域データも同時に止まったのか

マイコンが親機を兼ねていたため、**Raspberry Pi の測域データもマイコンを経由していた。**

```
Raspberry Pi ─┐
              ├─→ 制御マイコン（親機）─→ PC
マイコン自身 ─┘
```

マイコンが止まると、無関係なはずの測域データも同時に止まる。
**§5.2 で「測域は完璧」と見えたのは、30 秒窓の分位点で外れ値が消えていたためである。**

### 6.5 TCP は原因ではなく増幅器

制御データは WebSocket、つまり TCP で運ばれる。跳ねのうち 3 回で再送が発生していた。

| 無線が止まった時間 | アプリに届かなかった時間 | 倍率 |
| --- | --- | --- |
| 808.9 ms | 1342.5 ms | 1.7 倍 |
| 756.2 ms | 1380.5 ms | 1.8 倍 |
| 1243.0 ms | 1920.3 ms | 1.5 倍 |

TCP は順序を保証するため、**1 パケットの損失が再送完了まで後続の受信をすべてブロックする**
（Head-of-Line blocking）。600 ms 前後の無線停止が、**1.3〜1.9 秒のアプリ層断**になっていた。

**TCP は原因ではないが、被害を 1.5〜2.3 倍にしていた。**

### 6.6 中継を外すと 7 割消えた

仮説を検証するため、Raspberry Pi の無線を切り、**測域データを一時的に有線に移した。**
マイコンは自分のデータだけを扱う状態になる。

| 指標 | 中継あり | **中継なし** |
| --- | --- | --- |
| 制御データの跳ね | 10 回 | **3 回** |
| **うち純粋な無線停止** | **7 回** | **0 回** |
| 制御データの最大ギャップ | 1920 ms | 1482 ms |
| 測域データの跳ね | 10 回 | **0 回** |

**中継負荷を降ろすだけで、無線停止が 7 割消えた。**
残る 3 回もすべて ping が同時に途切れており、**中継とは無関係な、マイコン自身の処理に
起因する無線停止**が別に存在する（候補: 慣性センサの読み取り、制御ループ、無線タスクの
スケジューリング。**未特定**）。

ただしこの構成は有線に依存するため、**走行できない。**恒久策にはならない。

## 7. 解決 — 親機を Raspberry Pi に移した

Raspberry Pi を親機にし、制御マイコンを子機に変更した。**追加のハードウェアは不要。**

### 7.1 結果

**20 分あたり**

| 構成 | 制御の跳ね | 測域の跳ね | 制御の最大 | ping の途切れ | TCP 再送 |
| --- | --- | --- | --- | --- | --- |
| マイコンが親機（中継あり） | 10 | 10 | 1920 ms | 10 | 24 |
| マイコンが親機（測域は有線） | 3 | 0 | 1482 ms | 3 | 24 |
| Raspberry Pi が親機（**チャンネル 6**） | — | 54 | 1881 ms | 55 | — |
| **★ Raspberry Pi が親機（チャンネル 1）** | **1** | **0** | **300 ms** | **0** | **0** |

**制御データの最大ギャップが 1920 ms → 300 ms（6.4 分の 1）。**
TCP 再送は **36,892 パケット中 0 件**。測域データは跳ねゼロ（最大 200.1 ms）。
しかも**有線を使わない＝走行できる構成**である。

残る 1 回（300.0 ms）も ping が同時に 296.9 ms 途切れており、
§6.6 で残った「マイコン自身の処理起因の無線停止」と同じ性質と思われる。
**ただし 600 ms → 300 ms に半減している。**

### 7.2 チャンネルの選択を誤ると、比較そのものが無効になる

**最初、Raspberry Pi の親機をチャンネル 6 に置いて測り、「5 倍悪化」という結果を出した。**

| チャンネル | 周囲の他の親機の数 | 最強信号 |
| --- | --- | --- |
| 1 | 12 | 57 |
| **6** | **17** | **92** |
| 11 | 14 | 87 |

**チャンネル 6 は、この場所で最も混雑していた。**
一方、比較対象であるマイコンの親機機能はチャンネル 1 に固定されていた
（実装がチャンネルを指定していないため既定値になる）。

**同じ土俵で比べていなかった。**チャンネルを 1 に揃えただけで、
ping の途切れが **55 回 → 0 回**になった。

**比較実験では、比較対象以外の条件が本当に揃っているかを、実装まで遡って確認する必要がある。**

### 7.3 実施時に踏んだ落とし穴

| 事象 | 原因 | 対処 |
| --- | --- | --- |
| **マイコンが親機に一切接続できない**（接続要求すら届かない） | 親機側の**管理フレーム保護（802.11w）**が既定で有効。マイコン側のライブラリが非対応 | 保護を無効化し、暗号方式を明示的に固定 |
| 上記の診断が難しかった | 機体の基板構成上、**マイコンのログを読み出せない**。失敗が無言で起きる | 親機側の接続ログから、要求が届いていないことを確認した |

## 8. 併せて判明したこと

本検証の主題ではないが、同じ機体で同時期に測定し、対処したものを記録する。

### 8.1 人物検出の遅れが半分になった

無線とは別に、**測域データから人物を検出するまでの遅れ**を実測した。
「到着間隔」の測定では見えない、**一定の遅延**の側である（§2.1）。

| 条件 | 検出処理の遅延 | 検出周期 | **実効の古さ** | 1 m/s でのずれ |
| --- | --- | --- | --- | --- |
| 測域センサ = 高密度モード | 348 ms | 272 ms | **348〜620 ms** | **0.35〜0.62 m** |
| **測域センサ = 標準モード** | **179 ms** | **154 ms** | **201〜355 ms** | **0.20〜0.36 m** |

「実効の古さ」＝ 追従の計画部が握っている人物の位置が、**どれだけ前の姿か**。

**同時に、無関係なはずの前処理フィルタが 141 ms → 22 ms（−84 %）になった。**
これが遅延の正体を示している。**計算そのものの時間ではなく、CPU が混雑したことによる
待ち行列**だった。測域点の数が半分になって CPU に余裕ができた結果、
前処理も推論も同時に速くなった。

**「重い処理を軽くする」より前に、「その処理が待たされていないか」を見る必要がある。**

### 8.2 時計のずれが、通信基盤そのものを壊していた

Raspberry Pi には時計用の電池が無く、時刻同期も設定されていなかった。
**起動のたびに時刻が数日前に戻る**状態だった。

このとき、**通信基盤（DDS）のノード探索が一切成立しなかった。**
パケットは双方向に流れているのに、相手のノードが見えない。
時刻を合わせた直後に、探索が成立するようになった。

**症状（ノードが見つからない）から原因（時計）に辿り着くのが極めて難しい。**
PC 側に時刻サーバを立て、Raspberry Pi 側は**時刻同期の完了を待ってから**
センサを起動する順序に変更した。電源断からの再起動で自動的に正常化することを確認済み。

### 8.3 測域センサの読み取りが CPU の 8 割を食っている

測域センサのドライバが、**Raspberry Pi の 1 コアの 81.3 %** を消費していた。
内訳は利用者側 14.2 % に対し **システム側 67.2 %** ——つまり処理ではなく**システム呼び出し**である。

計測すると **毎秒約 12,000 回**のシステム呼び出しで、わずか 25.6 KB/s を読んでいた
（1 回あたり約 11 バイト）。**センサ製造元が提供する開発キットの実装に起因する**もので、
設定では変えられない。

**現時点で実害は確認していないが、4 コアのうち 1 コアが既に埋まっている。**
Raspberry Pi は今回の変更で**親機の役目も兼ねる**ようになったため、
今後この機体に処理を追加する際は、まずここを疑うべき箇所として記録した。

## 9. タイムアウトと最高速度への影響

§1 の式に、実測した受信ギャップの尾を入れる。

```
タイムアウトの下限 = 受信ギャップの尾 ＋ 余裕
タイムアウトの上限 = 許容侵入距離 ÷ 最高速度
```

**最高速度 1.12 m/s**（駆動系の上限 1.4 m/s に安全率 0.8 を掛けた値）を前提とすると:

| 受信ギャップの尾 | タイムアウトに解を持たせるために必要な**許容侵入距離** | 判定 |
| --- | --- | --- |
| 1920 ms（変更前） | **2.2 m 以上** | **非現実的。**最高速度を大幅に下げるしかない |
| **300 ms（変更後）** | **0.4 m 程度** | **現実的** |

**この構成変更は、最高速度 1.12 m/s を維持できるかどうかを分けた。**

なお **許容侵入距離そのものの決定は未了**であり、人の判断を要する（§11）。
本節が示しているのは「どちらの構成なら解が存在するか」までである。

## 10. この改善が直すもの・直さないもの

2026-08-17 の第 1 回追従走行試験（3 階 1 周・約 170 m・10 分 50 秒）では、
次の事象が記録されている。

| 事象 | 回数 |
| --- | --- |
| 緊急停止（すべて壁への衝突） | 5 |
| 対象見失いによる再選択 | 12 |
| 追従対象の乗り移り | 1 |
| **マイコンとの接続断** | **1** |
| 手動操作による復帰 | 5 |

加えて、**直線区間でも機体が左右に約 1 m 振れて**走行していた。

| 事象 | 本改善との関係 |
| --- | --- |
| **接続断** | **直接効く。**これが本検証の対象そのもの |
| **蛇行** | **一部効く。**人物位置の古さが 0.35〜0.62 m → 0.20〜0.36 m に減った（§8.1）。ただし追従アルゴリズム側の要因は手つかず |
| 見失い・乗り移り | **ほぼ効かない。**人物追跡の同定性能の問題であり、通信とは別 |
| 壁への衝突 | **効かない。**障害物回避の設計の問題 |

**したがって本改善だけで追従走行が実用に達するとは考えていない。**

**追従走行の再評価は、実装計画の段階 4（新しい追従走行の実装）の完了後に行う。**
現行の追従走行を再測定しても、置き換えが決まっている実装の数値を得るだけになるため、
**本検証はここで区切る。**

## 12. 教訓

**技術的な結論より、こちらが本書の主要な成果である。**

| # | 教訓 | 何が起きたか |
| --- | --- | --- |
| 1 | **平均や分位点で語ると実態を見誤る** | 30 秒窓の分位点では「測域データは無傷」と見えたが、生の到着時刻では 622 ms 跳ねていた。**外れ値を消す統計で外れ値を探していた** |
| 2 | **実運用と同じ負荷を掛けずに測った値は使えない** | 無負荷の ping が完璧だったことから「電波は無罪」と結論し、比較を打ち切りかけた。跳ねは負荷時にしか起きない |
| 3 | **比較実験では、比較対象以外が本当に揃っているか実装まで遡って確認する** | 無線チャンネルが揃っておらず、「5 倍悪化」という逆の結論が出た。揃えたら 55 回 → 0 回 |
| 4 | **層を分けて同時に観測すると、原因の所在が一意に決まる** | ping を並走させたことで「アプリでも TCP でもなく無線」と確定した。**1 系統だけ見ていた間は仮説の域を出なかった** |
| 5 | **「設定した」ことと「効いている」ことは別** | 省電力の設定変更は、再接続するまで反映されなかった |
| 6 | **相関から機序を決めつけない** | 「一方が良くなると他方が悪くなる」パターンから帯域の奪い合いと判断したが、中継の経路でも同じパターンが出る |
| 7 | **否定的な結果にも価値がある** | 割り込みの仮説（§3）が正しいと思い込んで実装を書き換えていれば、大規模なファームウェア改修に工数を使ったうえ、本当の原因が残ったままになっていた |
| 8 | **症状と原因が別の層にあることがある** | 「ノードが見つからない」の原因が時計だった（§8.2）。**この経路は推測では辿れない** |

**本検証で覆った 3 つの結論のうち 2 つは、筆者自身が一度「確定」として文書に書いたものである。**
測定手法を作り直すたびに、前段の結論が覆った。**測り方が結論を決めていた。**
