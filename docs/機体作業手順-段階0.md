### 2.1 2026-08-21 の判断


| 項目    | 決定                               | 根拠                                                                                                                                              |
| --------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **C-1** | **完了。問題なし**                 | テスタで駆動電源の遮断を確認。`WP-ESP32-01` の完了条件 ⑥ に相当。**`O-5` の関門は実質開いた**（残るは電源断での ⑤ だけ）                        |
| **C-2** | **残す。ただし「急制動」ではない** | 「いきなり速度 0 にすると倒れる」という懸念があったが、**ファームには既に加速度ランプが入っている**（下記）。急制動は実機のどの経路にも存在しない |
| **C-3** | **段階 3 の後へ**                  | この測定は「**手動走行のみ**」と定められているのに、その手動走行は段階 3 で作り直す。現行実装で測っても捨てる値になる                             |
| **D**   | **完了（測れないことが結論）**     | 形状・重量により**手押しは数 m が限度**。片道 200 m の搬送が成立しない。記録: [`data/meas03/baseline.md`](plan/detailed/data/meas03/baseline.md)  |

**★ C-2 で急制動は起きない。**`esp32/src/config.h:69` の `TARGET_RAMP_ACCEL_MPS2 = 1.5f` を
`main.cpp:168-170` の `rampToward()` が毎周期かけているため、**`/cmd_vel` をゼロにしても
目標速度は 1.5 m/s² でしか動かない。**`v_max = 1.12 m/s` からの停止は **0.75 秒・約 0.42 m**、
減速度は **0.15 G**。「意図的に制動距離を作る」という方針は**既に実装されている**ので、
C-2 はその実効値（スリップ・PID 追従誤差込み）を確かめる作業になる。

**★ 非常停止は逆にランプを通らない。**`main.cpp:156-164`（`estopActive || watchdogTripped`）と
`onWsDisconnect()` は `Motor::stopAll()` で PWM を 0 にするだけで、`motor.cpp` は DIR ＋ PWM 駆動
なので**能動制動がかからず空走する**。物理ボタンによる駆動電源の遮断も同じ。
**急ではないがランプ停止より長い可能性が高く、しかもこれが安全チェーンの実際の経路である。**
`brake_accel_mps2` はこれを表していない（[`DetailedDesign-open.md`](plan/detailed/DetailedDesign-open.md) `N-12`）。

**★ D が「無い」ことの意味。**手押しは [`Spec-safety.md`](plan/spec/Spec-safety.md) §6.3 で
「実装ゼロで成立する正式なフォールバック」とされていたが、**長距離では成立しない。**
通信断・AP 障害が移動の途中で起きたときのフォールバックは**存在しない**（`F-42`）。
併せて目標 G4 の判定基準が比較対象を失った（`F-43`）。

**B は A より後でなくてもよい**（電源断で完結するため）が、**A-3 でファームを焼くついでに B の設定も入れられる**ので、この順が早い。
**AP の比較は一度打ち切ったが、再開して決着した（§4.0）。**「電波は無罪」が誤りで、
ESP32 の無線が負荷時に丸ごと停止していた。**ラズパイ AP（ch1）を採用済み**（`scripts/rpi_setup_ap.sh`）。

### A-4 書き込みと電源断での確認

## 4. 手順 B — 遅延とリンク品質の測定（**2026-08-20 縮小改訂**）

### 4.0 何が分かったか（縮小の理由）

当初は「AP 3 案を比べて最良を選ぶ」計画だった。**その前提は 2 段階で崩れた。**

**第 1 段階（2026-08-19）— 省電力が支配要因だった**


| 発見                                     | 内容                                                                                                                              |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Wi-Fi の省電力**                       | ESP32 とラズパイの**両方**で有効だった。両方切ると LiDAR の途絶が**完全に消えた**（p99 298.6 → 103.9 ms、max 399.9 → 104.2 ms） |
| **AP 3 案の比較データは使えない**        | 8 条件すべてラズパイ側の省電力が有効なまま測っており、AP の差ではなく省電力の差を見ていた                                         |
| **設定は再アソシエーションまで効かない** | `iwconfig wlan0 power off` は稼働中の接続に反映されない。**再起動後に初めて効いた**                                               |
| **エンコーダ割り込みは無関係**           | 0.5 m/s（毎秒 3.2 万回の割り込み）でも p99 は変わらなかった（139.5 vs 140.6 ms）                                                  |

**第 2 段階（2026-08-19〜20）— そもそもネットワークが主因ではなかった**


| 発見                                 | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **悪いのは ESP32 経路だけ**          | 同じ電波・同じ受信機・同じ 10 分で、**LiDAR は max 104.2 ms（取りこぼしゼロ）**、ESP32 は max 603.4 ms で跳ね 3 回。**片方だけが悪いなら原因は電波ではない**                                                                                                                                                                                                                                                                                                                             |
| **電波は無罪（実測）**               | 2026-08-20、ESP32 AP へ ICMP を 5 Hz ×**600 秒（3000 発）**＝ `esp32ap_bothns_10min.csv` と同じ 10 分。**損失 0 %、max RTT 33.2 ms、p99 11.7 ms、100 ms 超は 0 件 / 3000、最大到着ギャップ 230.7 ms（送信間隔 200 ms なのでジッタ +30.7 ms）**。**603 ms の跳ねは無線区間では起きていない。**記録: [`meas04/ping_icmp_600s.md`](plan/detailed/data/meas04/ping_icmp_600s.md)。※ ICMP は ESP32 の LwIP が返すため、**アプリ側ループの停止は ping には出ない**（だから 4.3 の 2 が要る） |
| **5 分の強制再接続では説明できない** | `ws_link.cpp:32` の `FORCE_RECONNECT_MS = 300000` は実在するが、跳ねは t≒34s / 107s / 287s（間隔 73・180 秒）で **300 秒周期ではない**。以前の仮説は取り下げる                                                                                                                                                                                                                                                                                                                          |
| **10 Hz が下限を決めている**         | `CTRL_PERIOD_MS = 100`。実測 p50 はちょうど 100.0 ms。**電波を良くしても間隔は 100 ms を切らない**                                                                                                                                                                                                                                                                                                                                                                                       |
| **指標が「30 秒窓の分位点」だった**  | `/safety/link_quality` は窓 30 秒の p50/p99/max。CSV の p99 列は**分位点の分位点**で、603 ms の外れ値ではほとんど動かない。**誤フォルトを起こすのはその外れ値の方**                                                                                                                                                                                                                                                                                                                      |

**第 3 段階（2026-08-20）— 測っていたのは遅延ではなかった**


| 発見                               | 内容                                                                                                                                                                                         |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **到着間隔 ≠ 遅延**               | **全パケットが一律 1 秒遅れて届いても、到着間隔は 100 ms のまま。**間隔測定は一定遅延に対して**構造的に盲目**である。遅延は一度も測っていない                                                |
| **知覚が 5 倍遅い**                | `docs/architecture.md` の該当節のとおり **DR-SPAAM は CPU 推論で約 2 Hz（1 フレーム約 0.5 秒）**。試験員の位置は 500 ms に 1 回しか更新されない。100 ms の Wi-Fi はこの中に埋もれる          |
| **蛇行はネットワークでは直らない** | [第1回追従走行試験](第1回追従走行試験.md) の 19 件（復帰 5 回は結果なので除く）は、緊急停止（壁衝突）5・見失い 12・乗り移り 1・**ESP32 ロスト 1**。**ネットワークで説明がつくのは 1 件だけ** |
| **1 秒の体感遅れは説明がつく**     | LiDAR 1 回転 〜100 ms ＋**DR-SPAAM 〜500 ms** ＋ KF/planner 〜100 ms ＋ ブリッジ〜ESP32〜モータ立ち上がり 〜200 ms ＝ **約 0.9 秒**。Wi-Fi に異常が無くても出る                              |

**第 4 段階（2026-08-20 午後）— 実測で第 2 段階の結論が覆った**


| 発見                                             | 内容                                                                                                                                                           |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **跳ねの瞬間、4 系統すべてが同時に途切れる**     | ESP32 データ（TCP）／LiDAR`/scan`（DDS・ラズパイ発）／**ping 192.168.4.1**／**ping 192.168.4.2** が同時刻に 520〜640 ms 停止。20 分で 10 回、計 6.06 秒        |
| **ping まで途切れる＝アプリ層でも TCP でもない** | ICMP は ESP32 の LwIP が返す。それが止まる以上、**ESP32 の無線そのものが落ちている**                                                                           |
| **ESP32 は AP でもある**                         | ラズパイの`/scan` も ESP32 の中継を通る。だから ESP32 が止まると LiDAR も同時に止まる                                                                          |
| **負荷依存**                                     | 無負荷（ping のみ 600 秒）は**400ms 超 0 回**。負荷あり（10Hz feedback ＋ 20Hz `/cmd_vel` ＋ LiDAR 中継）で 10 回。**電波環境ではなく ESP32 の処理能力が律速** |
| **TCP は原因ではなく増幅器**                     | 再送が出た 3 回だけ ROS 側のギャップが電線上の 1.5〜1.7 倍に膨らむ。600 ms の無線停止が**1.3〜1.9 秒のアプリ層断**になる                                       |
| **「LiDAR は無傷」は誤りだった**                 | 30 秒窓の分位点 CSV を見ていたため外れ値が隠れていた。生の到着時刻では LiDAR も max 622 ms                                                                     |

記録: [`meas05/README.md`](plan/detailed/data/meas05/README.md)

**結論**: 遅延の実測へ切り替えた判断は正しかった（`scan_mode` で遅延が半減した）。
一方、**「AP を替えても直らない」は誤りだった。**ESP32 に「モータ制御」と
「LiDAR データの中継」を兼務させている構成そのものが跳ねを生んでいる。
**AP を ESP32 から降ろす検討を復活させる**（電波品質の比較としてではなく、
ESP32 から中継負荷を降ろす目的で）。再起動ばらつき・位置依存・モータノイズは打ち切ったまま。

### 4.1 必須の設定（**測定の前に必ず確認する**）

### 4.4 遅延の読み方（蛇行との関係）

追従ループの実際の段数はこうなっている。**律速は Wi-Fi ではない。**


| 段                  | 周期             | 出どころ                                                                                       |
| --------------------- | ------------------ | ------------------------------------------------------------------------------------------------ |
| LiDAR`/scan`        | 100 ms           |                                                                                                |
| **DR-SPAAM 推論**   | **154 ms**       | **← 律速**。実測 6.481 Hz（`scan_mode: Standard`）。切替前の DenseBoost は 272 ms（3.673 Hz） |

| Wi-Fi 到着間隔      | 100 ms (p50)     | `esp32ap_bothns_10min.csv`                                                                     |
| ESP32 制御          | 100 ms           | `config.h` の `CTRL_PERIOD_MS`                                                                 |

舵を切り続ける。これは制御ループとして発振する形で、**第 1 回試験の振れ幅「約 1 m」と
向きが合う。**ただし `scan_mode` の切替で半減させてもなお残る量であり、
**蛇行の主因が遅延だけだとは言えない。**

| 案                                 | 内容                                                                    | 懸念                                                                                |
| ------------------------------------ | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **推論を速くする**                 | GPU 化・入力点数削減（`scan_mode:=Standard` は適用済み）・モデル軽量化  | 現状 CPU 推論。ハード追加が要るかもしれない                                         |
| **2 Hz 前提で planner を作り直す** | 検出間の外挿（KF の速度推定を使う）・`k_ang` を下げる・`v_max` を落とす | `KalmanFilter` の `dt` 不具合は 2026-08-06 に修正済みで、速度推定は使える状態にある |

### 4.5 タイムアウトと `v_max` の判定

判定は `registry.yaml` の実際の導出に従う。**`v_max` はリンク品質からは出てこない**
（`v_max = drivetrain_ceiling_mps × v_max_headroom_ratio` = 1.4 × 0.8 = **1.12 m/s**、駆動系由来）。
リンク品質が効くのは、**タイムアウトに解があるか**という形でである。

```
下限 ≤ timeout ≤ 上限
  下限 = 受信間隔の尾 ＋ 余裕        ← 誤フォルトを出さない（①）
  上限 = intrusion_budget_m ÷ v_max  ← タイムアウトまでに走ってよい距離（②）
```

**解が無ければ `v_max` を下げる**（`P-5` により 1 回だけ引き下げ）。手順:

1. **`intrusion_budget_m` を決める**（未決・`N-2`。方針値なので人が決める。これが無いと上限が出ない）
2. 上限 = `intrusion_budget_m ÷ 1.12` を計算する
3. 下限（実測の尾＋余裕）と比べ、**区間が空でなければ現行構成でよい**
4. 空なら、まず**尾を潰す**（4.3 の 2）。それでも空なら `v_max` を下げる

**実測した尾と、`v_max = 1.12 m/s` を保つために必要な `intrusion_budget_m`**


| 尾（実測・20 分）                       | 必要な`intrusion_budget_m` | 判定                                         |
| ----------------------------------------- | ---------------------------- | ---------------------------------------------- |
| **1920 ms**（ESP32 が AP・旧構成）      | **2.2 m 以上**             | **非現実的。**`v_max` を大幅に下げるしかない |
| **300 ms**（ラズパイ AP ch1・**現行**） | **0.4 m 程度**             | **現実的**                                   |

つまり **AP を ESP32 から降ろせるかどうかが、`v_max` を保てるかを分けた。**
※ `intrusion_budget_m` は**未決**（4.7 の 1）。上表は「どちらの構成なら解が存在するか」まで。

## 9.4 手順 4 — 制動と空走の測定（`WP-MEAS-01` ＋ `N-12`）**通電**

> **安全**: 人が張り付く。**周囲 3 m に人と物を置かない。**手順 1 が終わっていること
> （物理非常停止が効かない機体で制動を測ってはいけない。`O-5`）。

**測るのは 2 種類で、別物である。**


| 種別           | 起こし方                     | 何になるか                                        |
| ---------------- | ------------------------------ | --------------------------------------------------- |
| **ランプ停止** | `/cmd_vel` を 0 にする       | `brake_accel_mps2`（ESP32 が 1.5 m/s² でランプ） |
| **空走**       | **走行中に物理ボタンを押す** | `N-12`（駆動電源が切れ、PWM 0 ＝ 能動制動なし）   |

**空走はソフトからは起こせない。**`/safety/estop` も twist_mux のタイムアウトも
`/cmd_vel = 0` を出すだけで、ESP32 はランプする。だから人が押す。

```bash
# 端末 A（記録）— 走らせる前に起動しておく
python3 scripts/meas07_brake_recorder.py /root/th_data/brake_$(date +%H%M%S).csv

# 端末 B（走行）。床に開始位置の印を付け、停止後にタイヤの位置を巻尺で測る
python3 scripts/meas07_drive.py --mode ramp  --speed 0.3 --hold 4 --i-am-supervising
python3 scripts/meas07_drive.py --mode coast --speed 0.3 --hold 6 --i-am-supervising
```

**取る本数**（`wp0` §9。3 条件 × 5 回）:


| 条件     | 速度        | 備考                                    |
| ---------- | ------------- | ----------------------------------------- |
| 低速     | 0.3 m/s     | 既定値。まずここで挙動を確かめる        |
| 中速     | 0.6 m/s     |                                         |
| 場内相当 | **1.0 m/s** | **第 1 回試験と同じ速度域。最後に行う** |

**空走は各速度 3 回で足りる**（押すたびに再投入が要るため）。

```bash
# 解析（巻尺の実測値を第 2 引数に。距離の正は巻尺）
python3 scripts/meas07_analyze.py /root/th_data/brake_XXXXXX.csv 0.42
```

**採るのは最も悪い値。**平均を採ってはいけない（`wp0` §6.3 FMEA①。制動距離を
短く見積もると、以降の全距離が危険側にずれる）。

`docs/plan/detailed/data/meas07/README.md`（空走の分を含む）。
