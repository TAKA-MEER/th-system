# 始業点検・校正・故障診断の実装

[DetailedDesign.md](DetailedDesign.md) の詳細。**「気づく」ための始業点検と、「直す」ための校正。**

```
始業点検（気づく） ──ズレを検知──> 校正（直す） ──> 始業点検（直ったか見る）
        ▲                                                              │
        └──────────────────────────────────────────────────────────────┘
```

**現状はどちらも独立した CLI スクリプト**（`th_calibration/` の 4 本）で、
手順書はコードのコメントにしかなく、実測値はターミナルへの手入力、
適用は補正値をコピーして別コマンドを叩く形になっている。
**これを一つの体験にまとめる**のがこのファイルの目的。

---


**`th_calibration/` の 4 本は廃止する。**計算部分だけを `calib_core.py` へ純粋関数として抜き出す
（[DetailedDesign-reuse.md](DetailedDesign-reuse.md)）。

## 1. 共通の安全規則

| 規則 | 始業点検 | 校正 |
| --- | --- | --- |
| **開始できるモード** | `IDLE` / `MANUAL` のみ | **同じ制限を課す**（`Z-1` / `F-15`） |
| 非常停止・フォルト | 即座に反映され停止 | 同左 |
| 機体が動く項目 | **モーター・エンコーダ確認のみ** | **直進・旋回の 2 つ**（自律で動く） |
| 動かし方 | **押している間だけ動き、離せば止まる** | **自律で動く。**常に見える位置に中断ボタン |
| 中断後 | いつでもやり直せる | **補正値を確定せずに終われる** |
| 非常停止・フォルトで止まった後 | やり直す | **やり直す。途中再開はしない**（`K-r5` / `T-CAL-08`） |

**校正のほうが危険である。**始業点検は人がボタンを押している間だけ動くが、校正は自律で走る・回る。
原典は始業点検にだけモード制限を書いていたが、**書き漏れとみなして校正にも課す。**

モード制限は `mode_entry.yaml` で表現する（`IDLE` / `MANUAL` からのみ `OPCHECK` / `CALIB` へ）。
**ノード側でも `/system/state` を見て二重に確認する**（現行 `config_manager` の流儀。UI の見た目だけに頼らない）。

### 1.1 ジョグ介入は不可

`OPCHECK` / `CALIB` は `C-01` の除外（[DetailedDesign-state.md](DetailedDesign-state.md) §4.1）。
**手順そのものが動きを規定している**ので、途中で手動が割り込むと測定が壊れる。

### 1.2 速度

`v_check`（始業点検）／ `v_calib`（校正）。ゾーンは `NA` なので `v_max` は適用されない。
**これが `DetailedDesign-names.md` §4 でゾーンを 3 値にした理由である。**
真偽値のままだと `NA` が場外に潰れ、点検・校正に `v_max` が乗る。

## 2. 始業点検（`OPCHECK`）

### 2.1 4 項目

| # | `item` | 何を確認するか | 機体が動くか | NG の行き先 |
| --- | --- | --- | --- | --- |
| 1 | `ESTOP` | 物理非常停止ボタンの状態をシステムが把握しているか | 動かない | **故障診断** |
| 2 | `MOTOR` | 低速で指令どおり動くこと、エンコーダが回転を検出できること | **動く** | **故障診断** |
| 3 | `IMU` | データが届くこと、校正状態 | 動かない | **IMU 校正** |
| 4 | `LIDAR` | スキャンが正しい範囲・周期で届くこと、死角マスクが実機と合っていること | 動かない | **LiDAR 死角マスク校正** |

**選んだ瞬間にモニターが立ち上がる**（`T-OPC-01` の `effect: start_monitor`）。
別ツールの起動やトピック名の暗記を要らなくする。

### 2.2 項目 1: 物理非常停止ボタン

**`DEBT-1`（`ESTOP_BENCH_TEST_BYPASS`）の解除を証明する項目でもある**
（[DetailedDesign-safety.md](DetailedDesign-safety.md) §11.1）。

| 順 | 画面の案内 | 判定 |
| --- | --- | --- |
| 1 | 「非常停止ボタンを**押してください**」 | 押下を検出したら自動で OK |
| 2 | 「押されていることが画面に出ています。実物と一致していますか」 | 人が目視で答える（`/opcheck/answer`） |
| 3 | 「ボタンを**解除してください**」 | 解除を検出したら自動で OK |
| 4 | 「解除されたことが画面に出ています。一致していますか」 | 人が目視で答える |

**押す・離すの両方を試す。**片方だけでは配線の断線・短絡を区別できない。

**この項目の実行中だけ、物理ボタン押下で `CARRY` に遷移させない**（`T-OPC-05`）。
押下のたびに手押しモードへ落ちると確認そのものが実行できない。この間も駆動は物理的に切れている。

**バイパスが有効だと構造的に通らない**（押下が `estopActive = false` に潰されるため 1 で止まる）。
よって「**項目 1 が OK ＝バイパス無効の証明**」として使える。

### 2.3 項目 2: モーター・エンコーダ

| 順 | 内容 |
| --- | --- |
| 1 | **前進・後退・右超信地旋回・左超信地旋回**の 4 方向ボタン。**押している間だけ `v_check` で動く** |
| 2 | 目視で動くことを確認しつつ、画面で**指令と実測の追従をリアルタイムに見る** |
| 3 | 離すと自動停止 |
| 4 | **符号・追従**が合っているかを自動で OK/NG |

左右輪それぞれ「指令 −0.10 m/s ／ 実測 −0.09 m/s ／ ✓」の形で並べる。
データ源は `/esp32/wheel_cmd_speed`（指令）と `/esp32/wheel_feedback`（実測）。
**既存の `WheelSpeedView.jsx` の時系列グラフをそのまま流用できる。**

`check_core.py`:

```python
def judge_motor(cmd_l, meas_l, cmd_r, meas_r, p) -> CheckVerdict:
    """符号の一致と追従率。Spec-checks.md §2.4-2"""
    for c, m, side in ((cmd_l, meas_l, "L"), (cmd_r, meas_r, "R")):
        if abs(c) < p.motor_deadband_mps:
            continue
        if c * m <= 0:
            return NG(f"sign_mismatch_{side}")          # 左右入れ替え／極性逆
        if abs(m) < abs(c) * p.motor_follow_min_ratio:
            return NG(f"no_follow_{side}")              # 片輪だけ追従しない
    return OK()
```

**速度指令の出し方**: `/cmd_vel_behavior` へ publish する（priority 20・`obstacle_limiter` を通る）。
> **`/cmd_vel_manual` を使ってはいけない。**現行 `linear_calib.py` はそちらを使っているが、
> 新設計では `/cmd_vel_manual` は **`jog_gate` の出力**であり、
> `jog_gate` は `OPCHECK` / `CALIB` 中は**通さない**（[safety](DetailedDesign-safety.md) §3.4.1）。
> 同じトピックに 2 つの publisher が乗り、モーター確認が構造的に動かない。
>
> **`calib_runner` の自律走行（`LINEAR` / `ROTATION`）も同じく `/cmd_vel_behavior`。**
> priority 20 でも非常停止とフォルトロックは確実に効く（ロックは 254/255）。

### 2.4 項目 3: IMU

| 順 | 内容 |
| --- | --- |
| 1 | 開くと IMU データの生死とジャイロ値がすぐ表示される |
| 2 | **静止状態でバイアスが小さいことを自動確認** |
| 3 | 校正状態（sys / gyro / accel / mag）をリアルタイム表示 |
| 4 | 未校正・劣化していれば **IMU 校正へ誘導** |

**「校正済みで今は正常」なのか「劣化していて校正が必要」なのかを画面が判断し、
後者のときだけ人に校正を促す。**毎回同じ案内をなぞらせない。

```python
def judge_imu(calib_status: int, gyro_bias_rad_s: float, alive: bool, p) -> CheckVerdict:
    sys_, gyro, accel, mag = unpack_calib(calib_status)   # 2 bit ずつ
    if not alive: return NG("no_data")
    if abs(gyro_bias_rad_s) > p.imu_bias_max_rad_s: return NG("bias_too_large")
    if min(sys_, gyro, accel, mag) < 3: return WARN("needs_calibration")
    return OK()
```

> **要注意**: `/esp32/imu_data` の `angular_velocity` は **rad/s** でなければならない。
> ファームが 2026-08-06 の dps→rad/s 修正前だと **57.3 倍**になる。
> `esp32_bridge` の `|wz| > 10 rad/s` 警告はこの検出のためにある。**始業点検でも同じ判定を入れる。**

### 2.5 項目 4: LiDAR

| 順 | 内容 |
| --- | --- |
| 1 | 生のスキャンをその場にライブ表示 |
| 2 | 死活・受信周期・全周の有効性を自動確認 |
| 3 | **死角マスクを重ねて表示**し、実機のアルミパイプの位置とズレていないか目視 |
| 4 | ズレを自動検知したら **LiDAR 死角校正へ直接誘導** |
| 5 | 既知距離の障害物との比較も、**カーソルを合わせるだけで数値が読み取れる** |

**ズレの自動検知**: 静止状態で `/scan` を平均し、**恒常的に近距離を返す角度帯**を推定して
`blind_angle_ranges` と比べる。差が `calib_blind_tolerance_deg` を超えたら NG。

**`DEBT-2`（幅ゼロのマスク）はここで必ず NG になる。**
推定された角度帯（4 か所・幅あり）と設定（幅ゼロ）が食い違うため。

### 2.6 故障診断（S-31・`C-r6` / `Z-2` / `F-16`）

**非常停止ボタンとモーター・エンコーダの NG は校正では直らない。**
IMU と LiDAR には校正への導線があるが、この 2 つには受け皿が無かった。

| NG の内容 | 出すチェック手順 |
| --- | --- |
| 非常停止ボタンの状態が届かない | GPIO 配線・プルアップ・ボタン自体の導通 |
| 押しても状態が変わらない | 同上。**＋ `ESTOP_BENCH_TEST_BYPASS` が有効でないか**（`DEBT-1`） |
| 指令を出しても実測が 0 | モーター配線・ドライバ・電源 |
| 指令と実測の**符号が逆** | 左右の入れ替わり、エンコーダ極性 |
| 片輪だけ追従しない | その側の配線・エンコーダ |

**この画面は診断結果を示すだけで、修理そのものは人が行う。**
チェック手順は `th_maintenance/config/repair_hints.yaml` に持つ（コードに埋めない）。

### 2.7 いつやるか（`C-r5`）

| タイミング | 範囲 |
| --- | --- |
| 導入時 | **4 項目すべてを人が実施** |
| 毎回の起動時 | **自動で判定できる項目だけ自動実行**（データ受信・値の範囲・死角マスクのズレ・物理ボタンの状態） |
| 走行を伴う確認 | **自動実行しない。**人が始業点検画面から明示的に始める |

自動実行の結果は S-00（接続確認）に総合ステータスとして出す。
**NG でも運用には入れる（警告のみ）。**必須通信系統の不通だけは別扱い（`C-r4`）。

## 3. 校正（`CALIB`）

### 3.1 4 項目

| # | `item` | 何を補正するか | 適用 |
| --- | --- | --- | --- |
| 1 | `LINEAR` | 車輪半径（走行距離の誤差） | **§4（`O-d10` の解決）** |
| 2 | `ROTATION` | 実効車輪間距離（旋回角度の誤差） | 即時反映・永続化 |
| 3 | `IMU` | センサ内部オフセット | §5 |
| 4 | `BLIND` | LiDAR 死角マスクの角度範囲 | 即時反映・永続化 |

### 3.2 ウィザードの骨格

```
Step 1 案内 ──> Step 2 実行・実測 ──> Step 3 確認（プレビュー）──> Step 4 検証
   │                 │                      │                        │
   └─────────────────┴──────────────────────┴────────────────────────┘
                    どのステップからでも [ 中断 ]（補正値を確定せず終了）
```

**この骨格が完全に当てはまるのは `LINEAR` と `ROTATION` だけ**（`K-r4`）。

| 項目 | 骨格との差 | UI |
| --- | --- | --- |
| `LINEAR` / `ROTATION` | 完全に当てはまる | 4 ステップのウィザード |
| `IMU` | **実測値の入力もプレビューも無い。**センサ自身が校正する | **進捗バーのみ** |
| `BLIND` | 実測値の入力の代わりに**画面上でなぞって範囲を指定** | ライブスキャン上のドラッグ選択 |

### 3.3 項目ごとの流れ

| # | 流れ |
| --- | --- |
| **`LINEAR`** | 指定距離を `v_calib` で自律走行 → 実際に進んだ距離を画面へ入力 → 補正後の値をプレビュー → 適用 → **検証走行で再確認** |
| **`ROTATION`** | 指定角度を自律旋回 → 実際の回転角を（分度器で測って）入力 → プレビュー → 適用 → **検証旋回で再確認** |
| **`IMU`** | 案内に従って機体を**8 の字**に動かす → sys/gyro/accel/mag を見ながら全て「完全」になるまで続ける → **自動で完了** |
| **`BLIND`** | 生スキャンをライブ表示 → 死角として写り込んでいる角度帯を**なぞって選択** → プレビューで正しくかかることを確認 → 適用 |

### 3.4 計算（`calib_core.py`・純粋関数）

```python
def corrected_wheel_radius(nominal_r: float, commanded_m: float, measured_m: float) -> float:
    """走った距離が短ければ半径が過大に見積もられている。"""
    return nominal_r * (measured_m / commanded_m)

def corrected_wheel_base(current_base: float, commanded_deg: float, measured_deg: float) -> float:
    """回りすぎたら車輪間距離が過小。"""
    return current_base * (measured_deg / commanded_deg)

def sanity(value: float, lo: float, hi: float) -> bool:
    """ゼロ割れ・桁違いを弾く。Step 3 のプレビュー前に必ず通す。"""
    return math.isfinite(value) and lo <= value <= hi
```

**`sanity()` を通らない値は Step 3 へ進めない**（`T-CAL-04` のガード `preview_sane`）。

**順序**: `wheel_radius` と `wheel_base` は互いに影響するので、**必ず直進 → 旋回の順**で行う。
UI は `ROTATION` の行に「先に直進校正を実施してください」を出し、
直進の校正日時が旋回より古ければ警告する。

### 3.5 検証と許容範囲（`F-13` / `K-r1` / `K-r2`）

```
Step 4 の検証で測った誤差 ≦ 許容範囲  → 完了・永続化
Step 4 の検証で測った誤差 >  許容範囲  → 適用前に戻し、やり直しを促す（T-CAL-06）
```

| 項目 | 許容範囲 | 分類 |
| --- | --- | --- |
| `LINEAR` | `calib_linear_tolerance_ratio`（指定距離に対する相対誤差） | **(c) 未確定** |
| `ROTATION` | `calib_rotation_tolerance_deg`（絶対誤差） | **(c) 未確定** |
| `IMU` | sys/gyro/accel/mag が全て 3 | 定義済み |
| `BLIND` | `calib_blind_tolerance_deg` | **(c) 未確定** |

**許容範囲は目標 G2（カメラ昇降が要求する許容差）から逆算できる**ので、
`O-a1` が決まると連鎖して決まる。それまでは `status: placeholder`。

#### 要再校正の判定

| 条件 | 内容 |
| --- | --- |
| **経過** | 前回校正から `calib_interval_days` を超えた |
| **悪化** | 始業点検で測った誤差が、前回の検証時より一定以上悪化した（「ドリフト増加を検知」） |

### 3.6 履歴とロールバック（`K-r3` / `F-14`）

```
/root/th_data/calib/
├── current.yaml        いま適用されている補正値
└── history/
    ├── 001.yaml        新しい順に 3 世代
    ├── 002.yaml
    └── 003.yaml
```

| 項目 | 内容 |
| --- | --- |
| 世代 | **3 世代**（原典の要求は「1 つ前に戻せる」だが余裕を持たせる） |

## 4. 直進校正のギャップ（`O-d10` の解決）

### 4.1 問題

**車輪半径は ESP32 ファームウェアのコンパイル時定数**（`config.h` の `WHEEL_RADIUS_M`）であり、
適用に**書き換えと再書き込み**が要る。他の 3 項目と同様に即時反映・再起動不要であるべきで、
`Spec-checks.md` §3.6 が「是正すべきギャップ」と宣言している。**方法は詳細設計で決める、とされていた。**

### 4.2 決定: **PC 側のスケール係数で解決する。ファームは触らない**

ESP32 は速度をこう計算している。

```
distPerCount = 2πR_fw / CPR
velL = counts × distPerCount / dt        ← R_fw はファームの公称値
```

真の半径を `R_true` とすると、ESP32 が報告する速度は `v_report = v_true × (R_fw / R_true)`。
PID は自分の報告値が指令に一致するよう駆動するので、`v_true = v_cmd × (R_true / R_fw)`。

**`k = R_true / R_fw` を `esp32_bridge` の両方向にかければ閉じる。**

| 方向 | 変換 |
| --- | --- |
| 指令（PC → ESP32） | `v_send = v_desired / k` |
| 実測（ESP32 → PC） | `v_actual = v_report × k` |

| 項目 | 内容 |
| --- | --- |
| パラメータ名 | **`wheel_radius_scale`**（`= k`）。`esp32_bridge` のランタイムパラメータ |
| 保存先 | `/root/th_data/calib/current.yaml` |
| 適用 | **即時反映・再起動不要・再書き込み不要** |
| `config.h` の `WHEEL_RADIUS_M` | **公称値として固定する。**校正で触らない |
| 検算 | `wheel_radius_m = WHEEL_RADIUS_M × wheel_radius_scale` を `registry.yaml` に `derived` として持ち、表示はこちらを使う |

### 4.3 安全上の制約

`k` が 1 から大きく外れると、PC 側の速度上限（`obstacle_limiter` が `v_desired` に対してかける）と
ESP32 内部の制限（`v_send` に対して効く）がずれる。

| アサーション | 内容 |
| --- | --- |
| **A10** | `\|wheel_radius_scale − 1\| ≤ wheel_radius_scale_max_dev`（既定 0.1）。超えたら**起動を拒否** |
| 意味 | 10% を超えるずれは校正ではなく**機械的な異常**（車輪の摩耗・別部品の混入）。数値で押し切らせない |

超えた場合は S-31（故障診断）へ誘導し、`config.h` の公称値そのものを見直す手順を出す。

### 4.4 なぜ NVS 方式にしないか

ESP32 の不揮発領域（Preferences/NVS）に半径を持たせ、新フレームで書き込む案もある。

| | スケール係数（採用） | NVS 書き込み |
| --- | --- | --- |
| ファーム変更 | **不要** | 必要（プロトコル追加） |
| 再書き込み | **不要** | 初回のみ必要 |
| 真値の所在 | PC（`calib/current.yaml`） | ESP32（機体に紐づく） |

## 5. IMU 校正の永続化

`Spec-checks.md` §3.1 は「完了状態を保存し、次回起動時に自動復元」と定める。
BNO055 のオフセットは**センサ内部のレジスタ**にあるので、PC 側に保存しても復元できない。

**ESP32 のファームで完結させる。**

| 順 | 動作 |
| --- | --- |
| 1 | `Imu::init()` で NVS からオフセットを読み、あれば `setSensorOffsets()` で書き戻す |
| 2 | 校正状態が sys/gyro/accel/mag すべて 3 になったら `getSensorOffsets()` で読み、NVS へ保存 |
| 3 | `IMU_DATA (0x04)` の `calib_status` で PC に伝えるのは現行のまま |

**プロトコル変更は不要。**ファーム内で閉じる。
`calib_runner` は `/esp32/imu_calib_status` を監視して 3/3/3/3 を待つだけ
（現行 `imu_calib_check.py` がやっていることと同じ）。
