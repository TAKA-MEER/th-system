# 推奨構成 — 試験場内の移動

**方針決定（2026-08-11・ユーザー指示）** を受けた推奨構成と実装順。
根拠は [前提の整理](onsite-premises.md)、案の比較は [移動方式の候補と比較](onsite-options.md)、
地図まわりは [地図作成の容易化と盤の指定](onsite-mapping.md)。

---

## 3.1 決まったこと

1. **呼び寄せを改良し、「試験員が立っていた位置」へロボットを移動させる。**
   試験員は指示したあと盤前から退く。→ **試験員の立ち位置が、そのまま盤前の停止位置になる。**
2. **配電盤の位置は毎回変わるので、毎回 SLAM で地図を作る。**
   そのタイミングで盤位置を登録する。
3. **盤の指定は地図タップではなく、登録済みピンの選択で行う**（[§2.5](onsite-mapping.md)）。

**これで前回まで選定をブロックしていた問題が 2 つ同時に解ける。**

* 盤前の**位置**を、地図から読み取るのでも座標を書くのでもなく、**試験員が立つことで与える**
  → `panels.yaml` の絶対座標が不要になり、[地図原点が毎回変わる制約](onsite-premises.md)が消える
* 「どこが盤か地図で分からない」→ ピンの同一性は**そこに立った行為**が与えるので、地図の可読性が要らなくなる

**`panels.yaml` を静的な座標ファイルとして使う方式は、これで完全に終わる。**
（配電盤は毎回変わるため、そもそも書き溜める対象ではなかった。）

## 3.2 構成

```
【地図作成フェーズ】試験場に到着 → WebUI「地図作成開始」
   試験員がロボットを追従で連れ回しながら盤を一巡し、
   各盤の前で「ロボットに立ってほしい位置」に立って【登録】を押す
       → その時点の base_link→map で試験員位置を map 座標へ変換して保持
       → 地図上に番号付きピンが立つ
   一巡したら「地図作成停止」（＝地図を凍結・自己位置推定は継続）

【運用フェーズ】試験員はどこにいてもよい
   (a) ピンを選ぶ  → 登録済み座標へ Nav2
   (b) その場で呼ぶ → 今の試験員位置へ Nav2（登録不要・地図品質にほぼ非依存）
       ↓
   試験員が退いたことを確認してから発進
       ↓
   到着（Nav2 到達許容 ±0.25 m / ±14°）
       ↓
   〔許容差が足りなければ〕LiDAR で盤面に正対して最後を詰める
       ↓
   AT_PANEL → 撮影 → 完了通知 → IDLE
```

**(a) と (b) は同じ幾何で、依存するものだけが違う。** ここを混ぜないこと。

| | (b) その場で呼ぶ | (a) ピンを選ぶ |
| --- | --- | --- |
| 目標 | **今**の試験員位置 | 登録**時**の試験員位置 |
| 必要なもの | 現在の `base_link→map` TF だけ | Nav2 が数分後にそこへ経路を引けること |
| **地図の品質** | **ほぼ依存しない** | **依存する** |
| 試験員 | 盤の前まで歩く必要がある | **歩かなくてよい** |
| 実装 | パラメータ + 小改造（§3.4 の 1・2） | 登録・ピン・FSM 是正が要る（同 4〜8） |

**(b) だけでも運用は成立する**（試験員が盤まで歩いて呼ぶ）。
**(a) の価値は「地図作成で一度歩けば、以後は歩かずに盤を指定できる」ことにある。**
[§1.3 項目 2](onsite-premises.md)（同じ盤に何回戻るか）で価値が決まるのは変わらない。

## 3.3 最大の技術的な穴 — **到着時の「向き」は立ち位置からは決まらない**

`summon_navigator_core.py` の `compute_stop_goal()` は

```python
yaw = math.atan2(person_y, person_x)   # base_link 相対
```

としており、これは**呼んだ瞬間のロボット位置から試験員へ向かう方向**である。
`stop_distance_m` を 0 にすれば**位置**は試験員の立ち位置に一致するが、
**向きはロボットがどこから来たかで決まってしまい、盤の法線とは無関係**である。
脚検知は人の位置しか出さないため、**試験員がどちらを向いていたかは原理的に観測できない。**

盤に対して 90° 横を向いて到着すればカメラは盤を見られない。**位置だけでは足りない。**

### 向きを与える 4 つの方法

| 方式 | 得られる精度 | 追加実装 | 試験員の手数 |
| --- | --- | --- | --- |
| ⓪ 何もしない（接近方向のまま） | **不定**（最悪 90° 以上ずれる） | ゼロ | ゼロ |
| ① 退いた方向の逆を使う | **当てにならない**（下記） | ほぼゼロ | ゼロ |
| ② **2 点指示**（立ち位置 ⇄ 盤へ一歩寄った点） | 点間 1 m・位置誤差 ±0.1 m で **±8〜11°** | 小 | **押下 +1 回** |
| ③ 到着後に LiDAR で盤面へ正対 | **数度**（原理値） | 中（新規ノード） | ゼロ（自動） |

#### ① を本命にできない理由 — 退避動線と法線は直交する

一見すると「試験員はどのみち退くのだから、退いた方向の逆が法線」で済みそうに見える。
**盤の配置を具体的に描くと成立しない。**

配電盤は壁際にある。試験員は「ロボットに立ってほしい位置」に、**部屋側を背にして盤に正対して**立つ。
ロボットは部屋の側にいるので、**試験員の背後から**その位置へ近づく。

* 「**盤からまっすぐ離れる**」＝ 部屋側へ下がる ＝ **ロボットの進路にそのまま入る**
* 進路を空ける自然な退き方は「**壁沿いに横へ**」＝ **法線と直交する方向**

つまり運用ルール「盤からまっすぐ退いてください」と「ロボットの進路から退いてください」は
**同時に満たせない**。ロボットが正面から来る（＝もっとも普通の状況）ほど退避は横向きになり、
退避ベクトルは法線に対しておよそ 90° ずれる。

→ **① は補助に降格する。** 観測した退避が偶然ほぼ放射方向だった場合に限り、
② の結果が妥当かを確かめる安価なサニティチェックとして使える。単独の根拠にはしない。

#### ② が本命 — 2 点指示

試験員は **2 回押す**。

1. **ロボットに立ってほしい位置**に立って押す（＝ゴール）
2. **そこから盤へ一歩寄った点**で押す（＝向きを与えるためだけ）

**2 点を結ぶベクトルが盤の法線である。** 「盤へ寄る」向きは一意で迷う余地がなく、
**退避動線とまったく競合しない**（押し終えたあとはどちらへ退いてもよい）。

* **精度**: 点間距離 L と人物位置の推定誤差 σ で決まり、L = 1 m・σ = 0.1 m で **±8〜11°** 程度。
  Nav2 の到達許容 ±14° と同程度であり、**指令側がボトルネックにならない水準**である。
* **実装**: `summon_navigator_core.py` に `atan2` 1 本と、サービス呼び出しの 2 段化。
* **(a) にも (b) にも使える。** [§3.2](onsite-recommendation.md) の (a)（登録）と
  (b)（その場で呼ぶ）で手順は同じで、**保存するかどうかだけが違う**。
  「2 点登録」ではなく「2 点指示」と呼ぶのはこのためである。

#### ③ は許容差が要求したときだけ

**③ は「Nav2 の到達許容 ±14° を下回れる唯一の方法」である。** ①②はどれだけ正確に
*指令*しても、Nav2 の `yaw_goal_tolerance = 0.25 rad`（`nav2_params.yaml:43`）で
±14° の到着ばらつきが残る。到着後に別ループで詰める ③ だけがこの下限を突破できる。

→ **[§1.3 項目 1](onsite-premises.md)（カメラ昇降の許容差）の役割が変わった。**
以前は「どの案を採るか」を決める値だったが、いまは
**「② だけで足りるか、③ も要るか」**を決める値である。±15° 程度を許容できるなら ② で終わる。

③ は盤面が LiDAR の高さで平面として見えることが前提で、
[§1.3 項目 5](onsite-premises.md) の確認が要る。

## 3.4 実装の差分

| # | 変更 | 対象 | 種別 | 位置付け |
| --- | --- | --- | --- | --- |
| 1 | 呼び寄せの停止距離を 0 にする | `planning_params.yaml` の `summon_navigator.stop_distance_m` | **パラメータのみ** | 必須 |
| 2 | **退避待ちゲート** — 試験員がゴールから一定距離離れるまでゴール送出を保留 | `summon_navigator.py` | Python 小 | **安全上必須**（下記） |
| 3 | **2 点指示**で盤の法線 yaw を決める（サービスの 2 段化 + `atan2`） | `summon_navigator_core.py` / `summon_navigator.py` | Python 小 | **必須**（§3.3 ②） |

| 6 | FSM に `IDLE → MOVING_TO_PANEL` を追加 | `mode_manager.cpp:134` | **C++・`colcon build` 必要** | (a) に必須 |
| 7 | `_cb_complete()` の遷移先を `FOLLOWING` → `IDLE` へ | `panel_navigator.py:167` | Python 小 | (a) に必須 |
| 8 | 地図 + ピン表示・登録ボタン・ピン選択 | `web_ui` | React 中 | (a) に必須 |
| 9 | LiDAR による盤面正対 | 新規（core + ノード） | Python 中〜大 | 許容差次第（§3.3 ③） |
| 10 | 人物を除いた `/scan_static` を SLAM に渡す | `th_perception` 新規 | Python 中 | **実測次第**（[§2.1](onsite-mapping.md)） |

**6・7 は [初期設計の名残](onsite-options.md)の是正である。**
`FOLLOWING → MOVING_TO_PANEL → AT_PANEL → 完了 → FOLLOWING` という
「常に試験員について回る」時代のループが FSM にそのまま残っており、
**現在は IDLE から MOVING_TO_PANEL へ遷移できない**（`mode_manager.cpp:134-143` で確認）。
前回は仮定の話だったが、**(a) を採る以上これはクリティカルパス上にある。**

### 2 が「安全上必須」である理由

停止距離を 0 にするということは、**呼び寄せのゴールが試験員の体のある場所そのものになる**
ということである。試験員が退く前に発進すると

* Nav2 の costmap 上でゴールセルが占有され、経路計画が失敗する（`goal in obstacle`）
* あるいは**試験員に向かって走る**

固定の待ち時間で誤魔化してはいけない。**`summon_navigator.py` が既に購読している
`/person/status` を使い、記録したゴールから試験員が一定距離離れたことを確認してから
送出する。** 離れるまでは WebUI に「退いてください」を出す。数十行で書ける上、
UI 側の表示も自然になる。

**待機中に追跡が切れた場合の扱いを必ず決めておくこと。** 試験員は移動中であり
DR-SPAAM は約 2 Hz なので、待機中の `is_lost` は十分に起こりうる。条件が
「試験員がゴールから離れた」だけだと、**追跡が切れた瞬間に条件が永久に成立せず、
ロボットが黙って発進しないまま止まる**。さらに `require_explicit_target_selection` が
ラッチすると（VISION.md §8）復帰にタブレット操作が要る。
**タイムアウトを設け、超えたら呼び寄せを中止して `SummonStatus` にイベントを出し、
理由付きで IDLE に戻す。** 仕様の穴になりやすいので明記する。

その上で:

1. **1 + 2 + 3**（呼び寄せの改良）。**ここまでで「盤の前に立って呼べばロボットが来る」が成立する。**
   登録もピンも FSM 変更も要らず、**地図の品質にもほぼ依存しない**（§3.2 の (b)）。
   最小構成として単独で価値があり、実証実験のフォールバックにもなる。
2. **4 + 5 + 6 + 7**（登録とピンへの移動）。試験員が歩かずに盤を指定できるようになる。
3. **8**（WebUI）。2 と対で必要。VISION.md §6.1 で撤去した配電盤カードを、
   登録機能付きで「準備」タブへ戻す（[§2.5](onsite-mapping.md)）。
4. **9 / 10**。0 の測定結果が要求したときだけ。
