# 発想を広げた案 — 試験場内の移動

[移動方式の候補と比較](onsite-options.md) の案 A〜G から外れる案の置き場。
transit 側の [9-A〜9-R](transit-ideas.md) と番号が衝突しないよう **10-x** を使う。

**この区間の詰まりどころは 2 つしかない**ので、案もそこに集まる。

1. **地図原点が毎回変わるので絶対座標が持てない**（[§1.5](onsite-premises.md)）→ 10-A・10-G
2. **搬送だけでは盤前の正対・距離を保証できない**（[§1.2](onsite-premises.md)）→ 10-B・10-C・10-E

そして 3 つ目の道として、**問題そのものを消す**案がある → 10-D・10-F。

---

# 第 1 群: 絶対座標を持たずに盤を指す

## 10-A. セッション内で盤位置を登録する — **✅ 採用（2026-08-11）**

> **決定済み。** 実装差分と実装順は [推奨構成 §3.4](onsite-recommendation.md) が正。
> 本項は経緯として残す。**登録方法は当初案から変わった**（下記）。

`panels.yaml` に**絶対座標を書き込んでおく**のをやめ、**そのセッションで実測した座標を
その場で登録する**。

> ✅ **登録は「試験員が盤前に立ってボタンを押す」だけでよい**（2026-08-11）。
> 当初はロボットを手動ジョグまたは人力で盤前に置く想定で、「1 周目は結局手動」を
> 弱点として挙げていた。**改良呼び寄せ（[案 E'](onsite-options.md)）と同じ幾何**
> — 試験員の立ち位置を `base_link→map` で map 座標に変換する
> （`summon_navigator.py:148` と同じ処理）— を使えば、**運転はまったく要らない。
> この弱点は消えた。**

* **何が解けるか**: [§1.5](onsite-premises.md) の地図原点問題が消える。
  セッションをまたいで座標を持ち越さないため、原点が毎回変わっても矛盾しない。
* **実装コスト**: **航法の新規実装は不要**。`panel_navigator.py` は既にあり
  Nav2 ゴールを投げる形にはなっているが、**実機での検証状況は未確認**（VISION.md §9 行 6 が
  「❓要確認」のまま）。この点は差し引いて読むこと。必要なのは
  1. 登録サービス（現在姿勢を盤 ID に紐付ける）
  2. `_load_panels()` の座標取得元を YAML からその登録テーブルへ差し替える
  3. WebUI の登録ボタン（§6.1 で撤去した配電盤カードを、登録機能付きで戻す）
  4. **FSM の是正** — `isTransitionAllowed()` に `IDLE → MOVING_TO_PANEL` を追加し、
     `_cb_complete()` の遷移先を `FOLLOWING` → `IDLE` へ。
     [初期設計の名残](onsite-options.md)を参照

  1〜3 は Python のみでシンボリックリンク反映が効くが、**4 は C++ で `colcon build` が要る**。
  「データの持ち方を変えるだけ」では済まない点に注意。
* **残る弱点**: 各盤を 1 回しか訪れないなら手数はほとんど減らない
  （登録のために結局歩くため）。**価値は「地図作成で一度歩いたあと、同じ盤に何回戻るか」に依存する**
  （[§1.3 項目 3](onsite-premises.md)）。撮り直し・複数アングル・午前と午後で 2 周、
  といった運用があれば効く。**1 回きりなら [案 E'](onsite-options.md)（その場で呼ぶ）だけで足りる。**
* **向きは別途必要**: 登録できるのは位置だけで、盤の法線は立ち位置からは決まらない。
  → [§3.3](onsite-recommendation.md)
* **副次効果**: 登録した盤前姿勢は**地図の中でロボットが確実に到達できた点**なので、
  経路計画が失敗しにくいことが分かっている。任意のタップ点（案 D）より安全である。

## 10-G. 追従の軌跡に「ここが盤」を打つ（教示再生の転用）

transit 側で検討した[教示再生（案 4）](transit-options.md)を試験場内に転用する。
試験員について回った軌跡を記録し、盤の前で立ち止まったところにマークを打つ。
再生時はマークまで走る。

10-A との違いは、**盤前姿勢だけでなくそこまでの経路も記録される**点。
Nav2 の経路計画が苦手な場所（狭い盤間、什器の隙間）でも、
一度通れた経路をなぞれる。

**ただし試験場内は数 m しかなく、経路を記録する価値は transit より小さい。**
10-A で足りるなら 10-A を採る。10-A で経路計画が失敗する現場だった場合の逃げ道として残す。

# 第 2 群: 最後の数十 cm を詰める

## 10-B. LiDAR で盤面に正対する — **条件付き必須**（[案 G](onsite-options.md) の中身）

> **2026-08-11 に位置付けが上がった。** 採用した「試験員の立ち位置を使う」方式は
> **位置は与えるが向きを与えない**（[§3.3](onsite-recommendation.md)）。
> さらに **Nav2 の `yaw_goal_tolerance = 0.25 rad` は指令精度によらず残る下限**であり、
> **本案だけがこれを下回れる。** アイデアではなく、
> [§1.4](onsite-premises.md) の許容差が ±15° より厳しければ**必須の構成要素**になる。
> 許容差が緩ければ、より安い [§3.3 の ②（2 点指示）](onsite-recommendation.md) で足りる。

前方の LiDAR 点群に直線をフィットし、その法線方向へ正対しつつ規定距離まで詰める。
`base_link` 相対で完結するため**地図も自己位置推定も要らない**。

* **実装の形**: CLAUDE.md「追従ロジックの二層構造」に従い、
  **ROS2 非依存の純粋関数**（スキャン点列 → 正対に必要な並進・回転）として書き、
  `pytest` でテストしてからノードに載せる。`follow_planner_core.py` と同じ構造。
  速度指令は `/cmd_vel_retreat`（priority 20）に出す（CLAUDE.md の不変ルール）。
* **精度**: 原理的には LiDAR の測距精度（数 cm）と平面フィットの角度精度で決まり、
  [§1.2](onsite-premises.md) の ±0.45 m / ±14° を 1 桁改善できる可能性がある。
* **弱点 1**: **盤面が LiDAR の高さで平面として見えるか**が現場依存。
  配線ダクト・扉の取っ手・銘板で凹凸があると平面フィットが暴れる。
  → [§1.3 項目 3・4](onsite-premises.md) で現物を確認する。
* **弱点 2**: **「どの平面か」を決められない。** 盤が壁面に埋め込まれていると盤と壁が
  同一平面になり、盤の左右位置が定まらない。前段（案 A〜F）が「盤が正面に来る位置」まで
  運んでいることが前提になる。10-C はこの弱点を直接に解く。

## 10-C. 盤に撤去可能な反射マーカーを置いて一意に識別する — **要検証**

盤の脇（または盤面下部）に反射材を一時的に貼り、LiDAR の反射強度（intensity）で
盤を特定する。10-B の弱点 2（どの平面か決まらない）が解ける。

* **現場許可**: `questions-venue.md` §4 で
  「経路上・壁面に目印（反射板・コーン等）を一時的に置いてよいか」を**既に聞いている**。
  新たに聞き直す必要がない。
* **要検証**: RPLIDAR S1 の intensity が、通常の面と反射材とで分離できるか。
  これは transit 側の [9-D（試験員に再帰反射材を着けて一意識別）](transit-ideas.md) と
  **同じ検証で兼ねられる**。片方を試せば両方の可否が同時に分かるため、検証の費用対効果が高い。
* **弱点**: 盤ごとにマーカーを置く手間が発生する。**これは「前日準備が大変」という
  先方の要望と逆行する。** 盤の数が多いほど不利。

## 10-E. 盤前に物理ガイドを置く

撤去可能な車止め・コーンで機体を機械的に位置決めする。ロボットを押し当てれば位置が決まる。

原始的だが**再現性は最も高い**。人力（[案 F](onsite-options.md)）や
手動ジョグ（[案 A](onsite-options.md)）と組み合わせると、
「試験員の目視頼み」だった精度が機械的に保証される。
`questions-venue.md` §4 で許可を確認済み。

**実証実験当日のフォールバックとして最も確実**であり、作るものが何も無い。

# 第 3 群: 問題そのものを消す

## 10-D. カメラ側に吸収してもらう — **交渉案・最も費用対効果が高い可能性**

[§1.3 項目 1](onsite-premises.md)（カメラ昇降が要求する許容差）を、
**「聞く」だけでなく「交渉する」対象として扱う。**

2D LiDAR + スキッドステアのクローラーで盤面に対して ±5 cm・±2° を出すのは無理筋である。
一方、**カメラ側で首振り・広角・デジタルズームによって ±30 cm 程度の位置ずれを吸収するのは
はるかに安い**。上部を「確認する」ことが目的であり、決まった画角で撮ることが目的ではない。

**この交渉が通れば、案 C・E がそのまま使えて 10-A・10-B は不要になる。**
逆にこの交渉をせずに位置合わせ機構を作ると、実証実験までの工数を機構に取られる。
[§1.3 項目 1](onsite-premises.md) を確認するときに、
**許容差を聞くのではなく「どこまで緩められるか」を聞く**のが正しい。

## 10-F. 盤列の中央に置き、移動そのものを減らす

盤が壁沿いに並んでいるなら、**1 箇所に置いて複数の盤をまかなえないか**を確認する。
移動が減れば [§1.1](onsite-premises.md) の「操作手数 × 盤の数」がそのまま小さくなる。

transit 側の [9-J（移動そのものをなくす）](transit-ideas.md) と同じ発想。
**成立するかどうかはカメラ昇降の到達範囲と盤の間隔（[§1.3 項目 2・4](onsite-premises.md)）で決まり、
技術ではなく寸法の問題である。** 早く確認するだけで結論が出る。

## 10-H. 試験員が指した方向を使う（専用指定デバイス）

VISION.md §8「待機中の『指定位置への移動』機能」の 3。距離計 + 姿勢計を持つデバイスで
盤を指すと、ロボットがそこへ行く。**ハードウェア含め未着手**であり、
デバイスの方位基準とロボット座標系のヨー合わせが技術課題として残っている。

**実証実験までの工数では現実的でない。** 10-A で同じ効果（絶対座標を持たない盤の指定）が
はるかに安く得られるため、この区間では優先しない。

## まとめ（2026-08-11 の決定後）

### 本線に昇格した

* **10-A** セッション内で盤位置を登録 — ✅ **採用**。登録は「立ってボタン」だけになり、
  当初の弱点（1 周目が手動）が消えた。→ [推奨構成](onsite-recommendation.md)

### 許容差が決めるもの

* **10-B** LiDAR で盤面に正対 — **条件付き必須**。Nav2 の ±14° を下回れる唯一の手段。
  [§1.4](onsite-premises.md) の許容差が ±15° より厳しければ作る。
  緩ければ [§3.3 の ②](onsite-recommendation.md)（2 点指示・押下 1 回増えるだけ）で足りる
* **10-D** カメラ側の許容差をどこまで緩められるか — **これが通れば 10-B が不要になる。**
  実装より先に交渉する価値は決定後も変わらない

### 寸法を聞くだけで結論が出る

* **10-F** 1 箇所から複数盤をまかなえるか — 成立すれば移動の回数そのものが減る

### 必要になったら検証する

* **10-C** 反射マーカー — 10-B の弱点 2（どの平面か決まらない）を解く。
  transit の [9-D](transit-ideas.md) と同じ intensity 分離性の検証で両方の可否が分かる。
  **ただし盤ごとにマーカーを置く手間は「前日準備が大変」と逆行する**ので、
  10-B が単独で成立しなかったときの手段に留める

### 作るものが無いフォールバック

* **10-E** 物理ガイド + 人力／手動ジョグ — 当日破綻したときに先方の要望自体は満たせる

### この区間では優先しない

* **10-G** 教示再生の転用（10-A で足りる場合の逃げ道）
* **10-H** 専用指定デバイス（工数が合わない）
