# 地図作成の容易化と盤の指定 — 試験場内

**配電盤の位置は毎回変わる**ため、試験場に着いたら毎回 SLAM で地図を作り、
そのタイミングで盤位置を登録する（[推奨構成](onsite-recommendation.md)）。
この地図作成が試験員だけで完結しないと運用が回らない。本ファイルはその 2 点

* **地図作成を簡単にする**（§2.1〜§2.4）
* **試験員が盤を指定できるようにする**（§2.5）

を扱う。前提は [前提の整理](onsite-premises.md)。

---

## 2.1 まず測る — 「地図が汚れる」はまだ伝聞である

出発点になっている「**作業者などが地図に写り込み、特殊なツールで整形する必要があった**」は、
**他所のワークフローについて聞いた話**であり、このリポジトリの構成
（`slam_toolbox` の `map_and_localization_slam_toolbox_node` + `/scan_filtered`）で
同じことが起きると確認したわけではない。

**対策を設計する前に、自分たちのスタックで再現するかを見る。**
これは transit 側の[実測が必要な数値](transit-premises.md)と同じ位置付けの、最も安いテストである。

> **測り方**: 人が数人歩いている部屋で普通に地図を作り、出来上がった occupancy grid を見る。
> ロボットは追従で連れ回せばよい（既存の FOLLOWING_MAPLESS）。特別な準備は要らない。

**予想**: `slam_toolbox` は occupancy grid をポーズグラフから再生成するため、
**人が通り過ぎただけのセルは後続スキャンで free に上書きされることが多い**。
焼き付きとして残りやすいのは

* **立ち止まっている人**（会話中の作業者など）
* **置かれたまま動かない台車・パレット**

であり、「歩いている作業者」ではない可能性が高い。**もしそうなら §2.4 のマスク実装は不要になる。**
この一点で工数がまるごと変わるため、測ってから決める。

---

## 2.2 「汚い」と「壊れる」を分ける

地図に人が写り込んだとして、**実害があるのはどの場合か**を切り分ける。
ここを混ぜると「地図をきれいにしなければならない」という過大な要求になる。

| 症状 | 実害 | 効く対策 |
| --- | --- | --- |
| 人が焼き付いて黒い点が散っている | **見た目だけ。実害なし** | **何もしなくてよい** |
| 焼き付きが通路を塞ぎ、Nav2 が経路を出さない | 盤へ移動できない | costmap のチューニング、または地図の作り直し（§2.3） |
| 試験員が地図を読めず、どこが盤か分からない | 盤を指定できない | **ピン方式で問題ごと消える（§2.5）** |
| 焼き付きが盤の直前にあり、盤前に入れない | 到着できない | 作り直し（§2.3）／登録位置の取り直し |

**3 行目がピン方式で消えることが重要である。** 「地図をきれいにしなければ」という圧力の
相当部分は、実は「試験員が地図を読んで盤を探す」という前提から来ている。
盤を**立ち位置の登録**で指すなら、地図が読めるかどうかは関係なくなる。

残る要求は「**Nav2 が盤まで経路を引けること**」だけであり、これは見た目の綺麗さとは別の基準である。

## 2.3 実装ゼロで効く手

順に試して、足りなければ §2.4 に進む。

1. **地図を作り直す。** VISION.md §8 の「地図を破棄」（`slam_toolbox` プロセスを終了させ
   `respawn` で作り直す）が**既に実装されている**。
   **失敗した地図は、特殊なツールを使わずに WebUI から捨ててやり直せる。**
   「整形しなければならない」という前提そのものが、この機能によって既に一段崩れている。
2. **人がいない時間帯に回る。** 地図作成は試験場に着いた直後の数分であり、
   その時間だけ通路を空けてもらう交渉は、恒久的な現場改変よりはるかに軽い。
3. **全部を地図にしなくてよい。** 必要なのは**盤の周辺**と**盤どうしを結ぶ経路**だけである。
   建屋全体を回る必要はない。範囲が狭いほど写り込みも滞在時間も減る。
4. **地図作成中の移動は追従で済む。** 試験員が歩いてロボットを連れ回すだけでよく、
   運転操作は要らない（既存の FOLLOWING_MAPLESS）。

## 2.4 それでも必要なら: 人物を除いたスキャンを SLAM にだけ渡す

§2.1 の実測で焼き付きが実害を出した場合の実装案。

**やること**: DR-SPAAM が出す脚検知位置の周辺のスキャン点を落とし、
**SLAM だけが購読する第 3 のトピック**として配信する。

```
                      ┌─→ /scan_filtered ─┬─→ 人物トラッカー（脚検知の入力）
/scan ─→ lidar_filter ┤                    └─→ Nav2 obstacle layer ★人を見せる
  (死角マスク)         │
                      └─→ /scan_static ──────→ slam_toolbox のみ ★人を消す
                           (人物マスク・新規)
```

* **入力は DR-SPAAM の `PoseArray`**（`multiple_sensor_person_tracker_component.cpp:1149` の
  `dr_spaam_topic_name`）。**追跡対象 1 人ではなく検知候補すべて**が入っているため、
  試験員以外の作業者もマスクできる。`/person/status`（追跡対象のみ）を使ってはいけない。
* **出力は必ず別トピックにする。`/scan_filtered` を上書きしてはいけない。** 理由は 2 つあり、
  2 つ目が重要:
  1. `/scan_filtered` は**人物トラッカー自身の入力**である（`bringup.launch.py:227`）。
     ここから人を消すと脚検知が自分の入力を失い、追従が壊れる。
  2. `/scan_filtered` は **Nav2 の obstacle layer の入力**でもある（`nav2_params.yaml:190`）。
     **ここから人を消すのは安全上の後退である。** 走行中のロボットが人を障害物として
     見なくなる。**この 1 点だけは後から「まとめて 1 本にすれば簡単」と整理されないよう、
     設計意図として明記しておく。**
* **限界**: DR-SPAAM は CPU 実行で約 2 Hz（VISION.md §4）。スキャンは 10 Hz 前後で来るため、
  マスクは**ベストエフォートであって保証ではない**。検知されなかった人は写り込む。
  §2.3 の「作り直せる」を消してよい理由にはならない。
* **実装の置き場**: `lidar_filter.py`（`th_perception`）と同じ形の純粋な変換ノード。
  死角マスクと同様、Python で書けて `--symlink-install` で即反映される。

## 2.5 盤の指定は「指す」のではなく「選ぶ」

### 地図タップの弱点は座標変換ではなく可読性

タブレットに地図を出してタップする方式（[案 D](onsite-options.md)）は操作として直感的だが、
**occupancy grid は壁の輪郭が黒い線として出るだけで、どれが配電盤かは表示されない。**
試験員は自分の記憶と照合しながら地図を読むことになり、盤が複数あると取り違える。

これは表示を工夫すれば解ける問題ではない。**盤という情報が地図の中に存在しない**からである。

### ピン方式 — 立ち位置の登録が同一性を与える

地図作成中に**試験員が盤の前に立って「ここが N 番盤」を押す**と、その位置がピンとして地図に載る
（[推奨構成](onsite-recommendation.md)）。以後の指定は**ピンを選ぶ**操作になる。

**ピンの同一性は「試験員がそこに立った」という物理的な行為から来ており、
地図を読み取る能力を要求しない。** 地図が多少汚れていても、ピンは正しい場所にある。

| | 地図タップ（指す） | ピン選択（選ぶ） |
| --- | --- | --- |
| 盤がどこか | **試験員が地図から読み取る** | **登録済み。読み取り不要** |
| 地図の可読性 | 必要 | **不要** |
| 取り違え | 起きうる | 番号で確定 |
| 正対の向き | 指定できない | 登録時に決められる（[§1.2](onsite-premises.md)） |
| 未登録の場所を指す | できる | できない |

最後の行だけがタップの利点である。**リカバリ用に残す価値はあるが、主操作にはしない。**

### 表示の作り

* **ピンには登録順の番号を振る**（1・2・3…）。名前の入力は現場では手間になるので既定は番号のみ。
* **地図は「ピンがどこにあるか」の空間把握のためだけに出す。** 地図から盤を探させない以上、
  多少汚くても運用は成立する（§2.2 の結論）。
* **ロボットの現在位置とピンを同じ画面に出す。** 「今どのピンへ向かっているか」が分かれば、
  取り違えたときに試験員が停止させられる。
* 将来的な装飾: 登録時のカメラ画像をサムネイルとしてピンに付けると一目で分かるが、
  カメラは外部システムであり（VISION.md §8）、**今は番号で足りる**。

### WebUI 側の前提

VISION.md §6.1 は「配電盤への移動は画面に出さない」として**配電盤カードを撤去済み**である
（MOVING_TO_PANEL がスコープ外だったため）。ピン方式を採るなら**登録機能付きで戻すことになる**。
置き場所は「準備」タブ（地図作成と同じフェーズ）に登録、「運用」タブに選択、が素直な分割である。
