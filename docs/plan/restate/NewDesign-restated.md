## 3. 開発の進め方

前提：PoC のあと、MVP を作る期間が短い。

* **P-1** PoC では、走行方式の候補を**削らずに全部実装**し、全部試験する。
* **P-2** MVP 段階では、PoC の結果で採用されなかった方式を**削っていく**。足し算ではなく引き算で進める。
* **P-3** そのため、方式ごとに独立した KPI を設定し、方式間で比較できるようにしておく（§5）。

### 採否の判断順（上から順に見て、落ちた時点で切る）

1. **許可** — その方式を試験場で使う許可が下りるか。下りなければ他がどれだけ良くても採用しない（足切り）。
2. **完走率・人の介入回数** — 実用に足る自律度があるか。
3. **安全** — 接触 0 件、意図しない発進 0 件。
4. **MVP 期間内に作れるか** — 工数。

## 9. 運用シナリオ：保管場所⇔試験場の移動

**往路と復路を区別しない。行きも帰りも同じ手順・同じ UI を使う。**

| 順 | やること                             |
| -- | ------------------------------------ |
| 1  | 駆動用バッテリー残量を確認する       |
| 2  | WebUI で走行方式を選ぶ               |
| 3  | 試験場（または保管場所）まで走行する |

### バッテリーの扱い

* 残量低下時には警告を出す。
* **警告が出ていないことは、長時間の動作を保証しない。**
* 走行時間と残量を見て、最終的に**試験員が判断する**。

### 選べる走行方式

WebUI には次の 7 つが並ぶ（原文の並び順のまま）。

1. 追従走行（速度改善版）
2. 手動走行（現行のまま）
3. 教示（追従走行）
4. 教示（手動走行）
5. 教示再生走行
6. 区画線走行
7. 電子リード走行

### 教示に関する制約

* **保管場所以外を起点にした教示はしない。**
* 教示再生走行は、**基本的に**保管場所からのみ開始する。
* 【希望・未確定】経路の付近にいるなら、途中からでも経路に復帰できるようにしたい。
* 教示をやり直すのは、次のとき。
  * 何度も使う新規経路ができたとき
  * 物の配置が大きく変わったとき

各方式の中身は [各走行方法の詳細](./NewDesign-transit-restated.md) にある。

## 11. 常時成り立つ規則：異常時

### 11.1 異常ウィンドウ

* 異常が発生したら、画面の上にウィンドウを表示する。
* **解決していなくても、試験員が非表示にできる。** 非表示にしたものは再表示できる。
* 異常が解決したら、ウィンドウは**自動で閉じる**。そのうえで「再開するか」を問う。

| 選択                   | 結果                               |
| ---------------------- | ---------------------------------- |
| はい                   | **異常発生前のモードに戻る** |
| いいえ                 | **停止モードで戻る**         |
| 確認（1 択のみの場合） | 再開はしない                       |

* できるだけ「再開できる」ように作る。
* ただし、**再開できない異常**、および**再開先が手動操作になる異常**では、選択肢を「確認」1 択にする。

### 11.2 物理緊急停止ボタン

* 押されている間は、**人力搬送モード**とみなす（人が機体を押して運んでいる）。
* **センサ系統は止めない。** 止めないので、解除後にそのまま再開できる。
* 押されている間、画面には**解除方法を案内**する。
* 解除されたら、**再開ボタン**を表示する。

### 11.3 走行中の障害物

* 障害物が現れたら、**原則停止**する。
* **走行開始時に決定した経路を逸脱しない。**（＝避けて回り込むことはしない）

### 11.4 通信断

次のどちらかが切断されたら**停止**する。

* 必須通信系統（ESP32 / RaspberryPi4 / PC）
* **実際に操作に使われていたタブレット**
  * 「接続されていただけ」のタブレットは対象外。切れても停止しない。

## 12. 常時成り立つ規則：人物追跡

LiDAR による人物追跡。**追従走行・位置指定・呼び寄せ**の 3 用途で使う。

### 12.1 対象の選び方

| 状況                         | 挙動                                       |
| ---------------------------- | ------------------------------------------ |
| 数秒間、一人しか認識されない | **その人を自動で選択する**           |
| 複数人いる                   | **勝手に選択しない**（試験員が選ぶ） |

### 12.2 ロスト時

| ロスト継続時間                              | 挙動                                   |
| ------------------------------------------- | -------------------------------------- |
| 500 ms 以内【暫定値・実際の動作を見て調整】 | **停止しない**（追跡を継続扱い）       |
| 500 ms 超                                   | **選択を解除し、停止する**             |

* 人物追跡が必要な状態でロストした（していた）ときは、**案内ウィンドウ**を出す。
* この案内ウィンドウは、**対象選択・モード選択の操作に被らない位置**に出す。
* モード選択で**人物追跡が不要なモードが選ばれた**場合、案内ウィンドウは**自動で閉じる**。

### 12.3 起動・停止

* 人物追跡は**任意のタイミングで停止できる**。
* **人物追跡が必要な画面に入ったら自動で起動する。**
* 起動中は、**対象選択画面の中心に「起動中」と表示**する。

## 13. 常時成り立つ規則：その他

* **人の検知などを任意のタイミングで止められる。** 理由：処理が相当重く、PC が熱くなる。
* 試験場内は**低速に制限**する。理由：納品する製品が置いてあるため。試験場内では自動ブレーキオンがデフォルト。
* 重心が高くなることが予想されるので加減速はゆっくり行う。ESP32のファームウェアレベルでモータ出力の急変を抑える。制動距離が長い前提で制御する。

### 15.1 ハードウェア

| # | 機器         | 役割・仕様                                                              | 接続                    |
| - | ------------ | ----------------------------------------------------------------------- | ----------------------- |
| 1 | Wi-Fi AP     | **全ての機器の通信を中継する**                                          | —                       |

| 3 | ESP32        | CuGoV3（モーター×2・エンコーダ×2）、IMU、物理緊急停止ボタンと GPIO 接続 | PC と Wi-Fi / WebSocket |

| 5 | LiDAR        | RPLIDAR S1、360° 全周、256000 baud、10 Hz                               | RaspberryPi4 に USB     |
| 6 | IMU          | DSR1603 / BNO055、9 軸（加速度計＋ジャイロ＋地磁気）                    | ESP32 に GPIO           |
| 7 | CuGoV3       | クローラー、DC モーター×2 ＋ エンコーダ×2                               | ESP32 に GPIO           |
