### C-01 必須通信系統は 3 者か 4 者か

| | 記述 |
| --- | --- |
| `NewDesign.md` §用語 | 「ESP32・RaspberryPi4(LiDAR)・PC の **3 者間**の通信」 |
| `restate/NewDesign-restated.md` §1 | 「WiFi-AP・ESP32・RaspberryPi4(LiDAR)・PC の **4 者間**」 |
| 同 §8 疎通確認表 | WiFi-AP を **必須**として列挙 |
| 同 §11.4 | 「必須通信系統（**ESP32 / RaspberryPi4 / PC**）」← 3 者に戻っている |

**採用: 3 者を「必須通信系統」と定義する。Wi-Fi AP は単一障害点として別枠で監視・表示する。**

根拠:
1. `restate` 側が同一文書内で 4 者（§1・§8）と 3 者（§11.4）の両方を書いており、**内部不整合**。
   一方 `NewDesign.md` は一貫して 3 者。
2. AP は「通信の相手」ではなく「通信路」である。AP が落ちれば 3 者すべてが同時に切れるので、

### C-13 異常解決後の「はい／いいえ」が何を指すか

| | 記述 |
| --- | --- |
| `NewDesign.md` §異常時 | 「再開する場合"はい"で**異常発生前のモードに戻る**。"いいえ"で**停止モードで戻る**」 |

原典は**モード**しか書いておらず、戻った先で**走り出すのか止まっているのか**が決まらない。
モードと状態を分ける本設計書（[Spec-modes.md](Spec-modes.md) §1）では、ここを明示する必要がある。

**採用: 次のように具体化する（U-8 により 2026-08-15 改訂）。**

| 選択 | モード | 状態 | 原典との対応 |
| --- | --- | --- | --- |
| **はい** | **異常発生前のモードに戻る** | **走行を再開する**（`RUN`） | 原典「異常発生前のモードに戻る」 |
| **いいえ** | **異常発生前のモードに戻る** | **一時停止のまま**（`PAUSE`） | 原典「停止モードで戻る」 |
| **確認**（1 択・モードは続けられる） | **異常発生前のモードに戻る** | **一時停止のまま**（`PAUSE`） | 再開の可否を問わない場合 |
| **確認**（1 択・モードを続けられない） | `IDLE` | 停止 | 記録の連続性が切れた等 |

**「いいえ」で待機（`IDLE`）に戻さない。**戻してしまうと、対象選択・経路指定・記録内容を

「いいえ」は「**まだ走り出さないでほしい**」という意思表示であって、
「方式をやめたい」という意思表示ではない。方式をやめたいときは「終了」を押す。

1. 「はい」と「いいえ」の違いは**走り出すかどうか**だけにする。モードは両方とも戻る。

   目標 G1 の「意図しない挙動」には当たらない。
3. モードを続けられない異常（教示中に記録の連続性が切れた等）だけは `IDLE` へ戻す。
   このとき**未保存の記録は破棄せず、保存するかを問う**。

### C-14 人物追跡は「任意のタイミングで停止できる」のか、できないモードがあるのか

| | 記述 |
| --- | --- |
| `NewDesign.md` §人物追跡 | 「人物追跡は**任意のタイミングで停止できる**」 |
| `NewDesign.md` §その他仕様 | 「人の検知などを**任意のタイミングで止めれる**ようにする（処理が相当重く PC が熱くなる）」 |
| `NewDesign.md` §人物追跡 | 「**必要な画面に入った場合は自動で起動する**」 |

「任意のタイミングで停止できる」と「必要な画面では自動起動する」が同居しており、
**人物追跡を必要とするモードの最中に停止したらどうなるかが決まらない。**

**採用: 人物追跡を要するモードでは停止できないものとする（OFF ボタンを非活性にする）。**

根拠:
1. 停止できてしまうと、追従走行中に人物データが消える。これは `PERSON_TRACKER_LOST` と
   区別がつかず、現行実装は強制遷移させる（`CL-X-1`）。
2. 「任意のタイミングで停止できる」の目的は**処理負荷と発熱の軽減**であり、
   人物追跡を使っていないときに止められれば目的は達せられる。
   使用中に止める必要はない。
3. 「必要な画面に入ったら自動で起動する」と原典自身が書いており、
   必要な画面で止められることは想定されていないと読める。

**したがって「意図的な OFF」は、人物追跡を要さないモードでのみ起こりうる。**
そこで起きた途絶はフォルトではないので、強制遷移させない（`CL-X-1` の解決）。

### C-15 試験場内のモードは人物追跡を使うのか（U-14 により新規）

原典は人物追跡を**走行方式の話としてしか書いていない**。一方で試験場内の手順は、
盤登録の 2 点指示も呼び寄せも「試験員がどこに立っているか」を前提にしている。
U-14 で試験準備・試験の画面に「対象選択」タブを置くと決めたことで、この矛盾が表に出た。

**採用: 試験場内のモードも人物追跡を使う。ただし「使う場面」を限定する。**

| モード | 人物追跡 | 使う場面 | ロスト時 |
| --- | --- | --- | --- |
| `PREP`（試験準備） | **使う** | 2 点指示で登録するとき | **強制遷移しない。**登録を受け付けないだけ（案内ウィンドウ）。地図作成そのものは人物追跡に依存しない |
| `SUMMON`（呼び寄せ） | **使う** | 2 点指示と退避待ち | **強制遷移する**（`IDLE` へ）。人の位置が分からないまま人のほうへ走らせない |
| `PANEL_NAV` / `AT_PANEL` / `HOME_NAV` | 使わない | — | 継続する |

**`PREP` を強制遷移の対象にしない理由**: 前日の地図作成は数十分続く作業で、
その大半は人物追跡を必要としない。ロストのたびに方式を抜けると作りかけの地図を失う。
「登録の瞬間だけ猶予なしで拒否する」は C-05 で既に決めた方針であり、それと同じ扱いにする。

反映先: [Spec-modes.md](Spec-modes.md) §9 ／ [Spec-safety.md](Spec-safety.md) §5 ／
[Spec-onsite.md](Spec-onsite.md) §2・§3
