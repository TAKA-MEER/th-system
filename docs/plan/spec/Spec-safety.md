# 安全と異常時の扱い

[Spec.md](Spec.md) の詳細。**目標 G1（人・物への接触 0 件、意図しない挙動 0 件）を担保する仕組み。**

> **G1 は他のすべてに優先する。G1 を犠牲にして G2〜G5 を満たしてはいけない。**

---

## 1. 安全チェーンの階層

止める仕組みを 4 層に分け、**上位が下位の故障に依存しない**ようにする。

| 層 | 仕組み | 反応時間 | 依存 |
| --- | --- | --- | --- |
| **1** | **物理非常停止ボタン** | 即時 | 何にも依存しない。押されている間は駆動が切れる |
| **2** | **ESP32 のウォッチドッグ** | **600 ms 以内** | ROS2 が落ちても効く。ESP32 単体で成立 |
| **3** | **安全監視の非常停止・フォルトロック** | **100 ms 以内** | PC 上。モード管理の処理を待たずに速度指令をゼロにする |
| **4** | **モード管理の状態遷移** | 上位が止めた後 | **回復フォルトは状態を `PAUSE` へ／重大フォルトは `ESTOP` へ**（§3.5）。**`IDLE` へは落とさない** |

**設計上の不変ルール**: 速度指令は必ず優先度つきの多重化を経由する。
どのノードも駆動へ直接指令してはいけない。
安全監視の出力が最上位の優先度を持ち、**モード管理の処理を待たずに**モーターをゼロにする。

## 2. 障害物への反応

### 2.1 方式ごとの扱い（[Spec-open.md](Spec-open.md) C-11 / U-2）

| 対象 | 挙動 | 無効化 |
| --- | --- | --- |
| **自律系**（追従／教示（追従）／教示再生／ライン誘導走行／電子リード走行／試験場内 Nav2） | **停止する** | **不可** |
| **手動系**（手動走行／教示（手動）／ジョグ介入）・**場外** | **警告のみ。**自動ブレーキは既定 OFF | 試験員が任意 ON にできる |
| **手動系・試験場内** | 自動ブレーキ **既定 ON** | 試験員が OFF にできる（**既定であって固定ではない**） |

**停止したあと**は、人が手動操作で避けるか、障害物をどける。
**自動で迂回しない。走行開始時に決定した経路を逸脱しない。**

### 2.2 停止距離の決め方

```
制動距離 = v² / (2a) + v × t_遅延
停止判定距離 = 制動距離 + 余裕
```

`a`（実測の制動加速度）が決まるまで、`obstacle_check_distance_m` /
`lidar_timeout_ms` / `v_max` / 追従の停止距離は**すべて暫定値**である
（[Spec-params.md](Spec-params.md)、[Spec-open.md](Spec-open.md) O-c1）。

**現状値の危険性**（要引き直し）:

| 項目 | 現状値 | 計画 `v_max` = 0.7 m/s での意味 |
| --- | --- | --- |
| `obstacle_check_distance_m` | 0.45 m | **不足**（設定上の制動距離だけで 0.49 m） |
| `lidar_timeout_ms` / `esp32_timeout_ms` | 2000 ms | タイムアウトまでに **1.4 m 走る** |

### 2.3 後退方向は LiDAR の死角（`CL-X-4`）

360° LiDAR でも機体構造物のマスクにより後方に死角が生じる。
**手動ジョグでぶつかるのはここ**である。

| 対策 | 内容 |
| --- | --- |
| 後退速度 | **前進よりさらに落とす**（`v_reverse` < `v_slow`） |
| 表示 | 後退中は画面に「後方は死角があります」と常時表示する |
| 検証 | 障害物リミッタの故障注入試験で**後退方向も必ず試す**（`CL-X-3` / `CL-X-4`） |

### 2.5 障害物は単一点では判定しない（実機 2026-09-04）

**スキャン 1 枚に 1 点だけ現れた近距離点で停止してはいけない。**
実機で「何も無いところで止まり、しばらくして独りでに走り出す」が起きた。
ノイズ 1 点が停止距離を割り、次のスキャンで消えるため再開していた。

| 項目 | 方針 |
| --- | --- |
| 判定 | 円錐内の**最小値ではなく、k 番目に小さい距離**を障害物までの距離とみなす（既定 k = 3） |
| 根拠 | 実機の前方円錐（±28.6°）には約 105 点入り、停止距離 0.425 m では 1 ビームの弧長が 3.7 mm。**幅 2 cm の実体なら 5 点以上に映る。**1 点で止めるのは過敏 |
| 有効点が k 未満のとき | **最小値に退避する**（LiDAR が壊れている場合に安全側へ倒すため） |
| 変えないもの | 円錐の角度・停止距離・スキャン途絶判定・死角マスク。**変えるのは「何点あれば障害物とみなすか」だけ** |

### 2.4 障害物リミッタは新機能である

現在の安全チェーンには「探知された方向には進まない」相当の機能が無い（`CL-X-3`）。
速度指令の多重化の**手前に置くリミッタ**を新設する必要がある。実装は詳細設計で扱う。

## 3. 速度と加減速

| 項目 | 方針 |
| --- | --- |
| ゾーン別の上限 | 場外 `v_max` ／ 試験場内 `v_slow`（[Spec-modes.md](Spec-modes.md) §7） |
| 場内を低速にする理由 | **納品する製品が置いてある**ため |
| 加減速 | **ゆっくり行う。**重心が高くなることが予想されるため |
| 実現層 | **ESP32 のファームウェアレベルでモータ出力の急変を抑える。**上位が急な指令を出しても機体側で鈍らせる |
| 前提 | **制動距離が長い前提で制御する** |

**「目標速度を鈍らせる」だけでは足りない（実機 2026-09-11）。**目標速度側にランプを掛けても、
速度制御の出力（PWM）そのものは急変できる。実機で手動ジョグの発進・停止を計測したところ、
中速・高速域でファームのランプ設定（1.5 m/s²）の約 2 倍の実加速度が出ていた
（最大は高速停止の 2.94 m/s²）。停止側が最も超過するのは、目標 0 で出力を即座にゼロへ
落とす経路があるため。

| 項目 | 方針 |
| --- | --- |
| 制限をかける場所 | 目標速度だけでなく**駆動出力そのものの変化率**を制限する |
| 例外 | **障害物・非常停止による停止指令は制限の対象外**。安全のための停止は鈍らせない |
| 保証の強さ | **数値での保証はしない**（ユーザー決定 2026-09-11）。「急変させない」ことを構造として持つのが目的 |

## 3.5 フォルトの 2 階級（[Spec-open.md](Spec-open.md) F-20）

原典と旧版の本設計書は `ESTOP` の契機を「UI ボタン**または重大フォルト**」と書きながら、
**「重大フォルト」がどれを指すのかをどこにも定義していなかった。**
定義が無いと、`LIDAR_LOST` が `ESTOP` へ行くのか §5 の再開フローへ行くのかが決まらず、
**「異常発生前のモードに戻る」（§5）が使えるかどうかが読者に判断できない。**

**決定: フォルトを 2 階級に分け、`ESTOP` へ落とすものを限定列挙する。**

| 階級 | 定義 | 該当するもの | 落ちる先 | 解除後 |
| --- | --- | --- | --- | --- |
| **回復フォルト** | **原因が解消すれば同じ作業を続けられる**もの | `LIDAR_LOST` ／ `ESP32_DISCONNECTED` ／ `PERSON_TRACKER_LOST` ／ 必須通信系統の断 | **モードは保持し、状態を `PAUSE` に落とす**（§5 の再開フローに乗る） | 元モードの `RUN` または `PAUSE`（§5.3） |
| **重大フォルト** | **原因が解消しても、そのまま続けると危険が残る**もの | 安全チェーン自身の異常（速度指令の多重化・障害物リミッタの故障）／ 駆動系の暴走を検知したとき／ 状態機械が不整合に陥ったとき／ **自己位置を見失ったとき（`LOCALIZATION_LOST`）** | **`ESTOP`** | **`IDLE` のみ**（§4.1） |

**`LOCALIZATION_LOST` を重大フォルトに入れる理由**: 自己位置が凍結しても
**LiDAR も ESP32 も生きているので回復フォルトの検出には引っかからず、機体は走り続ける。**
そのとき機体が持っている座標は現実とずれており、**地図上の経路をなぞる動作そのものが危険になる。**
原因（推定の破綻）が解消しても、**破綻していた間に進んだ分のずれは残る**ので、
同じ作業をそのまま続けさせてはいけない。復帰は `IDLE` からの再推定を経る。

**必須通信系統の断を重大フォルトに含めない**のが要点である。
含めると最も起きやすいフォルトが毎回 `ESTOP` に落ち、解除が `IDLE` のみになるので、
**§5 の再開フローと [Spec-modes.md](Spec-modes.md) §6 の「異常解決後の復帰」表が丸ごと使えなくなる。**
通信断で駆動が止まることは安全チェーンの層 2・層 3 が別途担保しているので、
モードまで畳む必要はない。

**回復フォルトで `IDLE` へ強制遷移させない理由**: 落とすと、画面はそのまま（例: 追従走行画面）で
ヘッダのモード表示だけ「待機」になり、[Spec-modes.md](Spec-modes.md) §1 の
「画面 1 : モード 1」対応が崩れる。**モードを保ったまま `PAUSE` にすれば、
駆動は層 3 が即時ゼロにしているので安全は変わらず、復帰先だけが素直になる。**

> **詳細設計への申し送り**: 現行 `mode_manager.cpp` は**フォルト発生時に動作系モードから
> `IDLE` へ強制遷移する**実装である。本決定はこれを変えるので、
> [Spec-modes.md](Spec-modes.md) §10 の差分表に載せてある。

### 3.5.0 `LOCALIZATION_LOST` を何で検知するか（ユーザー決定 2026-09-20）

§3.5 は `LOCALIZATION_LOST` を重大フォルトに列挙しながら、**何をもって「見失った」とするかを
定義していなかった。**3 つの根拠を**すべて**使う（A・B・C を採用）。

| 記号 | 検知するもの | 捕まえる状況 | 理由コード |
| --- | --- | --- | --- |
| **A** | **地図と機体をつなぐ補正が届かなくなる**（`map→odom` の配信が止まる） | 自己位置推定が止まった・固まった。**残り区間が無音でデッドレコニングに劣化する**（台帳 `W-02` の実害の半分） | `stale` |
| **C** | **自己位置推定のノードが居ない／死んだ** | 起動失敗・クラッシュ | `node_down` |
| **B′** | **オドメトリだけで推測した位置と、自己位置推定が出した位置が食い違う** | **補正が飛んだ。**経路を選ぶたび `map→odom` が数 m・100〜200°飛んだ不具合（2026-09-04 実機）はこれで鳴る | `jump` |
| ~~B~~ | ~~スキャンマッチの確からしさが低い~~ | **廃案**（下記「B を捨てた理由」） | — |

**C は A に含まれる**（プロセスが死ねば補正も凍る）が、**別に持つ**。検知が速く、
操作者に出す文言が変わるため（「推定が止まりました」と「推定が動いていません」は打つ手が違う）。

#### 出し方は既存の監視と同じ形にする

他の 8 つの監視対象はすべて**トピックの途絶**で判定している。これに揃える。

| 項目 | 方針 |
| --- | --- |
| 健全性の配信 | 自己位置推定の健全性を**1 つのトピックで出す**（`ok` と上表の理由コード） |
| 監視 | `safety_monitor` に `localization` を追加し、**そのトピックの途絶**と **`ok == false` の継続**の両方で発火する |
| 保持時間 | §3.5.1 と同じく、条件が続いたときだけ報告する（単発で撃たない） |
| 閾値 | `registry.yaml` に置く（`Spec.md` §5 SD-9。ノード内リテラルにしない） |

#### A が捕まえるのは「配信が止まる」であって「値が変わらない」ではない

**推定器は補正できていなくても同じ値を出し続ける**（`map→odom` を一定周期で配信し続ける）。
したがって A は「**届かなくなった**」ことしか見ない。**生きたまま補正をやめた状態は A では
捕まらない。**そのぶん C と重なるが、C（ノードの不在）より広い（プロセスは居るのに固まった、も入る）。
「生きたまま間違っていく」側は B′ と `O-e2` が担当する。

#### **使っていない間は監視しない**（これを忘れると誤発火する）

**自己位置推定を使っているモードでだけ効かせる。**教示（地図を作っている最中）、
`stage` が低くて地図が無い起動、手動走行では `map→odom` が無いのが正常なので、
そこで発火させてはいけない。

#### B（スキャンマッチの確からしさ）を捨てた理由（2026-09-20 実測）

**自己位置推定が出す共分散は、間違っているかどうかを表していない。**

Docker 内で合成した部屋（5m×4m ＋ 柱 2 本）で地図を作り、`odom` だけを 1.5 m ずらして
**「オドメトリの予測と実際が食い違う」**状態を作った。推定位置は真値から **1.3 m 以上**
ずれたまま走り続けたが、共分散は次のとおりだった。

| | 正常（40 件） | **ずれている間（26 件）** |
| --- | --- | --- |
| x の分散 中央値 | 0.00139 | **0.00134**（むしろ小さい） |
| 正常時の最大値を閾値にしたときの検出率 | — | **26 件中 6 件（23%）だけ。**しかも大半は飛んだ瞬間の 1 点 |

**77% は健全時と見分けがつかない。**閾値をどこに引いても検知器にならない。

これは既知の性質でもある —— Nav2 の資料は **「共分散は真の誤差ではない。低い共分散だけでは
正確さを保証しない」**と明記している。また **slam_toolbox はスキャンマッチのスコアも
「ロスト」診断も外部に出していない**（公開されているのは自己位置・地図・グラフ可視化と、
AMCL 互換の再初期化入力だけ）。

#### B′ —— オドメトリと自己位置推定の食い違いを見る

B の代わりに置く。**自動運転の Autoware が本番の診断で使っている考え方**と同じ。

> 短い周期ごとに、**①オドメトリだけで推測した位置**と**②自己位置推定が出した位置**を比べ、
> 食い違いが許容を超えたら異常とする。

この構成では自己位置推定は `map→odom` を足すだけなので、**食い違い ＝ `map→odom` の飛び**になる。
短期のオドメトリ（車輪＋ジャイロ）は信頼できるという前提に乗る。

| 項目 | 方針 |
| --- | --- |
| 比較の周期・許容 | `registry.yaml` に置く。周期 0.5 秒／**並進 1.0 m／回転 0.5 rad（約 29°）**（2026-09-21 に実走のデータで決め直した。下記「実走で分かったこと」） |
| 出すもの | 理由コード `jump` |
| **捕まえられないもの** | **補正が止まってオドメトリに追従するだけ**の状態（①と②が一致してしまう）。そこは A の担当 |

**実走で分かったこと（2026-09-21・誤りの訂正）**

当初は Autoware の既定（並進 0.11 m／回転 1°）を「出発点」に置き、**前提として「短期のオドメトリは信頼できる」と書いた。
この機体（クローラー）では成り立たなかった。**実機で走らせたところ、**走るたびに `jump` が出て重大フォルト
（＝非常停止）に落ちた**（走行中 170 点のうち 14% が超過、停止中でも 4 点）。

`map→odom` は、自己位置推定が**オドメトリのずれを引き戻す補正そのもの**である。クローラーは旋回中に
スリップし、オドメトリのヨーが実際とずれるので、**補正は階段状に大きく入る**のが正常な動作である。

| 0.5 秒あたりの `map→odom` の変化（走行中 170 点。約 5 分） | 並進 | 回転 |
| --- | --- | --- |
| 中央値 | 1.4 cm | 0.2° |
| p95 | 8.6 cm | 5.4° |
| p99 | 25.4 cm | 7.7° |
| **最大** | **37 cm**（その場旋回中） | **10.5°**（その場旋回中） |
| 停止中（408 点）の最大 | 8.4 cm | 3.7°（動きが止まったあとも補正が遅れて入る） |

**閾値は「正常な補正の最大の 2.5 倍程度」に置く**（並進 0.37 m → **1.0 m**、回転 10.5° → **0.5 rad（28.6°）**）。
この検知が捕まえたいのは**桁の違う飛び**であって、正常な補正ではない —— 実際に起きた不具合
（地図の読み直しが積み上がり、`map→odom` が**数 m・100〜200°**飛んだ件）はこの閾値を大きく超える。

**限界**: 記録は約 5 分・1 か所の床面のみ。**より滑る床・長い直進・高速旋回では正常な補正がもっと大きい可能性がある。**
閾値は実機で走行距離を伸ばしながら見直す。**「Autoware の既定を出発点にする」は別の構成（EKF と推測航法の比較）
の値であり、`map→odom` の変化には当てはめられない。**

#### まだ埋まらない穴 —— 「ゆっくり間違っていく」

**A・C・B′ をすべて実装しても、「更新も続き、飛びもしないが、少しずつ間違った場所にいる」は
検知できない。**上の実測が示したのはまさにこの状態である。

塞ぐには **`/scan` と地図の一致度を自前で測る**しかない（古典的には、スキャンの各点から
地図の最近傍点までの平均距離）。注意点も分かっている —— 地図に無い物（人・動く物）で
悪化するので外れ値を除く必要があり、局所解にはまると間違っていても良い値が出る。
**実機で閾値を決める必要があるため別の作業とする**（理由コード `low_confidence` を予約しておく）。

**この穴が空いていることを承知のうえで運用する。**教示再生は始点マーク運用（台帳 `W-01`）が
前提であり、操作者が同行して見ていることも前提である。

### 3.5.1 重大フォルトの発火には保持時間を課す（実機 2026-09-04）

実機で「一瞬でもエラーが出ると停止し、そこから復帰できない」が起きた。
安全監視のループ自身が一時的に遅れると、**複数の入力が同じ判定周期で同時に
タイムアウト超過に見える**（実機ログ: 2 種類のフォルトが同じ 1 ms に発火し、
**26 ms 後に両方とも解除**された。実体の途絶ではなく検知側の取りこぼし）。

| 項目 | 方針 |
| --- | --- |
| 対象 | **安全チェーン自身の異常**（多重化・リミッタの故障、状態機械の不整合）の系統 |
| 条件 | 条件が `critical_fault_hold_ms` **継続したときだけ**重大フォルトとして報告する |
| 変えないもの | 各入力のタイムアウト値そのもの。**判定のしきい値ではなく「何周期続いたか」だけを足す** |
| 対象外 | 回復フォルト（一時停止から正常に再開できるため猶予は要らない） |

### 3.5.2 重大フォルト起因の `ESTOP` からも元のモードへ戻れる（実機 2026-09-04）

§4.1 の「`ESTOP` からの復帰は `IDLE` のみ」は、**UI ボタン起因の `ESTOP`** を想定した規則だった。
フォルト起因にも同じ規則を当てると、**26 ms のフォルト 1 回で作業の最初からやり直し**になる
（再生中なら経路選択から。そこで再び大きな地図を読むので落ちやすさが再発する）。

| 項目 | 方針 |
| --- | --- |
| 復帰先 | **フォルト起因でも元のモードへ戻れる**（ユーザー決定 2026-09-04）。**フォルトの種類による除外は設けない** |
| 戻ったときの状態 | 元モードの **`PAUSE`（停止状態）**。走り出すには操作者がもう一度「走行」を押す |
| 依然として要求すること | フォルトが実際に消えていること・物理非常停止ボタンが解放されていること |
| 変えないもの | 物理非常停止ボタンと ESP32 ウォッチドッグ（600 ms） |

**遷移表の正本は [Spec-modes.md](Spec-modes.md) §3.1.1（`SM-3.1.1-11` 系）**。
UI 起因に限っていたガードからその限定を外すこと。

### 3.5.3 `DRIVE_RUNAWAY` は実測が新鮮なときだけ判定する（2026-09-21 決定・台帳 `W-06` の②）

`DRIVE_RUNAWAY`（駆動系の暴走）は、**指令した速度と車輪の実測速度が乖離した状態が続いたとき**に出す重大フォルトである。
当初は「実測の直近値」を鮮度を見ずに使っていたため、**実測の到着が遅れると「新しい指令 対 古い実測」を比べ続けて、
走り出すたびに誤発火した**（無線経由の時代。台帳 `W-06`。誤発火のせいで検知を無効化して運用してきた）。

| 項目 | 方針 |
| --- | --- |
| 判定する条件 | 実測が**新鮮**（最後に届いてから `runaway_feedback_stale_ms` 以内）なときだけ |
| **実測が古いあいだ** | **判定を凍結する。**保持時間を**進めも戻しもせず**、フォルトの状態も**変えない** |
| 一度も届いていないとき | 古いものとして扱う（＝判定しない。ESP32 の不在は `ESP32_DISCONNECTED` が担う） |
| 閾値 | `registry.yaml` に置く（`Spec.md` §5 SD-9）。**出発点 250 ms**。実機で詰める |

**「スキップして保持時間を戻す」ではなく「凍結」にする理由**: 戻すと、**本物の暴走が起きていて実測が断続的に途切れる**とき、
保持時間が永遠に溜まらず**暴走を見逃す**。凍結なら、古い実測を根拠にした**誤った累積は起きず**、
新鮮な実測が戻れば判定が続きから再開する。

**検知に穴が空かない根拠**: 実測が古いまま `esp32_timeout_ms` を超えれば `ESP32_DISCONNECTED`（回復フォルト。全停止して `PAUSE`）が、
ファームウェアの独立したウォッチドッグ（600 ms）がそれぞれ担う。凍結される窓は「`runaway_feedback_stale_ms` から
`esp32_timeout_ms` まで」の**有限の範囲**に限られる。

**閾値の根拠**: 2026-09-21 の実機計測（ESP32 をラズパイへシリアル直結・25 分・15,000 フレーム欠落ゼロ）で、
到着間隔は中央値 100 ms・p99 120.8 ms、最大 361〜480 ms、**500 ms 超は 0 件**
（[実機作業キュー.md](../../実機作業キュー.md) §4.0）。250 ms は p99 の 2 倍強で、`esp32_timeout_ms`（322 ms）より短い。
**ただし最大 480 ms は保持時間（`runaway_hold_ms` 500 ms）に 20 ms 差まで迫る**ため、この凍結が無いと
「戻すだけ」は安全側に倒せない。

**この決定だけでは `DRIVE_RUNAWAY` は有効にならない。**監視対象へ戻す（台帳 `W-06` ⑥）のは、
**駆動電源のある走行日に、指令と実速度の乖離を実際に検知できること・誤発火しないこと**を確かめてからにする。

## 4. 非常停止

### 4.1 2 系統ある

| | **UI 非常停止**（`ESTOP`） | **物理非常停止**（`CARRY`） |
| --- | --- | --- |
| 契機 | WebUI のボタン／重大フォルト | 機体の物理ボタン |
| 意味 | 「止めたい」 | **「人が押して運ぶ」＝手押しモード** |
| センサ系統 | 動かし続ける | **動かし続ける**（原典明記） |
| 画面 | 異常ウィンドウ | **解除方法を案内するウィンドウ** |
| 解除後 | **UI ボタン起因（重大フォルト無し）は再開ボタンで押下前のモードへ／「メニューへ」で `IDLE`。重大フォルト起因は `IDLE` のみ**（2026-09-01 変更。[Spec-modes.md](Spec-modes.md) §3.1.1 `SM-3.1.1-11`） | **再開ボタンで押下前のモードへ戻れる** |

### 4.2 UI 非常停止ボタンの絶対要件

| 要件 | 内容 |
| --- | --- |
| 常時表示 | ヘッダに常設し、**何にも覆われない**（[Spec-webui.md](Spec-webui.md) §1.1（重なり順）） |
| 常時動作 | **どんなときでも動作する。**異常ウィンドウが開いていても押せる。**例外は `CARRY`（手押し）中の 1 つだけ**（下記） |
| スクロールで隠れない | 画面はヘッダ固定・本文のみスクロール。**過去にスクロールで非常停止が画面外に出た事例が安全上の欠陥として記録されている** |
| 解除の配置 | 「押す」と「解除」を**画面の上下に離して**置き、色と形も変える。誤って解除しないため |

**唯一の例外: `CARRY`（手押し）中は UI 非常停止を受け付けない**
（[Spec-modes.md](Spec-modes.md) §4.1 ／ [Spec-open.md](Spec-open.md) F-26）。

**これは安全側の例外である。**物理ボタンが押されている `CARRY` 中は、
**すでに駆動が物理的に切れており、UI で止めるべきものが残っていない。**
受け付けると「押下前のモード」が `CARRY` に上書きされ、解除後の復帰先が壊れるほうが害が大きい。

**ボタン自体は隠さない。**ヘッダに出したまま、押しても効かないことが分かる見た目にし、
手押しウィンドウ（W-2）に「駆動は既に切れています」と出す。
**「見えているのに効かない」を、説明なしに作らないこと。**

**内部動作と二重化**（[Spec-open.md](Spec-open.md) F-39・旧 `O-d7`。詳細設計で決着）:

| 項目 | 決めたこと |
| --- | --- |
| 経路 | **UI ボタンは安全監視を経由する**（層 3）。駆動へ直結しない |
| 表し方 | **押下は継続送信**で表し、**押下側にラッチ**する（通信が途切れて「解除」が落ちても解除されない） |
| 二重化 | 物理と UI の集約は **「どちらかが押されていれば非常停止」の 1 か所**で行う。2 系統を別々に扱わない |
| 独立性 | **層 1（物理）は UI の状態に一切依存しない。**UI が落ちても物理ボタンは効く |

**残る宿題**: 押下側にラッチする以上、**WebUI が押下中に落ちると UI からは解除できない。**
UI に依存しない解除経路が要るかは詳細設計で未決。

### 4.3 手押しモードの流れ

| 順 | 状態 | 画面 |
| --- | --- | --- |
| 1 | 物理ボタンが押された | 「手押しモードです」＋**解除方法の案内**を表示 |
| 2 | 押されている間 | センサ系統は動作継続。走行は不可 |
| 3 | 解除された | **「再開」ボタン**を表示 |
| 4 | 再開を押す | **押下前のモード**へ戻る |
| 5 | 再開を押さない | `IDLE` に留まる |

**起動時に既に押されていた場合**（`CL-B-6`）: 起動シーケンスの中で検出し、
「非常停止ボタンが押されています。解除してください」と案内する。解除するまで運用に入れない
（→ [Spec-ops.md](Spec-ops.md)）。

## 5. 異常ウィンドウ

### 5.1 ライフサイクル

```
異常発生
   │
   ▼
[ 異常ウィンドウを表示 ] ──試験員が「非表示」──> [ ヘッダにバッジ表示 ]
   │                                                      │
   │ <──────────────── 「再表示」──────────────────────────┘
   │
   │ 異常が解決した
   ▼
[ 同じウィンドウが「再開しますか」に変わる ]
   │
   ├── [ はい ]  ──> 異常発生前のモードへ戻り、走行を再開する（RUN）
   ├── [ いいえ ] ──> 異常発生前のモードへ戻るが、一時停止のまま（PAUSE）
   └── [ 確認 ]   ──> 1 択。走行は再開しないが、モードは戻す（PAUSE）
                       ※モード自体を続けられない異常のときだけ IDLE へ
```

**「いいえ」でも待機（`IDLE`）には戻さない**（[Spec-open.md](Spec-open.md) U-8）。
対象選択・経路指定・記録内容を選び直させないためである。
方式をやめたいときは異常とは関係なく「終了」を押す。

### 5.2 規則

| 項目 | 仕様 |
| --- | --- |
| 表示位置 | 画面の上に重ねる。**ただしヘッダの下**（ヘッダには絶対に被さらない） |
| 非表示 | **解決していなくても試験員が非表示にできる。**非表示中はヘッダにバッジが出る |
| 再表示 | バッジをタップすればいつでも戻せる |
| 解決時 | **自動で閉じる。**そのうえで再開するか問う |
| ブラウザ標準ダイアログ | **使わない**（`alert` / `confirm` はヘッダより上に出てしまうため） |

**「自動で閉じ、再開するか問う」の解釈**（`E-5`）:
**同じウィンドウが再開確認に変わる。**別ウィンドウを出し直さない。
異常の内容と再開の可否を続けて読めるほうが分かりやすいため。

### 5.3 選択肢の出し分け

| 状況 | 選択肢 | 復帰先 |
| --- | --- | --- |
| 走行を自動で再開できる | **はい／いいえ** | 元モードの `RUN` ／ 元モードの `PAUSE` |
| **復帰後のモードが手動操作になる** | **確認**（1 択） | 元モードの `PAUSE`（人が改めて操作する） |
| **モード自体を続けられない** | **確認**（1 択） | `IDLE`。未保存の記録は保存可否を問う |
| **その異常でモードが止まらない** | ウィンドウを出さず**案内ウィンドウ（W-3）だけ** | モードも状態も変えない |

**最後の行の実例**: `PREP`（試験準備）中の人物追跡ロスト。
登録操作は受け付けなくなるが地図作成は続くので、異常ウィンドウで作業を止めない
（[Spec-open.md](Spec-open.md) C-15 ／ [Spec-modes.md](Spec-modes.md) §5）。

**`E-6` の解釈**: 「再開先が手動操作の場合」は
**①復帰後のモードが手動操作になる場合**と解釈する（②復帰に人の手操作が要る場合、ではない）。
手動走行は人が改めて始めるものであり、自動で「再開」する対象にならないため。
ただし**モードは戻す**（待機には戻さない）。

モード別の復帰先は [Spec-modes.md](Spec-modes.md) §6 の表を正とする。

### 5.4 できるだけ再開できるように作る

原典の方針。**モードと状態を分けている**（[Spec-modes.md](Spec-modes.md) §1）のはこのためで、
異常で止まっても対象選択・経路指定が保持されるので、多くの場合そのまま再開できる。

## 6. 通信断

### 6.1 停止する条件

| 条件 | 挙動 |
| --- | --- |
| **必須通信系統**（ESP32 ／ RaspberryPi4(LiDAR) ／ PC）のいずれかが切れた | **停止する。モードは保持し、状態を `PAUSE` に落とす**（§3.5 の回復フォルト） |
| **実際に操作に使われていたタブレット**が切れた | **停止する**（同じく `PAUSE`） |
| 接続されていただけのタブレット | 停止しない |

**`IDLE` へ強制遷移させない**（[Spec-open.md](Spec-open.md) F-20）。
必須通信系統の断は §3.5 の**回復フォルト**であり、**`ESTOP` にも `IDLE` にも落とさない。**
駆動を止めるのは層 2・層 3 であって、モードを畳んでも安全は増えない。
`PAUSE` に留めておくほうが、原因が解消したときに §5 の再開フローへそのまま乗る。
**`PAUSE` を持たない 3 モード**（`IDLE` / `OPCHECK` / `CALIB`）の扱いは
[Spec-modes.md](Spec-modes.md) §3.0-② に従う。

### 6.2 「使用されていた」の判定（`E-7`）

原典は判定基準を書いていない。次のように定める。

```
その端末から最後にメッセージが届いてから tablet_active_window_s 以内、
かつ WebUI が前面にある（操作画面が表示されている）なら「使用中」
```

**複数端末が使用中の場合は、そのいずれかが切れたら停止する**（誰が操作していたか特定できないため安全側に倒す）。

**判定の基準は「操作したか」ではなく「見ているか」である（ユーザー決定 2026-09-04）。**
当初は「最後の操作（ボタン押下・スティック操作）から窓の内側」と定めていたが、実機で
**走行中に操作者が見るのはロボットであってタブレットではない**ため、30 秒ごとに画面へ
触れという要求が用途に合わなかった（画面をスクロールすると復帰する、という症状になる）。

| 端末の状況 | 判定 |
| --- | --- |
| WebUI が前面にあり、通信が生きている | **使用中**（触っていなくてよい） |
| 画面を消す・別のアプリに切り替える | 使用中でない → 停止 |
| 端末が落ちる・回線が切れる（メッセージが途絶） | 使用中でない → 停止 |

窓の長さ（`tablet_active_window_s`）は変えない。

### 6.2.1 止まった理由を必ず画面に出す（実機 2026-09-04）

在席が確認できないと速度上限が 0 になるが、これは**フォルトでも一時停止でもない**ため、
当初は画面にもログにも何も出なかった。**操作者に理由が分からないまま機体が止まる**のは
禁止する。

| 項目 | 方針 |
| --- | --- |
| 出す理由 | 在席未確認／障害物／死角未校正／フォルト |
| 出す条件 | **機体が走るはずのときだけ**。走らせていない間は速度指令が無いのが正常で、常時出すと画面を覆い続ける |
| 除外 | 「指令が古い」だけの状態は理由に含めない（操作者に打つ手が無く、走り出し直後に一瞬出て点滅するため） |
| 表示の大きさ | **1 行**。本文を押し下げず、隠す面積を最小にする |

### 6.3 Wi-Fi AP は単一障害点（[Spec-open.md](Spec-open.md) C-01）

すべての機器の通信を AP が中継しており、**PC は機体に載っていない（有線接続もしない）**。
AP が落ちれば必須通信系統の 3 者がすべて同時に切れる。

| 項目 | 扱い |
| --- | --- |
| 必須通信系統の定義 | **3 者**（ESP32 ／ RaspberryPi4 ／ PC）。AP は含めない |
| 理由 | AP は通信の相手ではなく通信路。AP 障害は 3 者全滅として検出できるので監視上は等価 |
| 表示 | **疎通確認画面とヘッダで「Wi-Fi AP ＝単一障害点」であることを明示する** |
| フォールバック | **手押し**（物理ボタンを押して人が運ぶ）。実装ゼロで成立する正式なフォールバックとして明記する |

## 7. 「待つ」ときの打ち切り方針（[Spec-open.md](Spec-open.md) F-11）

原典は「原則停止する」としか書かず、停止したあと待ち続けるのか打ち切るのかを決めていない。
そのため詳細側で待ちの種類ごとに別々の既定が採られていた。**全体規則として次を置く。**

| 待ちの種類 | タイムアウト | 例 | 理由 |
| --- | --- | --- | --- |
| **人が動くのを待つ** | **する** | 呼び寄せの退避待ち／平面認識登録の退避待ち | 人は戻ってこられる。中止して操作をやり直せばよい。永久に発進しない状態を作らない |
| **経路が通れるようになるのを待つ** | **しない** | 試験場内 Nav2 が塞がれた／障害物で停止 | 勝手に迂回するより待つほうが安全。試験員が指示したときだけ再検索する |
| **機器が繋がるのを待つ** | **する**（起動時） | 起動時の疎通確認 | 一定時間で制御系を再起動する（→ [Spec-ops.md](Spec-ops.md)） |

## 9. 安全は KPI ではなく故障注入で検証する

**「接触 0 件」は数えて確かめるものではない。意図的に壊して止まることを確かめる。**

| 検証項目 | 方法 | 合格条件 |
| --- | --- | --- |
| 障害物リミッタ | 意図的に障害物へ向けて走らせる | 停止する。**後退方向も試す**（`CL-X-4`） |
| 非常停止 | 走行中に押す | 停止する |
| **通信断 → フォルト検知** | LiDAR / ESP32 の通信を切る | **`lidar_timeout_ms` / `esp32_timeout_ms` 以内**にフォルトが立つ（現状 2000 ms。**要引き直し** → §2.2） |
| **フォルト検知 → 停止** | 上と同じ試験の**続き**を測る | フォルトが立ってから **100 ms 以内**に速度指令が 0 |
| 呼び寄せの退避待ち | 退かずに待つ | **発進しない** → **タイムアウトで中止する** |
| ESP32 ウォッチドッグ | ROS2 側を落とす | **600 ms 以内**に停止する |
| 人検知 OFF とフォルトの区別 | 意図的に人物追跡を OFF にする | **フォルトにならない・強制遷移しない**（[Spec-modes.md](Spec-modes.md) §5.1） |
| 物理ボタン起動時押下 | 押したまま起動する | 運用に入れず、解除を案内する |

**「フォルト → 停止」を 2 行に分けた理由**（[Spec-open.md](Spec-open.md) F-21）:
1 行で「通信を切ってから 100 ms 以内に速度指令が 0」と書くと、
**現状の `lidar_timeout_ms` = 2000 ms では正常な実装でも必ず不合格になる。**
100 ms は安全チェーンの層 3 の応答時間（§1）であって、通信断からの合計時間ではない。
**測るべき時計が 2 つある**ので、試験も 2 つに分ける。
合計（通信断 → 停止）が実際の危険量であり、**§2.2 の「タイムアウトまでに 1.4 m 走る」がそれである。**

## 10. 開発モードの安全境界

開発モードでは**選択した特定の警告を無視して動作させられる**（機器未接続・バッテリー電圧低下など）。
**暴走する危険を承知の上で開くモード。**

| 無視できるもの | 無視できないもの |
| --- | --- |
| 機器が接続されていない警告 | **物理非常停止ボタン** |
| バッテリー電圧低下の警告 | **ESP32 のウォッチドッグ** |
| 始業点検の総合ステータス NG | **UI 非常停止ボタン** |
| 必須通信系統の不通による運用開始の禁止 | **自律系の障害物停止** |

**安全チェーンの層 1・2 は開発モードでも無効化できない。**
層 3・4 のうち「警告」に類するものだけを無視できる。

**開発段階では ROS 側からも有効にできる**（2026-09-20 ユーザー決定。[Spec-webui.md](Spec-webui.md) §5.1）。
検証を行う実装管理担当が WebUI を開かずに使えるようにするため。
**1 点だけ緩む**: 物理 E-Stop の状態が**まだ分からない間**（ESP32 未接続で一度も届いていない）、
開発モードは運用開始を通す。**押されていると分かっている間は開発モードでも止める**ので、
押されたまま走り出すことはない（[Spec-webui.md](Spec-webui.md) §5.1「物理 E-Stop の扱い」）。

**それ以外の境界は動かさない** —— `dev_mode` を `safety_monitor` と `obstacle_limiter` に
**渡さない**ことで構造的に保証する（[DetailedDesign-names.md](../detailed/DetailedDesign-names.md) §1.3）。
両ノードが値を知らなければ、実装を間違えても無効化は起こらない。

**未確定**（[Spec-open.md](Spec-open.md) O-d6）: 誰が有効化できるか（権限）、
通常運用中に誤って有効化されないための対策。**通常運用に入る直前に決める**
（ユーザー決定 2026-09-20。開発段階では制限をかけない）。
