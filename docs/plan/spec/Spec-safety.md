# 安全と異常時の扱い

[Spec.md](Spec.md) の詳細。**目標 G1（人・物への接触 0 件、意図しない挙動 0 件）を担保する仕組み。**

> **G1 は他のすべてに優先する。G1 を犠牲にして G2〜G5 を満たしてはいけない。**

---

## 1. 安全チェーンの階層

止める仕組みを 4 層に分け、**上位が下位の故障に依存しない**ようにする。

| 層 | 仕組み | 反応時間 | 依存 |
| --- | --- | --- | --- |
| **1** | **物理非常停止ボタン** | 即時 | 何にも依存しない。押されている間は駆動が切れる |
| **2** | **ESP32 のウォッチドッグ** | **600 ms 以内** | ROS2 が落ちても効く。ESP32 単体で成立 |
| **3** | **安全監視の非常停止・フォルトロック** | **100 ms 以内** | PC 上。モード管理の処理を待たずに速度指令をゼロにする |
| **4** | **モード管理の強制遷移** | 上位が止めた後 | 動作系モードから `IDLE` へ落とす |

**設計上の不変ルール**: 速度指令は必ず優先度つきの多重化を経由する。
どのノードも駆動へ直接指令してはいけない。
安全監視の出力が最上位の優先度を持ち、**モード管理の処理を待たずに**モーターをゼロにする。

## 2. 障害物への反応

### 2.1 方式ごとの扱い（[Spec-open.md](Spec-open.md) C-11 / U-2）

| 対象 | 挙動 | 無効化 |
| --- | --- | --- |
| **自律系**（追従／教示（追従）／教示再生／ライン誘導走行／電子リード走行／試験場内 Nav2） | **停止する** | **不可** |
| **手動系**（手動走行／教示（手動）／ジョグ介入）・**場外** | **警告のみ。**自動ブレーキは既定 OFF | 試験員が任意 ON にできる |
| **手動系・試験場内** | 自動ブレーキ **既定 ON** | 試験員が OFF にできる（**既定であって固定ではない**） |

**停止したあと**は、人が手動操作で避けるか、障害物をどける。
**自動で迂回しない。走行開始時に決定した経路を逸脱しない。**

### 2.2 停止距離の決め方

```
制動距離 = v² / (2a) + v × t_遅延
停止判定距離 = 制動距離 + 余裕
```

`a`（実測の制動加速度）が決まるまで、`obstacle_check_distance_m` /
`lidar_timeout_ms` / `v_max` / 追従の停止距離は**すべて暫定値**である
（[Spec-params.md](Spec-params.md)、[Spec-open.md](Spec-open.md) O-c1）。

**現状値の危険性**（要引き直し）:

| 項目 | 現状値 | 計画 `v_max` = 0.7 m/s での意味 |
| --- | --- | --- |
| `obstacle_check_distance_m` | 0.45 m | **不足**（設定上の制動距離だけで 0.49 m） |
| `lidar_timeout_ms` / `esp32_timeout_ms` | 2000 ms | タイムアウトまでに **1.4 m 走る** |

### 2.3 後退方向は LiDAR の死角（`CL-X-4`）

360° LiDAR でも機体構造物のマスクにより後方に死角が生じる。
**手動ジョグでぶつかるのはここ**である。

| 対策 | 内容 |
| --- | --- |
| 後退速度 | **前進よりさらに落とす**（`v_reverse` < `v_slow`） |
| 表示 | 後退中は画面に「後方は死角があります」と常時表示する |
| 検証 | 障害物リミッタの故障注入試験で**後退方向も必ず試す**（`CL-X-3` / `CL-X-4`） |

### 2.4 障害物リミッタは新機能である

現在の安全チェーンには「探知された方向には進まない」相当の機能が無い（`CL-X-3`）。
速度指令の多重化の**手前に置くリミッタ**を新設する必要がある。実装は詳細設計で扱う。

## 3. 速度と加減速

| 項目 | 方針 |
| --- | --- |
| ゾーン別の上限 | 場外 `v_max` ／ 試験場内 `v_slow`（[Spec-modes.md](Spec-modes.md) §7） |
| 場内を低速にする理由 | **納品する製品が置いてある**ため |
| 加減速 | **ゆっくり行う。**重心が高くなることが予想されるため |
| 実現層 | **ESP32 のファームウェアレベルでモータ出力の急変を抑える。**上位が急な指令を出しても機体側で鈍らせる |
| 前提 | **制動距離が長い前提で制御する** |

## 3.5 フォルトの 2 階級（[Spec-open.md](Spec-open.md) F-20）

原典と旧版の本設計書は `ESTOP` の契機を「UI ボタン**または重大フォルト**」と書きながら、
**「重大フォルト」がどれを指すのかをどこにも定義していなかった。**
定義が無いと、`LIDAR_LOST` が `ESTOP` へ行くのか §5 の再開フローへ行くのかが決まらず、
**「異常発生前のモードに戻る」（§5）が使えるかどうかが読者に判断できない。**

**決定: フォルトを 2 階級に分け、`ESTOP` へ落とすものを限定列挙する。**

| 階級 | 定義 | 該当するもの | 落ちる先 | 解除後 |
| --- | --- | --- | --- | --- |
| **回復フォルト** | **原因が解消すれば同じ作業を続けられる**もの | `LIDAR_LOST` ／ `ESP32_DISCONNECTED` ／ `PERSON_TRACKER_LOST` ／ 必須通信系統の断 | **モードは保持し、状態を `PAUSE` に落とす**（§5 の再開フローに乗る） | 元モードの `RUN` または `PAUSE`（§5.3） |
| **重大フォルト** | **原因が解消しても、そのまま続けると危険が残る**もの | 安全チェーン自身の異常（速度指令の多重化・障害物リミッタの故障）／ 駆動系の暴走を検知したとき／ 状態機械が不整合に陥ったとき | **`ESTOP`** | **`IDLE` のみ**（§4.1） |

**必須通信系統の断を重大フォルトに含めない**のが要点である。
含めると最も起きやすいフォルトが毎回 `ESTOP` に落ち、解除が `IDLE` のみになるので、
**§5 の再開フローと [Spec-modes.md](Spec-modes.md) §6 の「異常解決後の復帰」表が丸ごと使えなくなる。**
通信断で駆動が止まることは安全チェーンの層 2・層 3 が別途担保しているので、
モードまで畳む必要はない。

**回復フォルトで `IDLE` へ強制遷移させない理由**: 落とすと、画面はそのまま（例: 追従走行画面）で
ヘッダのモード表示だけ「待機」になり、[Spec-modes.md](Spec-modes.md) §1 の
「画面 1 : モード 1」対応が崩れる。**モードを保ったまま `PAUSE` にすれば、
駆動は層 3 が即時ゼロにしているので安全は変わらず、復帰先だけが素直になる。**

> **詳細設計への申し送り**: 現行 `mode_manager.cpp` は**フォルト発生時に動作系モードから
> `IDLE` へ強制遷移する**実装である。本決定はこれを変えるので、
> [Spec-modes.md](Spec-modes.md) §10 の差分表に載せてある。

## 4. 非常停止

### 4.1 2 系統ある

| | **UI 非常停止**（`ESTOP`） | **物理非常停止**（`CARRY`） |
| --- | --- | --- |
| 契機 | WebUI のボタン／重大フォルト | 機体の物理ボタン |
| 意味 | 「止めたい」 | **「人が押して運ぶ」＝手押しモード** |
| センサ系統 | 動かし続ける | **動かし続ける**（原典明記） |
| 画面 | 異常ウィンドウ | **解除方法を案内するウィンドウ** |
| 解除後 | **`IDLE` のみ** | **再開ボタンで押下前のモードへ戻れる** |

### 4.2 UI 非常停止ボタンの絶対要件

| 要件 | 内容 |
| --- | --- |
| 常時表示 | ヘッダに常設し、**何にも覆われない**（[Spec-webui.md](Spec-webui.md) §1.1（重なり順）） |
| 常時動作 | **どんなときでも動作する。**異常ウィンドウが開いていても押せる。**例外は `CARRY`（手押し）中の 1 つだけ**（下記） |
| スクロールで隠れない | 画面はヘッダ固定・本文のみスクロール。**過去にスクロールで非常停止が画面外に出た事例が安全上の欠陥として記録されている** |
| 解除の配置 | 「押す」と「解除」を**画面の上下に離して**置き、色と形も変える。誤って解除しないため |

**唯一の例外: `CARRY`（手押し）中は UI 非常停止を受け付けない**
（[Spec-modes.md](Spec-modes.md) §4.1 ／ [Spec-open.md](Spec-open.md) F-26）。

**これは安全側の例外である。**物理ボタンが押されている `CARRY` 中は、
**すでに駆動が物理的に切れており、UI で止めるべきものが残っていない。**
受け付けると「押下前のモード」が `CARRY` に上書きされ、解除後の復帰先が壊れるほうが害が大きい。

**ボタン自体は隠さない。**ヘッダに出したまま、押しても効かないことが分かる見た目にし、
手押しウィンドウ（W-2）に「駆動は既に切れています」と出す。
**「見えているのに効かない」を、説明なしに作らないこと。**

**未確定**（[Spec-open.md](Spec-open.md) O-d7）: UI ボタンを押したときの内部動作（安全監視との接続）と、
物理ボタンとの二重化の扱い。設計としては「安全チェーン層 3 に入る」とだけ決め、実装は詳細設計へ。

### 4.3 手押しモードの流れ

| 順 | 状態 | 画面 |
| --- | --- | --- |
| 1 | 物理ボタンが押された | 「手押しモードです」＋**解除方法の案内**を表示 |
| 2 | 押されている間 | センサ系統は動作継続。走行は不可 |
| 3 | 解除された | **「再開」ボタン**を表示 |
| 4 | 再開を押す | **押下前のモード**へ戻る |
| 5 | 再開を押さない | `IDLE` に留まる |

**起動時に既に押されていた場合**（`CL-B-6`）: 起動シーケンスの中で検出し、
「非常停止ボタンが押されています。解除してください」と案内する。解除するまで運用に入れない
（→ [Spec-ops.md](Spec-ops.md)）。

## 5. 異常ウィンドウ

### 5.1 ライフサイクル

```
異常発生
   │
   ▼
[ 異常ウィンドウを表示 ] ──試験員が「非表示」──> [ ヘッダにバッジ表示 ]
   │                                                      │
   │ <──────────────── 「再表示」──────────────────────────┘
   │
   │ 異常が解決した
   ▼
[ 同じウィンドウが「再開しますか」に変わる ]
   │
   ├── [ はい ]  ──> 異常発生前のモードへ戻り、走行を再開する（RUN）
   ├── [ いいえ ] ──> 異常発生前のモードへ戻るが、一時停止のまま（PAUSE）
   └── [ 確認 ]   ──> 1 択。走行は再開しないが、モードは戻す（PAUSE）
                       ※モード自体を続けられない異常のときだけ IDLE へ
```

**「いいえ」でも待機（`IDLE`）には戻さない**（[Spec-open.md](Spec-open.md) U-8）。
対象選択・経路指定・記録内容を選び直させないためである。
方式をやめたいときは異常とは関係なく「終了」を押す。

### 5.2 規則

| 項目 | 仕様 |
| --- | --- |
| 表示位置 | 画面の上に重ねる。**ただしヘッダの下**（ヘッダには絶対に被さらない） |
| 非表示 | **解決していなくても試験員が非表示にできる。**非表示中はヘッダにバッジが出る |
| 再表示 | バッジをタップすればいつでも戻せる |
| 解決時 | **自動で閉じる。**そのうえで再開するか問う |
| ブラウザ標準ダイアログ | **使わない**（`alert` / `confirm` はヘッダより上に出てしまうため） |

**「自動で閉じ、再開するか問う」の解釈**（`E-5`）:
**同じウィンドウが再開確認に変わる。**別ウィンドウを出し直さない。
異常の内容と再開の可否を続けて読めるほうが分かりやすいため。

### 5.3 選択肢の出し分け

| 状況 | 選択肢 | 復帰先 |
| --- | --- | --- |
| 走行を自動で再開できる | **はい／いいえ** | 元モードの `RUN` ／ 元モードの `PAUSE` |
| **復帰後のモードが手動操作になる** | **確認**（1 択） | 元モードの `PAUSE`（人が改めて操作する） |
| **モード自体を続けられない** | **確認**（1 択） | `IDLE`。未保存の記録は保存可否を問う |
| **その異常でモードが止まらない** | ウィンドウを出さず**案内ウィンドウ（W-3）だけ** | モードも状態も変えない |

**最後の行の実例**: `PREP`（試験準備）中の人物追跡ロスト。
登録操作は受け付けなくなるが地図作成は続くので、異常ウィンドウで作業を止めない
（[Spec-open.md](Spec-open.md) C-15 ／ [Spec-modes.md](Spec-modes.md) §5）。

**`E-6` の解釈**: 「再開先が手動操作の場合」は
**①復帰後のモードが手動操作になる場合**と解釈する（②復帰に人の手操作が要る場合、ではない）。
手動走行は人が改めて始めるものであり、自動で「再開」する対象にならないため。
ただし**モードは戻す**（待機には戻さない）。

モード別の復帰先は [Spec-modes.md](Spec-modes.md) §6 の表を正とする。

### 5.4 できるだけ再開できるように作る

原典の方針。**モードと状態を分けている**（[Spec-modes.md](Spec-modes.md) §1）のはこのためで、
異常で止まっても対象選択・経路指定が保持されるので、多くの場合そのまま再開できる。

## 6. 通信断

### 6.1 停止する条件

| 条件 | 挙動 |
| --- | --- |
| **必須通信系統**（ESP32 ／ RaspberryPi4(LiDAR) ／ PC）のいずれかが切れた | **停止する。**動作系モードは `IDLE` へ強制遷移 |
| **実際に操作に使われていたタブレット**が切れた | **停止する** |
| 接続されていただけのタブレット | 停止しない |

### 6.2 「使用されていた」の判定（`E-7`）

原典は判定基準を書いていない。次のように定める。

```
最後の操作（ボタン押下・スティック操作）から tablet_active_window_s 以内であれば「使用中」
```

画面を開いているだけ・見ているだけは含まない。
**複数端末が使用中の場合は、そのいずれかが切れたら停止する**（誰が操作していたか特定できないため安全側に倒す）。

### 6.3 Wi-Fi AP は単一障害点（[Spec-open.md](Spec-open.md) C-01）

すべての機器の通信を AP が中継しており、**PC は機体に載っていない（有線接続もしない）**。
AP が落ちれば必須通信系統の 3 者がすべて同時に切れる。

| 項目 | 扱い |
| --- | --- |
| 必須通信系統の定義 | **3 者**（ESP32 ／ RaspberryPi4 ／ PC）。AP は含めない |
| 理由 | AP は通信の相手ではなく通信路。AP 障害は 3 者全滅として検出できるので監視上は等価 |
| 表示 | **疎通確認画面とヘッダで「Wi-Fi AP ＝単一障害点」であることを明示する** |
| フォールバック | **手押し**（物理ボタンを押して人が運ぶ）。実装ゼロで成立する正式なフォールバックとして明記する |

## 7. 「待つ」ときの打ち切り方針（[Spec-open.md](Spec-open.md) F-11）

原典は「原則停止する」としか書かず、停止したあと待ち続けるのか打ち切るのかを決めていない。
そのため詳細側で待ちの種類ごとに別々の既定が採られていた。**全体規則として次を置く。**

| 待ちの種類 | タイムアウト | 例 | 理由 |
| --- | --- | --- | --- |
| **人が動くのを待つ** | **する** | 呼び寄せの退避待ち／平面認識登録の退避待ち | 人は戻ってこられる。中止して操作をやり直せばよい。永久に発進しない状態を作らない |
| **経路が通れるようになるのを待つ** | **しない** | 試験場内 Nav2 が塞がれた／障害物で停止 | 勝手に迂回するより待つほうが安全。試験員が指示したときだけ再検索する |
| **機器が繋がるのを待つ** | **する**（起動時） | 起動時の疎通確認 | 一定時間で制御系を再起動する（→ [Spec-ops.md](Spec-ops.md)） |

## 9. 安全は KPI ではなく故障注入で検証する

**「接触 0 件」は数えて確かめるものではない。意図的に壊して止まることを確かめる。**

| 検証項目 | 方法 | 合格条件 |
| --- | --- | --- |
| 障害物リミッタ | 意図的に障害物へ向けて走らせる | 停止する。**後退方向も試す**（`CL-X-4`） |
| 非常停止 | 走行中に押す | 停止する |
| **通信断 → フォルト検知** | LiDAR / ESP32 の通信を切る | **`lidar_timeout_ms` / `esp32_timeout_ms` 以内**にフォルトが立つ（現状 2000 ms。**要引き直し** → §2.2） |
| **フォルト検知 → 停止** | 上と同じ試験の**続き**を測る | フォルトが立ってから **100 ms 以内**に速度指令が 0 |
| 呼び寄せの退避待ち | 退かずに待つ | **発進しない** → **タイムアウトで中止する** |
| ESP32 ウォッチドッグ | ROS2 側を落とす | **600 ms 以内**に停止する |
| 人検知 OFF とフォルトの区別 | 意図的に人物追跡を OFF にする | **フォルトにならない・強制遷移しない**（[Spec-modes.md](Spec-modes.md) §5.1） |
| 物理ボタン起動時押下 | 押したまま起動する | 運用に入れず、解除を案内する |

**「フォルト → 停止」を 2 行に分けた理由**（[Spec-open.md](Spec-open.md) F-21）:
1 行で「通信を切ってから 100 ms 以内に速度指令が 0」と書くと、
**現状の `lidar_timeout_ms` = 2000 ms では正常な実装でも必ず不合格になる。**
100 ms は安全チェーンの層 3 の応答時間（§1）であって、通信断からの合計時間ではない。
**測るべき時計が 2 つある**ので、試験も 2 つに分ける。
合計（通信断 → 停止）が実際の危険量であり、**§2.2 の「タイムアウトまでに 1.4 m 走る」がそれである。**

## 10. 開発モードの安全境界

開発モードでは**選択した特定の警告を無視して動作させられる**（機器未接続・バッテリー電圧低下など）。
**暴走する危険を承知の上で開くモード。**

| 無視できるもの | 無視できないもの |
| --- | --- |
| 機器が接続されていない警告 | **物理非常停止ボタン** |
| バッテリー電圧低下の警告 | **ESP32 のウォッチドッグ** |
| 始業点検の総合ステータス NG | **UI 非常停止ボタン** |
| 必須通信系統の不通による運用開始の禁止 | **自律系の障害物停止** |

**安全チェーンの層 1・2 は開発モードでも無効化できない。**
層 3・4 のうち「警告」に類するものだけを無視できる。

**未確定**（[Spec-open.md](Spec-open.md) O-d6）: 誰が有効化できるか（権限）、
通常運用中に誤って有効化されないための対策。
