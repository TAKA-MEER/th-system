## 1. 対象

配電盤上部を確認するロボットのうち、**移動に関わるすべて**。
移動機構だけでなく、それを運用するための WebUI・始業点検・校正・異常時の扱いを含む。

**範囲外**: カメラ昇降のピッチ・ヨー・高さ（別担当）／盤前の低速並進／ライン誘導走行のマップ編集画面。

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| 機体 | 走行部（CuGoV3 + ESP32 + LiDAR + RaspberryPi4）を載せた車体本体。PC は含まない |
| 試験員 | 機体を運用する人。**原則 1 人で全作業が完結する**ことを目標にする |
| 保管場所 | 機体を置いておく場所。教示の起点であり、教示再生の起点でもある |
| 試験場 | 配電盤があり、確認作業を行う場所。**納品前の製品が置かれている** |
| 待機場所 | 試験場内で機体が待つ場所。試験場内地図の初期位置となる |
| 走行方式 | 保管場所⇔試験場の移動を実現する手段。全 7 方式 |
| 教示 | 経路を一度人が走らせて記録すること。記録そのもので移動も達成される |
| 教示再生 | 記録済み経路を機体が単独でなぞること |
| 盤 | 配電盤。上部をカメラで確認する対象 |
| カメラ昇降 | 盤上部を見るためにカメラを持ち上げる機構。**停止精度の要求元** |
| 対象（人物） | LiDAR による人物追跡で選択された、追従・呼び寄せの相手 |
| 手押しモード | 物理非常停止ボタンが押されている状態。人が機体を押して運んでいるとみなす |
| 必須通信系統 | **ESP32・RaspberryPi4(LiDAR)・PC の 3 者間**の通信。これ以外は任意 |
| ゾーン | 試験場内か場外か。**画面で自動判定する** |

## 3. 目標

| ID | 目標 | 達成とみなす条件 |
| --- | --- | --- |
| **G1** | 人・物への接触 0 件、意図しない挙動 0 件 | **数えるのではなく故障注入で検証する**（[Spec-safety.md](Spec-safety.md) §9） |
| **G2** | カメラ昇降が要求する許容差内に、手動微調整なしで停止できる | 盤前停止後、試験員が機体を手で動かす必要が一度もない |
| **G3** | 地図作成＋盤登録が試験員 1 人で完結し、地図の手修正が不要 | 2 人目の補助なし、地図をエディタで直す作業なし |
| **G4** | 保管場所⇔試験場を、試験員が付き添う以上の負担なく移動できる | 「人が押して運ぶ」より手間が増えていない |
| **G5** | 往復＋準備＋試験を再起動なしで完走できる | 運用途中で再起動を必要としない。n=1 で足りる |

> **G1 は他のすべてに優先する。G1 を犠牲にして G2〜G5 を満たしてはいけない。**

### 3.1 KPI は率ではなく回数で書く

n=10〜30 の試行数では「完走率 95%」も「99%」も検証できない。
**「10 回中 10 回」「介入 0 回 / 200 m × 10 往復」**の形で書く。
方式ごとの KPI は [Spec-transit.md](Spec-transit.md) §7.3 と [Spec-onsite.md](Spec-onsite.md) §8。

## 4. 開発の進め方

前提: **PoC のあと MVP を作る期間が短い。実証実験でデータを得た時点で開発終了。**

* **PoC では走行方式を削らずに全部作り、全部試験する。MVP で採用されなかったものを削る**（引き算で進める）
* **方式の比較と取捨選択は社内試験（1 方式あたり n = 10〜30）でしかできない。**
  実証実験は先方の教育用施設で n = 1〜2 しか取れない
* 採否の判断順（上から見て落ちた時点で切る）:
  **① 許可**（足切り）→ **② 完走率・介入回数** → **③ 安全**（接触 0・意図しない発進 0）→ **④ MVP 期間内に作れるか**

## 5. 設計思想

記号は `SD-n`（`D-n` は `CL-D-n` / `DF-D-n` と衝突するため使わない）。

* **SD-1 操作系は WebUI のみ。**専用アプリ・コマンドライン操作を運用手順に含めない
* **SD-2** WebUI は **PC とタブレットの両方**で操作でき、**縦長・横長の両方**に対応する
* **SD-3 ヘッダは常に最上位。**非常停止はどんなときでも動作し、何にも覆われない
* **SD-4 モードと状態を分ける。**「停止」と「終了」、異常からの復帰が素直に表せる
* **SD-5 ゾーンは画面が決める。**試験員が切り忘れる余地を作らない
* **SD-6 速度指令は必ず優先度つきの多重化を経由する。**駆動へ直接指令するものを作らない
* **SD-7 数値は出どころで 3 分類する。**測らないと分からない値に事前の目標を置かない

## 6. 全体構成

```
        [ Wi-Fi AP ]  ← 全通信を中継。単一障害点
       ╱      │      ╲
 [ PC ]   [ ESP32 ]   [ RaspberryPi4 ]
   │       ├ CuGoV3    ├ LiDAR (USB)
   │       ├ IMU       └ リードデバイス (USB)
   │       └ 物理E-Stop
 [ タブレット ] ← WebUI・任意    PC は機体に載せず有線接続もしない
```

### 6.1 ハードウェア構成

| # | 機器 | 役割・仕様 | 接続 |
| --- | --- | --- | --- |
| 1 | **Wi-Fi AP** | 全ての機器の通信を中継する。**単一障害点** | — |
| 2 | **PC** | ほとんどの処理を担う。**機体に乗せず、有線接続もしない** | Wi-Fi |
| 3 | **ESP32** | CuGoV3（モーター×2・エンコーダ×2）、IMU、物理非常停止ボタンと GPIO 接続 | Wi-Fi / WebSocket |
| 4 | **RaspberryPi4** | LiDAR を USB 接続しスキャンを配信する | Wi-Fi |
| 5 | **LiDAR** | RPLIDAR S1、360° 全周、256000 baud、10 Hz | RaspberryPi4 に USB |
| 6 | **IMU** | DSR1603 / BNO055、9 軸 | ESP32 に GPIO |
| 7 | **CuGoV3** | クローラー、DC モーター×2 ＋ エンコーダ×2 | ESP32 に GPIO |
| **8** | **カメラ**（ライン誘導走行用） | 前方 1 台。区画線と分岐を認識する | **要検討**（詳細設計） |
| **9** | **リードデバイス**（電子リード走行用） | Arduino。張力の有無とリードの向きを取る | **RaspberryPi4 に USB** |

> **8・9 は本設計書で追加した**（原典の構成表は 7 項目のまま）。**RaspberryPi4 は LiDAR も USB で繋ぐため帯域を共有する。**

### 6.2 ソフトウェア構成

| # | 機器 | 構成 |
| --- | --- | --- |
| 1 | PC | **Ubuntu + Docker + Ubuntu 22.04 + ROS2** |
| 2 | ESP32 | C++ |
| 3 | RaspberryPi4 | Ubuntu 22.04 + ROS2 |

> **Docker はやめない。**変更されたのはホスト OS（Windows+WSL → Ubuntu）である。
> したがって各所の「docker ワークスペースに保存」という記述は正しい（[Spec-open.md](Spec-open.md) C-04）。

## 7. 走行方式（7）

| # | 方式 | 事前に必要なもの | 試験員は | 障害物 | 終わり方 |
| --- | --- | --- | --- | --- | --- |
| 1 | **追従走行** | なし | 先を歩く | 停止 | 人が停止 |
| 2 | **手動走行** | なし | 画面を見て操作 | **警告** | 人が停止 |
| 3 | **教示（追従）** | なし | 先を歩く | 停止 | 人が停止 |
| 4 | **教示（手動）** | なし | 画面を見て操作 | **警告** | 人が停止 |
| 5 | **教示再生走行** | 教示済み経路 | 見ている（先導も可） | 停止 | 人が停止 |
| 6 | **ライン誘導走行** | 区画線＋ラインマップ | 見ている | 停止 | **自動停止** |
| 7 | **電子リード走行** | リードデバイス | リードを引いて歩く | 停止 | 人が停止 |

**逆再生は独立した方式ではなく、教示再生画面の中の選択肢。**
ただし **KPI では順再生と分けて計測する**ので、計測単位としては 8 になる（[Spec-open.md](Spec-open.md) C-03）。

詳細は [Spec-transit.md](Spec-transit.md)。

## 8. モード（18）

| 群 | モード |
| --- | --- |
| 基盤 | `INIT` / `IDLE` / `ESTOP` / `CARRY`（手押し） |
| 走行方式 | `FOLLOW` / `MANUAL` / `TEACH_FOLLOW` / `TEACH_MANUAL` / `REPLAY` / `LINE` / `LEASH` |
| 試験場内 | `PREP` / `PANEL_NAV` / `AT_PANEL` / `SUMMON` / `HOME_NAV` |
| 保守 | `OPCHECK` / `CALIB` |

`IDLE` を中心とするハブ＆スポーク。**走行方式どうしの直接遷移は無い。**
手動が要るときはモードを変えず**ジョグ介入**で行う。

遷移表・人物追跡の要否・ゾーン・速度・自動ブレーキ・復帰先は [Spec-modes.md](Spec-modes.md)。

## 9. 1 日の流れ

```
[保管場所] 電源ON → Wi-Fi接続 → start.sh → 疎通確認 → メインメニュー画面
              ↓ バッテリー残量を確認 → 走行方式を1つ選ぶ
[試験場]   前日: 地図作成・待機場所登録・盤登録 → 保存
           当日: (a) ピンを選ぶ  または  (b) その場で呼ぶ → 作業 → 待機場所へ
              ↓ 走行方式を1つ選ぶ（往路と同じ手順・同じUI）
[保管場所] 終了手順（保存 → 停止 → 電源断）
```

**往復を区別しない。**詳細は [Spec-ops.md](Spec-ops.md) と [Spec-onsite.md](Spec-onsite.md)。

**例外は教示 2 種（`TEACH_FOLLOW` / `TEACH_MANUAL`）だけ。**
教示は保管場所以外を起点にしないと決めてあるので（[Spec-transit.md](Spec-transit.md) §3.5）、
**復路では選べない。**メインメニュー画面での前提確認に含める（[Spec-transit.md](Spec-transit.md) §0.6）。
