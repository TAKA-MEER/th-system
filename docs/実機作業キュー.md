## 4. ESP32 の受信ギャップ（未解決・要実機）

2026-08-21 の実測（`th_ws/data/meas04_after.csv`・22 分）で、**esp32 軸に 600 ms 超の断が
3 回、最悪 4106 ms** 残っている。p99（161 ms）は健全だが裾が健全でない。
`esp32_timeout_ms = 322 ms` なので、**実機では誤フォルトではなく「本物の断」による停止が
起きる。**

`meas05` の切り分け（`th_ws/data/meas05/*_verdict.txt`）による原因は 3 つ:

| 原因 | 内容 | 直せる場所 |
| --- | --- | --- |
| **A** | TCP の HOL blocking（WebSocket は TCP。1 フレーム落ちると再送で 200〜600 ms 途切れる） | UDP 化か WS フレーム分割の見直し。**設計判断が要る** |
| **B** | ESP32 が送っていない（IMU の I2C 読みか制御ループの詰まり） | **ファーム。実機必須** |
| **C** | `esp32_bridge`（Python）の詰まり（50 Hz の `_drain_rx_queue` と GIL 競合） | **PC のみで直せる。**実機を待たなくてよい |

無線区間そのものは健全（ICMP 3000 発が全て 33 ms 以内・損失 0 %。
`meas04/ping_icmp_600s.md`）。**AP を替えても直らない。**

## 6. 記録先の不整合（解消済み）

`機体作業手順-段階0.md` §7 が完了条件として検査するパスに `docs/plan/detailed/data/`
配下を挙げていたが、このディレクトリは統合ブランチに存在せず、実測データは
`th_ws/data/` にしかないというズレがあった。2026-08-26 に解消済み。

**決定した方針: 記録先は `th_ws/data/` に一本化する。**
`docker-compose.yml` がコンテナへバインドマウントするのは `src` / `esp32` /
`scripts` / `data` / `dr_spaam_weights` のみで、`docs/` はマウントされていない。
計測スクリプトはコンテナ内で走るため `docs/` 配下には直接書けず、「書ける場所」と
「記録する場所」を一致させる必要があった。以後、新しい計測データも `docs/` 配下ではなく
`th_ws/data/` に置くこと。

対応内容:

| 項目 | 対応 |
| --- | --- |
| `WP-MEAS-01`（制動） | `th_ws/data/brake_accel_*.csv` として既に存在。`registry.yaml` の `source` を実パスに修正 |
| `WP-MEAS-02` | 未実施のまま。`th_ws/data/meas02/` へ記録する（手順書 §7 参照） |
| `WP-MEAS-03` | 未実施のまま。`th_ws/data/meas03/baseline.md` へ記録する（手順書 §7 参照） |
| `WP-MEAS-04` | `recovered/feat/meas-latency-triage` から改善前の比較用生データ 12 ファイルを `th_ws/data/meas04/` へ取り込み、`th_ws/data/meas04_after.csv` を `th_ws/data/meas04/after.csv` にリネームして揃えた |
| 寸法（`dimensions/body.md`） | **恒久的に消失。**値は `registry.yaml`（`body_width_m` / `body_length_m`）の `note` に出典注記付きで生存しており再計測不要 |

手順書 §7 と `registry.yaml` の `source` / `note` は上記に合わせて更新済み（値は変更していない）。
