> **【2026-09-05 更新】焼き方が変わった。** ESP32 は**常時ラズパイに USB 接続**

### 1.3 `WP-CARRY-01` の実機確認結果（2026-08-31・完了）

`§10 ③`（電源断での遷移）と `§10 ④`（通電でのテスタ確認）を実施した。

**③ 遷移**（モータ電源断・`stage:=1` / `lidar_source:=network`）:

| 事象 | 観測 |
| --- | --- |
| 押下 | `MANUAL → CARRY`、`estop_hw=True`、`prev_mode=MANUAL` をラッチ |
| `CARRY` 中の `ui.estop.press` | **拒否**（`accepted=False` / `reject_reason_key='estop_disabled_in_carry'`） |
| 解放 | `estop_hw=False`。**`CARRY` のまま**（明示的な resume を要求する設計どおり） |
| `ui.carry_resume` | `MANUAL/PAUSE` へ復帰（`prev_mode` から正しく戻る） |

**④ テスタ実測**（通電）。手順は「先にボタンを押してから通電する」順にした
（駆動が通電した状態でボタンを押す順にしないため）:

| 状態 | モータードライバ電源ライン |
| --- | --- |
| **物理ボタン押下中** | **0.5 V** |
| **解放後** | **26.52 V** |

**合格**。押下でハード的に駆動電源が落ちている。残留 0.5 V は開放接点の漏れ・
テスタの負荷・ブリーダ経由の残留と考えられ、26.52 V に対し 1.9 %。
モータードライバが動作する電圧ではない。**この 2 値は次回の比較基準にすること**
（値が上がっていたら接点の劣化を疑う）。

**副次的に確認できたこと**: 一連の操作でフォルトは 0 件。モータードライバの
通電・遮断そのものは `safety_monitor` の監視対象を一切揺らさない。

> **細かいが記録しておく点**: ボタン解放の直後に `last_reject_reason='not_allowed'`
> が 1 回立つ（`CARRY` 中の `hw.estop.release` に対応する遷移が無いため）。
> 動作上は無害だが、この値は `/system/state` に載るので **UI がそのまま出すと
> 「操作が拒否されました」と誤って見せうる**。UI 側の扱いを決めるときに考慮すること。

### 1.2 実機専用 3 本（04 / 08 / 10）の実施手順

`case_04` / `case_08` / `case_10` の docstring は「個別の実施手順はこのファイルに

**実施したら結果（日付・実測値・所見）をこの節に追記すること。**
3 本とも `pytest.fail` のまま赤で居続けるのが正しい状態なので（T-3）、
「実施済み」の記録はこの文書にしか残らない。

#### 故障注入 04「非常停止（物理）」

> **前提**: `ESTOP_BENCH_TEST_BYPASS` を外したファームが焼けていること（§0）。
> **バイパスが有効なままだと押しても何も起きず、しかもテストは「押しても止まらない」
> という正しい観測を返す。**先に §0-3 で `/safety/firmware_flags` が `0` であることを確認する。

| 順 | 操作 |
| --- | --- |
| 1 | **先に記録を始める。**別端末で `ros2 topic echo /safety/estop_hw` と `ros2 topic echo /cmd_vel`、`ros2 topic echo /system/state` を回しておく（押してから echo を始めると遷移の瞬間を取り逃す） |
| 2 | `MANUAL` ジョグで低速前進させる |
| 3 | 走行中に物理ボタンを押す |

**合格条件**: `/safety/estop_hw` が `true` になり、`/cmd_vel` がゼロになり、車輪が止まる。
`/system/state` の `mode` が `ESTOP` になる。**押下 → 停止の実測値を記録すること**（合否だけでは次に活かせない）。

#### 故障注入 08「ESP32 ウォッチドッグ」

> **落とすのは `esp32_bridge` を含む ROS2 側全体。**`obstacle_limiter` だけを落としても
> `esp32_bridge` が生きていればキープアライブが 20Hz でゼロを送り続けるため、
> **ESP32 のウォッチドッグは発火しない**（それは故障注入 12 の担当範囲であり、
> この項目の観測対象ではない）。ここで見たいのは「PC が丸ごと死んでもファームだけで止まるか」。

| 順 | 操作 |
| --- | --- |
| 1 | 車輪が空転しても安全な状態にする（機体を持ち上げるか、十分な空間を確保する） |
| 2 | 低速前進させる |
| 3 | 走行中に PC 側の ROS2 を丸ごと落とす。**ホストで `docker kill th_robot`**（コンテナ内の全プロセスが同時に SIGKILL される＝「PC の突然死」に最も近い。`pkill -f` が自分のシェルを殺す落とし穴も踏まない。2026-09-23 に `launch` の `Ctrl-C`／`kill -9` から変更） |

**合格条件**: `esp32_watchdog_ms`（600 ms・`config.h` の `WATCHDOG_MS`）以内に車輪が止まる。
ESP32 のシリアルログ（`[DBG]` 行）で停止時刻を裏取りできるとなおよい。

> **後始末**: `docker start th_robot` でコンテナを起動し直し、`使い方.md` §1-2 から起動し直す
> （コンテナの再起動で `/dev/shm` の DDS の残骸も消える。`kill -9` を繰り返すと DDS discovery が
> 壊れる話は `CLAUDE.md` の「環境の癖」）。
>
> **シリアル直結（2026-09-05）後も手順は有効。**ラズパイの `pi_serial_relay` は PC との接続を
> 素通しするだけで、自分でゼロ指令やキープアライブを送らない（2026-09-23 にコードで確認）。
> PC が死ねば ESP32 への指令が途絶え、ESP32 のウォッチドッグだけが止める。

#### 故障注入 10「物理ボタン起動時押下」

| 順 | 操作 |
| --- | --- |
| 1 | 物理ボタンを押した（またはラッチさせた）状態にする |
| 2 | その状態でシステムを起動する |
| 3 | `INIT` から出ないことを確認する |
| 4 | **ボタンを解放し、`IDLE` へ進むことを確認する** |

**合格条件**: 手順 3 で `/system/state` の `mode` が `INIT` のまま（`connectivity_checker` の
L-2 が `/safety/estop_hw` = true の間 `link_ok` を出さない）、かつ UI に解除の案内が出る。
**そのうえで手順 4 が通ること。**

> **手順 4 を省かないこと。**`connectivity_checker` は `/safety/estop_hw` を
> **一度も受信していない間も**「判定できない＝不合格」として `INIT` に留める
> （`_estop_seen`。§6.2）。つまり「起動しなかった」だけでは、

## 4. ESP32 の受信ギャップ（**解消済み・2026-09-05**）

> **【解消】原因 A（TCP の HOL blocking）ごと構成から取り除いた。**
> 第4回3階教示再生走行試験（2026-09-05）で通信エラーにより教示できなかったことを受け、
> **ESP32 の無線を廃止し、ラズパイへ USB-UART で直結**する構成に変更した
> （[network.md](network.md) / [教示再生走行試験.md](教示再生走行試験.md) §5）。
> ESP32↔ラズパイ間は TCP を通らないので、この節が挙げる原因 A は原理的に発生しない。
> 導入後の実測では `/esp32/wheel_feedback` は約100ms間隔・標準偏差 0.003〜0.01s。
>
> 残る原因 B（ファーム側の詰まり）・C（`esp32_bridge` の GIL 競合）は、
> 現在この症状として観測されていない。**再発したときのために以下の切り分け記録を残す。**
>
> なお導入直後に**似た症状が一度再発した**が、原因は新設の `pi_serial_relay` 側で、
> `ser.read` の固定50msポーリングが ESP32 の100ms送信周期とビートを起こしていたもの
> （`ad3960d` で解消）。**同じ「毎周期バースト」の見え方をするので混同しないこと。**

以下は無線構成だった当時（〜2026-09-05）の記録。

2026-08-21 の実測（`th_ws/data/meas04_after.csv`・22 分）で、**esp32 軸に 600 ms 超の断が
3 回、最悪 4106 ms** 残っている。p99（161 ms）は健全だが裾が健全でない。
`esp32_timeout_ms = 322 ms` なので、**実機では誤フォルトではなく「本物の断」による停止が
起きる。**

`meas05` の切り分け（`th_ws/data/meas05/*_verdict.txt`）による原因は 3 つ:

| 原因 | 内容 | 直せる場所 |
| --- | --- | --- |
| **A** | TCP の HOL blocking（WebSocket は TCP。1 フレーム落ちると再送で 200〜600 ms 途切れる） | UDP 化か WS フレーム分割の見直し。**設計判断が要る** |
| **B** | ESP32 が送っていない（IMU の I2C 読みか制御ループの詰まり） | **ファーム。実機必須** |
| **C** | `esp32_bridge`（Python）の詰まり（50 Hz の `_drain_rx_queue` と GIL 競合） | **PC のみで直せる。**実機を待たなくてよい |

無線区間そのものは健全（ICMP 3000 発が全て 33 ms 以内・損失 0 %。
`meas04/ping_icmp_600s.md`）。**AP を替えても直らない。**

### 4.0 シリアル直結後の実機再確認（2026-09-21・駆動電源なし）

**条件**: ESP32 → ラズパイを USB シリアル直結。`th_robot` で `bringup.launch.py`（`stage:=1`・**通常モード**）を起動し、
`/esp32/wheel_feedback` の到着間隔を購読だけで計測した（速度指令は出していない。`/cmd_vel` は全件ゼロ）。
駆動電源が無くてもエンコーダ 0 のままフレームは届くので、**受信ギャップの計測はできる**。

| | 1 回目（計測中に私が別操作をした） | 2 回目（何も操作しない） |
| --- | --- | --- |
| 時間・フレーム | 600 s・6000 | 900 s・**9000 / 9000（欠落ゼロ）** |
| 間隔 p50 / p99 | 100.0 / 120.8 ms | 100.0 / 120.8 ms |
| **最大ギャップ** | **479.9 ms** | **361.1 ms** |
| 200 ms 超 | 3 件 | 1 件 |
| **500 ms 超** | **0 件** | **0 件** |
| 期間中のフォルト | `ESP32_DISCONNECTED` 1 回（200 ms で解除） | 無し |

- **原因 A 由来の「500 ms 超〜数秒」の受信ギャップは、25 分間で 0 件。**WiFi 経由の時代（最大 1.2 秒台が数分に 3 回）から
  **桁が変わった。**接続確立直後の最初のフレームだけ 1.22 s の遅れがあった（起動時の 1 回のみ）
- **ゼロにはなっていない。**200〜480 ms の途切れは静かな状態でも残る（2 回目で最大 361 ms）。
  1 回目の方が悪かったので、一部は同時に走らせた読み取り操作の負荷だった可能性が高いが、**負荷が無くても 322 ms 超は起きうる**
- **N-6 との関係**: `esp32_timeout_ms = 322 ms` は上の最大値（361〜480 ms）より短い。実際に 1 回目で
  **480 ms の途切れが `ESP32_DISCONNECTED`（回復フォルト）を発火**した。走行中なら `PAUSE` に落ちる大きさで、
  **走行試験中の散発的な一時停止として現れうる**。値をどちらへ動かすかは未決（N-6）
- 静止時の車輪速度ノイズは最大 0.004 m/s。`runaway_zero_threshold`（0.02 m/s）の 1/5 なので、
  静止中に `DRIVE_RUNAWAY` が誤発火することはない

  （ESP32 が居れば最初のフレームで判明する）が実機で成り立っている
- 開発モードの実機確認も通った（OFF の 25 分間は記録 0 件、ON＋選択で `state`/`fault`/`cmdvel` が ISO8601 時刻つきで記録、

**`W-06` への含意**: 除外理由の前提（受信ギャップで走行のたびに誤発火）は**消えた**。ただし最大 480 ms は
`runaway_hold_ms`（500 ms）に**20 ms 差まで迫っている**。「`runaway` を戻すだけ」ではなく、台帳 `W-06` の②
（wheel_feedback の鮮度ゲート）を先に入れるのが安全側だったので、**②は 2026-09-21 に実装した**（`4253442`。実測が古いあいだは判定を凍結）。`DRIVE_RUNAWAY` の検知そのもの（指令と実速度の乖離）は
**駆動電源がある走行日でないと確かめられない**。

**起動時の注意（今回踏んだ）**: `bringup.launch.py` の `lidar_source` 既定は **`local`**（USB 直結の `sllidar_node` を起動する）。

### 4.0.1 走行して分かったこと（2026-09-21・駆動電源あり）

**今日入れた `LOCALIZATION_LOST` の検知が、実際の走行で当たった**（走行できない状態で入れた検知を、走行日まで安全側に
倒さずに有効にしたため）。原因は 2 つで、どちらも実機で確認した。

| # | 症状 | 原因 | 対処 |
| --- | --- | --- | --- |
| 1 | **走らせるとすぐ止まる**（`localization ng: reason=jump` が 0.5 秒おき ＋ `LOCALIZATION_LOST`） | B′ の閾値（0.11 m／1°）が、クローラーの旋回中の**正常な補正**（最大 0.37 m／10.5°）より厳しすぎた。保持時間（300 ms）も発信周期（500 ms）に負けて効いていなかった | 閾値を **1.0 m／0.5 rad** に（**main 統合済み 2026-09-21・`bc3bce3`**）。`Spec-safety.md` §3.5.0（計測 `th_ws/data/meas07_jump/`） |
| 2 | **再生で経路を選ぶと非常停止**（再起動が終わった瞬間に解除） | `slam_control` が地図の読み直しのたびに `slam_toolbox` を**わざと落として立て直す**（最大 45 秒）のを、`node_down`／`stale` が異常と見なした | 計画的な再起動を保留する設計（`Spec-safety.md` §3.5.0「計画的な再起動は異常ではない」）。**main 統合済み 2026-09-21・`b6cee5e`**（`/slam_control/estimator_restarting`。ホスト試験＋Docker の振る舞い試験。**実機で確認済み 2026-09-21**＝経路選択で非常停止なし、`/safety/localization_health` が `reason: ''` → `restarting` → `''` と遷移） |

**【確認済み 2026-09-21】** 再起動後に走らせて `jump` で止まらず、経路選択でも非常停止なし（上記の遷移を確認）。旧い一時回避は外れている。
以下は反映手順の記録: **実機へ反映するには bringup を再起動する**（走らせたままなら `ros2 param set /localization_health jump_translation_m 1.0`／`jump_rotation_rad 0.5`。#2 は再起動が要る）。
**再確認すること**: 経路を選んで再生に入っても非常停止にならない／`/safety/localization_health` が `restarting` を経て `ok` に戻る／
走らせても `jump` で止まらない。旧い一時回避（`jump_*` を 100、`localization_stale_ms` を 90000 にする）を入れたままなら**外す**。

### 4.1 切り分けは 1 回の走行で済むようになった（2026-08-26）

`esp32_bridge` に**自己計測の計器を入れた**（本線 `fdb72bd`）。50 Hz の drain タイマーが
実際に何 ms 遅れて呼ばれたかを測り、1 Hz で機械可読のサマリを出す。

```
esp32_bridge_diag: timer_interval_max_ms=..., drain_duration_max_ms=..., feedback_gap_max_ms=...,
frames_since_window=..., frames_total=..., coalescer_dropped_total=..., rx_queue_dropped_total=...,
invalid_frames_total=...
```

**判定の仕方**（`ros2 launch` のログを `grep esp32_bridge_diag` で拾うだけ）:

| 観測 | 結論 |
| --- | --- |
| `feedback_gap_max_ms` が跳ねた窓で `timer_interval_max_ms` **< 50** | **C は否定。**原因は A か B。`meas05_esp32_triage.sh` の tcpdump で A/B を分ける |
| 同じ窓で `timer_interval_max_ms` **が跳ねている** | **C が確定。**bridge 側が実際に止まっている |
| `rx_queue_dropped_total` / `coalescer_dropped_total` が増える | 輻輳が実在する。値は捨てた件数そのもの |

**tcpdump より先にこれを見ること。**ログを見るだけで 3 択が 2 択以下に減る。

### 4.2 実機計測で原因 C は否定された（2026-08-31）

**この計器は設計どおりに効いた。**実機 bringup を 190 秒動かすだけで 3 択が 2 択に減った。

| --- | --- |

| 同 p90 | 120.1 ms |

### 4.3 A/B の切り分け結果（2026-08-31）: **A（TCP）。ただし発生条件が分かった**

`meas05_esp32_triage.sh` を条件を変えて 2 回（各 600 秒）回した。**差分は `/scan` を
購読するかどうかだけ**（ラズパイ AP 構成では LiDAR も ESP32 も同じ無線区間を通るため、
`/scan` を受け続けること自体が電波の占有を再現する）。

| 条件 | ESP32 (ROS) 最大 | 電線上 最大 | TCP 再送 | 250ms 超 |
| --- | --- | --- | --- | --- |
| `/scan` 購読**なし** | 未取得※ | **131.1 ms** | **0 / 18,616** | **0 回** |
| `/scan` 購読**あり** | **1220.9 ms** | **927.2 ms** | **8 / 18,601** | **1 回** |

※ 1 回目は `meas05_arrival_recorder.py` が欠損していて起動せず、ROS 側が取れなかった。
これ自体は事故だったが、結果として「`/scan` を受けない条件」の対照実験になった。

```
t+528.1s  ROS 1220.9ms  電線上 927.2ms  再送 8 件  → A（TCP 再送）
```

**結論: A（伝送方式）。AP を替えても直らない。**ただし今回分かったのは判定だけではない:

1. **跳ねは「LiDAR と ESP32 が同じ無線区間を共有しているとき」にだけ出た。**
   共有しない条件では電線上のギャップ 0 回・再送 0 件で、まったく再現しない。
2. **LiDAR 自身は無傷**（ROS 側 max 179.0 ms・250ms 超 0 回）。
   競合したとき壊れるのは **ESP32 側だけ**という非対称がある。TCP で小さなフレームを
   高頻度に送る ESP32 が、再送とバックオフの影響を受けやすいのだと考えられる。
3. **ROS 側（1220.9ms）が電線上（927.2ms）より約 294 ms 大きい。**
   支配項は電線側だが、`esp32_bridge` 側にも上乗せがある。

> **2026-08-20 の判定（B: ESP32 が送っていない）と食い違う。**当時は ESP32 が AP の構成で、
> 跳ねも 1 回・最大 300 ms だった。今日は 1 回・電線上 927 ms で再送 8 件という直接証拠がある。
> **どちらも跳ね 1 回に対する判定なので断定はしない**が、構成が変われば支配的な原因も
> 変わりうるということ。**構成を変えたら必ず測り直すこと。**

**対処の候補**（未決。設計判断が要る）:

| 案 | 効果 | 代償 |
| --- | --- | --- |
| ESP32 リンクを UDP 化 | 再送とバックオフが消える。根本対処 | ファームと `esp32_bridge` の両方を書き換える。順序保証を自前で持つ |
| WS のフレーム分割・送信頻度の見直し | 占有時間を減らす | 効果は限定的かもしれない |
| **LiDAR と ESP32 を別の無線に分ける**（帯・チャネル・物理 I/F） | 競合そのものを無くす。今回の実測が直接支持する | 機材構成の変更 |
| LiDAR を有線化（ラズパイ〜PC を Ethernet） | 無線区間から `/scan` が消える | 配線の取り回し |

**`esp32_timeout_ms = 322 ms` に対し実測 1220.9 ms なので、この跳ねは実運用で
「本物の断」として停止を起こす**（N-6）。対処が入るまでは、走行試験中に
`ESP32_DISCONNECTED` が出ても機材の故障ではなくこれを疑うこと。

**頻度は meas04 より悪化している。**meas04 は 22 分で 600 ms 超が 3 回だったが、
今回は約 3 分で 322 ms 超が 3 回（うち 3 回とも 1.2 秒以上）。ネットワーク構成が
当時と違う（PC は USB WiFi ドングル経由で `th-rpi-ap` に接続）ため、
**ドングル側の可能性も切り分け対象に加えること。**

> **ping を WiFi 品質の指標に使わないこと。**同日の実測で ESP32 への ICMP は
> avg 85.8 / max 150.7 ms と悪い値を示したが、同じリンク上の実データは 10.00 Hz・
> std dev 0.4 ms で極めて安定していた（AP 自身への ICMP は 1.4〜3.1 ms）。
> ESP32 の省電力モードが ICMP 応答だけを遅らせている。`esp32_bridge_diag` を見ること。

なお C の**発生機構自体は本線で塞いである**（送信のコアレッシング・受信キューの有界化・
ログの throttle。`bedc984` / `bcc80d9` / `97337ca` / `c516a53` / `544617e`）。
それでもなお C が出るなら、塞いだ経路以外に原因があるということになる。
