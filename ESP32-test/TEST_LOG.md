# 試験ログ

## 2026-07-06: Stage1 モーター単体 + エンコーダー反応確認

実機(COM4接続, Silicon Labs CP210x)に `stage1_motor_encoder` を書き込み、duty 10/20/30% で
左右モーターを正転・逆転させ、エンコーダー応答を記録した。

### 1. 低duty域での右モーター間欠動作（既知の課題）

- duty 30%: 左右とも安定駆動 (mean±stddev: 左 ≈1090±32 cnt/100ms、右 ≈965±50 cnt/100ms)
- duty 10%: 右モーターの回転が不安定化。試行によって完全停止 (mean≈-17、ばらつき大) または
  低速で継続 (mean≈-190、stddev 40〜50) と再現性のない挙動が出た。
- 静止摩擦(スティクション)対策として起動時キックスタート (60%duty×150ms, `stage1_motor_encoder.cpp`
  の `k` トグル) を追加・検証したが改善せず、むしろ stddev が69〜87に悪化した。
  → 10%duty では単純にトルク不足で回転を維持できないと判断（ユーザー実機確認でも同じ所見）。
- 左モーターの振動は今回のエンコーダーデータ (10/20/30%) では明確に再現しなかった。

### 2. 右エンコーダーの符号反転バグ（新規発見・修正済み）

- 正転コマンドで dLeft は常にプラス、dRight は常にマイナスという非対称を確認
  (10/20/30% duty、正転・逆転とも再現。ポート競合の可能性を排除した上で再検証済み)。
- 原因: `lib/hw_common/encoder.cpp` の左右ISRが同一ロジックで、左右ミラー配置による
  符号差が未補正だった。
- `th_ws/esp32/src/encoder.cpp` も全く同一実装で同じ問題を持ち、`main.cpp` の速度PID
  (`velR`) にそのまま流れ込んでいたため、報告されている「右モーターの間欠動作」の
  一因だった可能性が高い。
- 修正: 両ファイルの `readAndResetRight()` の戻り値を反転 (`-v`)。
  - `ESP32-test/lib/hw_common/encoder.cpp` — 実機書き込み・再確認済み
  - `th_ws/esp32/src/encoder.cpp` — コード修正のみ（本体ロボット実機への書き込み・確認は未実施）
- 修正後の実機再検証: dRight = 正転 +601〜+698 / 逆転 -430〜-465 で左右の符号が一致することを確認。

### 次のステップ

- `th_ws/esp32` を実ロボットに書き込み、右モーターの間欠動作が改善したか確認する。
- Stage2（直進性確認）に進む。

## 2026-07-06: Stage2 直進性確認（オープンループ）

機体を拘束した状態で `stage2_straight_line` を実機書き込みし、duty 30%（デフォルト）で
前進・後退それぞれ8秒間（安全タイムアウトまで）走行させ、左右累積距離を記録した。

- 前進: distLeft=5.0618m, distRight=4.4218m, diff=0.6400m (**13.5%**)
- 後退: distLeft=-5.0654m, distRight=-4.4861m, diff=-0.5793m (**12.1%**)
- 左が右より約12〜13%速く進む左右差を確認。Stage1で見た30%duty時の平均カウント差
  (左≈1090 / 右≈965 cnt/100ms、約11%差) と一致しており、右エンコーダーの符号バグとは
  別の要因（モーター/ギアボックスのトルク・摩擦特性差など機械的な左右差）と考えられる。
- Stage4のPIDゲイン調整で補正すべき基礎データとして記録。

## 2026-07-06: Stage3 指定距離での停止

機体を拘束した状態で `stage3_distance_stop` を実機書き込みし、duty 30%（デフォルト）で
目標距離 1.0m を2回、0.5m を1回試行した。

| 目標距離 | 実測avg | オーバーシュート | 所要時間 | distLeft / distRight |
|---|---|---|---|---|
| 1.0m (試行1) | 1.0033m | +0.0033m (0.3%) | 1700ms | 1.0688 / 0.9378 |
| 1.0m (試行2) | 1.0027m | +0.0027m (0.3%) | 1700ms | 1.0752 / 0.9301 |
| 0.5m (試行3) | 0.5241m | +0.0241m (4.8%) | 900ms | 0.5619 / 0.4863 |

- 停止精度(左右平均基準)自体は良好(1.0m目標でオーバーシュート0.3%程度)。
  ただし短距離(0.5m)では相対的にオーバーシュートが大きい(4.8%) — 100ms周期の停止判定と

- 左右個別の距離差は約12〜13%で、Stage2で確認した左右差と一致（左右平均で停止判定して
  いるため停止精度自体への影響は小さいが、直進性としては引き続きズレている）。

## 2026-07-06: Stage4 速度PIDゲイン調整

機体を拘束した状態で `stage4_timed_distance` を実機書き込みし、`t 1.0 2.0`
（目標速度0.5m/s）でゲイン調整を試みた。

### 1. 初期ゲインでの左輪発振（重大）

初期値 (左 Kp=100/Ki=30/Kd=8、右 Kp=80/Ki=30/Kd=8) では**左輪が発振**した。

```
[CTRL] t=4900ms velL=-0.834  outL=255.0
[CTRL] t=5000ms velL= 1.305  outL=-198.9
```

毎周期(100ms)で速度の符号が反転し出力も±255に張り付く不安定状態。目標時間2.0秒に対し
実際は5.2秒かかった。右輪(Kp=80)は発振せず安定していたが、velR≈0.3m/sで目標0.5m/sに
届かない定常偏差があった。

### 2. ゲイン調整

- Kp_left を 100→50 に下げても発振は解消せず、ほぼ同じ振幅で継続。
- Kd_left=0, Ki_left=0, Kp_left=20 の P制御のみにすると発振は完全に消えたが、
  定常偏差が非常に大きい(velL≈0.04m/s、目標0.5m/s)。
- **Kp_left=30, Ki_left=10, Kd_left=8** で発振解消かつ定常偏差もある程度改善
  (velL≈0.18〜0.22m/s。目標0.5m/sにはまだ届かず、1.0m到達に5.1〜5.3秒
  かかっている＝収束はまだ遅い)。
- 発振という危険な状態は解消できたため、これ以上の高速収束の追い込みは一旦保留。

### 3. PID微分キックのバグ発見・修正済み

走行開始直後（最初の1周期目）だけ出力が跳ね上がる現象をユーザーが実機で体感し、
ログで確認した。

```
[CTRL] t=  100ms outL=55.5 outR=81.5   ← 最初の周期だけ跳ね上がる
[CTRL] t=  200ms outL=-18.8 outR=-21.3 ← 以降は通常レベル
```

原因: `reset()` 直後は `prevError_` が0のままなので、目標速度が0→setpointへ
瞬時にステップ変化する1周期目だけD項が `Kd × error / dt` という急峻な値になる
（典型的な「セットポイント微分キック」）。ゲイン調整のたびに毎回発生する構造的な
問題で、`th_ws/esp32/src/pid.h` にも全く同じ実装・同じ問題があった。

修正: `PID` クラスに `firstCall_` フラグを追加し、`reset()` 後の最初の
`compute()` 呼び出しではD項を0にする。
- `ESP32-test/src/stage4_timed_distance.cpp` — 実機書き込み・修正確認済み
  (t=100msの出力が55.5→15.5、81.5→41.5に低下しD項の跳ねが消えたことを確認)
- `th_ws/esp32/src/pid.h` — 同じ修正を適用（本体ロボット実機への書き込み・確認は未実施）

### 4. ゲインをpins.hのデフォルトに反映

Stage4で見つけた暫定値(左Kp=30/Ki=10/Kd=8)を `ESP32-test/lib/hw_common/pins.h` の
`PID_KP_LEFT`/`PID_KI_LEFT` デフォルト値として書き込んだ（右は未調整のまま
Kp=80/Ki=30/Kd=8）。まだ目標速度への収束が遅い暫定値であることに注意。
`th_ws/esp32/src/config.h` 側は未反映（ベンチと本体で負荷条件が異なる可能性があり、
実機未検証のまま反映するかは要確認）。

併せてユーザーが `PID_OUT_MIN`/`PID_OUT_MAX` を ±255 → ±120 に手動変更（最大出力を
抑える意図）。

### 5. 逆転ブレーキ禁止 + アンチワインドアップ（設計変更・実機未検証）

初期ゲイン(Kp_left=100)での発振時、`outL`が+255↔-190のように**実際に逆回転方向へ
出力**されていたことが激しい発振(velLの符号反転)の直接原因と考えられた。これを踏まえ、
「目標速度と逆符号の出力（逆転ブレーキ）を禁止する」設計変更を検討・実装した。

- 変更点: `PID::compute()` の出力クランプを対称(`outMin_`〜`outMax_`)から、
  目標速度(setpoint)の符号に応じた非対称クランプに変更。
  - `setpoint >= 0` → 出力は `[0, outMax_]` のみ許可（逆回転禁止）
  - `setpoint <  0` → 出力は `[outMin_, 0]` のみ許可
- 副作用として、出力が飽和している間に積分項(`iTerm_`)が巻き込まれ続ける
  ワインドアップが発生しやすくなるため、**出力が飽和した周期は`iTerm_`を
  更新しない**アンチワインドアップも同時に追加。
- トレードオフ: 減速手段が「逆回転による能動ブレーキ」から「出力ゼロにして
  摩擦・慣性で自然減速」に変わるため、オーバーシュート後の収束が遅くなる
  可能性がある。なお緊急停止(estop/watchdog)はPIDを経由せず`Motor::stopAll()`
  で即座に切るため、この変更による停止性能への影響はない。
- 適用箇所（**ESP32未接続のためビルド確認のみ、実機検証は未実施**）:
  - `ESP32-test/src/stage4_timed_distance.cpp` — ビルド成功確認済み
  - `th_ws/esp32/src/pid.h` — コード修正のみ

### 6. 参考: 類似機体(mirs260x-esp)のPID実装との比較

ユーザーから類似機体のコード (`github.com/6kam/mirs260x-esp` の `mirs24_esp32`) を
共有いただき比較した。

- **右エンコーダー符号反転の裏付け**: 向こうの`encoder.ino`は左右のISRで符号の
  扱いを意図的に逆にしていた(`enc_change_l`は`a==b`で`++`、`enc_change_r`は
  `a==b`で`--`)。今回の右エンコーダー符号修正が単なる配線ミスではなく、
  この機体設計(左右ミラー配置)に起因する既知の特性であることが独立ソースから
  裏付けられた。
- **PIDゲインの出自が判明**: 向こうの`config.h`のゲイン(右Kp=80/Ki=30/Kd=8、
  左Kp=100/Ki=30/Kd=8)が本プロジェクトの元のデフォルト値と完全一致。つまり
  検証済みの参考値ではなく、共通の未検証値がそのまま転記されていたと判明。
  （tuning自体の参考にはならなかった）
- **アンチワインドアップなし**: 向こうは`err_sum`に無条件加算するのみで
  積分項のクランプ処理がなく、本プロジェクトの実装の方が安全。
- **採用した安全策**: 目標速度がちょうど0の場合はPID計算を経由せず出力を
  強制的に0にする処理（向こうの`if(r_vel_cmd==0) r_pwm=0;`に相当）を追加。
  停止時のにじり出し・積分ワインドアップ防止のフェイルセーフとして
  `PID::compute()` 冒頭に実装。
  - `ESP32-test/src/stage4_timed_distance.cpp` — ビルド確認済み(実機未検証)
  - `th_ws/esp32/src/pid.h` — コード修正のみ
