# ICMP による無線区間の切り分け（2026-08-20）

## 目的

`esp32ap_bothns_10min.csv` で **ESP32 だけが max 603.4 ms で跳ね、LiDAR は max 104.2 ms
（取りこぼしゼロ）だった**。片方の経路だけが悪いなら原因は電波ではないはずで、
それを無線区間だけを叩いて確かめる。

## 方法

```bash
# PC のドングル wlx6c1ff789d5d4（192.168.4.50）→ ESP32 AP（192.168.4.1）
ping -i 0.2 -c 3000 -W 2 -D 192.168.4.1 > ping_icmp_600s.log
```

`esp32ap_bothns_10min.csv` と**同じ 10 分**。送信間隔 200 ms（5 Hz）。
ROS ノードは起動していない（DDS のディスカバリで自分から負荷を掛けないため）。

## 結果

| 指標 | 値 |
| --- | --- |
| 送受信 | **3000 / 3000（損失 0 %）** |
| RTT p50 | 3.5 ms |
| RTT p99 | 11.7 ms |
| RTT p99.9 | 27.3 ms |
| RTT max | **33.2 ms** |
| **100 ms を超えた RTT** | **0 件 / 3000** |
| 最大到着ギャップ | **230.7 ms**（送信間隔 200 ms なのでジッタは実質 +30.7 ms） |

先行して 180 秒（900 発・5 Hz）でも同じ傾向だった（損失 0 %、max RTT 18.6 ms、ギャップ 0 回）。

## 結論

**無線区間は健全。**同じ 10 分・同じ AP・同じアダプタで、ICMP は 3000 発すべてが
33 ms 以内に返っている。**603 ms の跳ねは無線区間では起きていない。**

したがって **AP を差し替えても跳ねは消えない。**AP 3 案の比較は打ち切る
（[機体作業手順-段階0](../../../機体作業手順-段階0.md) §4.0）。

## この測定で否定**できない**こと

ICMP echo は ESP32 の **LwIP（Wi-Fi/TCP タスク）が返す**ので、
**アプリ側の制御ループが止まっていても ping は返り続ける。**
よってこの結果は次の 3 つを否定しない。切り分けは `scripts/meas05_esp32_triage.sh` で行う。

| 残る候補 | 内容 |
| --- | --- |
| A | TCP の再送（WebSocket は TCP。1 フレーム落ちると再送タイマ 200〜600 ms 分途切れる） |
| B | ESP32 のアプリ側ループの停止（IMU の I2C 読み・制御ループの詰まり） |
| C | `esp32_bridge`（Python）の詰まり（50 Hz の `_drain_rx_queue`・GIL 競合） |
